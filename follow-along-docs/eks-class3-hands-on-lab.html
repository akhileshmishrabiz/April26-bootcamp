Exercise 1

01Create the EKS control plane (custom config)

Do this

Goal: stand up a real, managed EKS control plane through the console, understanding every field instead of clicking "next" blindly.

  1. Console → EKS → Create cluster. You'll be offered Auto Mode or Custom configuration. Choose Custom configuration and turn Auto Mode off — Auto Mode adds ~12% extra cost per node and hides the exact pieces this lab is teaching you to see.
  2. Name your cluster (e.g. august-cluster).
  3. Cluster IAM role — click "Create new role." The console attaches the correct managed policy (the Amazon EKS cluster policy) for you automatically — this is the control-plane-side IAM role, permitted to talk to EC2 and VPC APIs so it can manage nodes and load balancers on your behalf.
  4. Kubernetes version — pick a supported, non-bleeding-edge version (avoid the very newest unless you have a reason).
  5. Cluster access — choose EKS API (not the legacy aws-auth ConfigMap — nobody uses that path anymore). Leave it here; you'll come back to grant a second user access in Exercise 3.
  6. Networking — keep the default VPC for this lab. Choose private subnets only for the control plane when the console asks — EKS deliberately won't let you pick a public subnet here, precisely so newcomers can't accidentally expose the control plane's API to the internet.
  7. Security group — for this lab, choose one with open outbound access on port 443 so the control plane can reach nodes and other AWS APIs. In a real environment you'd scope this down; Class 4's Terraform version will show the tightened version.
  8. Cluster endpoint access — choose Private if you have a VPN/jump host set up, otherwise Public (scoped to your IP) is fine for this lab. Never leave it open to 0.0.0.0/0 in anything beyond a throwaway lab.
  9. Logging — enable at least API server logging so you can audit calls later; leave the rest off for now.
  10. Add-ons — keep the defaults checked: CoreDNS, kube-proxy, and the VPC CNI plugin. Do not skip the VPC CNI add-on — without it, nodes will show up as running EC2 instances but will never join the cluster (you'll deliberately reproduce this failure mode in Exercise 4).
  11. Click Create. This step only builds the control plane — it takes roughly 10–15 minutes. No nodes exist yet, and nothing can run yet.
What "custom configuration" actually bought you Every field above maps to something Akhilesh described in theory earlier in class: the cluster IAM role is the "left side" permission layer (control plane ↔ EC2/VPC APIs); the private-subnets requirement is EKS refusing to let you expose your API server by accident; the add-ons are exactly the three components he called out as load-bearing — CoreDNS for name resolution, kube-proxy for the iptables rules behind every Service, and the VPC CNI for pod networking. None of this is optional scaffolding; skip any one of them and something specific breaks later in this lab.

02Point kubectl at your new cluster

Do this

Goal: reproduce the exact aws eks update-kubeconfig / rename-context flow from class, and understand what it actually edits.

# before: only your kind context (if any) exists
kubectl config get-contexts

# add the new EKS cluster to your local kubeconfig
aws eks update-kubeconfig --name august-cluster --region <your-region>
Added new context arn:aws:eks:us-east-1:123456789012:cluster/august-cluster to /Users/you/.kube/config

# confirm the new, long ARN-style context now exists
kubectl config get-contexts

# give it a short, memorable name — exactly as done in class
kubectl config rename-context \
  arn:aws:eks:us-east-1:123456789012:cluster/august-cluster aug

kubectl config use-context aug
Switched to context "aug".
What update-kubeconfig actually wrote Open ~/.kube/config in an editor and look for the new entry: it added a cluster block with the API server endpoint URL and a base64 certificate-authority-data blob, plus a user block that shells out to aws eks get-token at request time rather than storing a static credential. That's the same file kind was writing to all along — EKS just adds one more context/cluster/user triplet to it, which is exactly why rename-context and use-context work identically to how you switched between kind clusters.

03AWS access ≠ Kubernetes access (IAM access entries)

Do this

Goal: reproduce the exact "I have AWS access, why can't I list pods?" moment from class, then fix it properly with an IAM access entry.

kubectl get pods -A
Error from server (Forbidden): pods is forbidden: User "arn:aws:iam::123456789012:user/your-user"
cannot list resource "pods" in API group "" at the cluster scope

This will fail for any IAM identity that wasn't the one that created the cluster — the cluster creator gets admin by default; nobody else does, automatically, no matter what AWS-side permissions they hold.

  1. Console → your cluster → Access tab → IAM access entries → Create access entry.
  2. Choose the IAM user or role you want to grant access to (type ahead to find it). Keep type = Standard.
  3. Attach an access policy — for this lab, attach the AmazonEKSClusterAdminPolicy so you can follow the rest of the exercises without permission friction. In a real team, you'd scope this to a read-only or namespace-limited policy instead — see the callout below.
  4. Scope = cluster (not namespace) for this lab.
  5. Save, then wait ~5–10 seconds for the change to propagate.
kubectl get pods -A
NAMESPACE     NAME                       READY   STATUS    RESTARTS   AGE
kube-system   aws-node-xxxxx             1/1     Running   0          2m   ← wait, see Exercise 4
kube-system   coredns-xxxxxxxxx-xxxxx    0/1     Pending   0          5m
kube-system   coredns-xxxxxxxxx-xxxxx    0/1     Pending   0          5m
Don't hand out AmazonEKSClusterAdminPolicy by default This lab uses the admin policy so nothing blocks you while you're learning. In a real team, follow the same instinct Akhilesh described for banking-grade environments: scope access entries per person or per team, often down to a specific namespace, using a read-only or namespace-restricted policy instead of cluster-wide admin. The access-entry scope field you saw in step 4 is exactly the lever for that — cluster-wide vs. a single namespace.

04Pending pods — and why EKS looks "empty" at first

Do this

Goal: see, hands-on, the exact difference the instructor pointed out between a kind cluster and a real EKS cluster — and understand why CoreDNS is stuck Pending.

kubectl get pods -n kube-system
NAME                       READY   STATUS    RESTARTS   AGE
coredns-xxxxxxxxx-xxxxx    0/1     Pending   0          6m
coredns-xxxxxxxxx-xxxxx    0/1     Pending   0          6m

kubectl describe pod -n kube-system -l k8s-app=kube-dns
...
Events:
  Type     Reason            Message
  ----     ------            -------
  Warning  FailedScheduling  0/0 nodes are available: no nodes found matching node affinity

Compare this to kubectl get pods -A against a kind cluster (see the Class 1 lab) — kind showed you etcd-..., kube-apiserver-..., kube-scheduler-..., and kube-controller-manager-... pods living in kube-system. Run the same command here:

kubectl get pods -n kube-system
# notice: no etcd pod, no kube-apiserver pod, no kube-scheduler pod anywhere
Why the control plane is invisible here — this is the point of "managed" On kind, the control plane runs as ordinary pods on your one node, so kubectl get pods -A shows you etcd, the API server, and the scheduler directly. On EKS, AWS runs those components on infrastructure you never see or query with kubectl — that's precisely what "AWS manages the control plane" means in practice, not just in theory. What you do see in kube-system on EKS are the pieces layered on top of the managed control plane: the CoreDNS, kube-proxy, and VPC CNI add-ons you selected in Exercise 1 — and right now, CoreDNS is Pending for the same reason any pod would be: there is nowhere to schedule it. Zero worker nodes exist yet.

05Provision a managed node group

Do this

Goal: give your cluster somewhere to actually run workloads, using the "Managed Nodes" option (AWS handles autoscaling/patching, EBS mounts supported) — the middle option of the three discussed in class.

  1. Console → your cluster → Compute tab → Add node group.
  2. Name it (e.g. aug-ng-1) and create/select a node IAM role — this is the second IAM layer from class: permissions for the nodes themselves (mounting EBS volumes, pulling from ECR, talking to the cluster).
  3. AMI type — keep the default (Amazon Linux). Capacity type — On-Demand for this lab. Instance type — t3.medium.
  4. Scaling configuration — set desired = 1, minimum = 1, maximum = 2. Keep it small; this is a lab, not a production sizing exercise.
  5. Subnets — choose private subnets only, same instinct as the control plane.
  6. Remote access (SSH) — leave this disabled. As Akhilesh put it: nobody should be able to log directly into these nodes; that's not a healthy pattern even for admins.
  7. Create the node group. Watch it progress from Creating → Active, which takes a few minutes.
# while it's provisioning, watch the EC2 side directly
aws ec2 describe-instances --filters "Name=tag:eks:nodegroup-name,Values=aug-ng-1" \
  --query "Reservations[].Instances[].State.Name"
[
    "pending"
]
The security-group detail from class, made concrete When the node instance comes up, check EC2 → Instances → your node → Security: you'll see it was attached the cluster's default security group automatically (not necessarily the custom one you may have created), and it needs inbound/outbound rules that let it reach the control plane's API server and let the control plane reach it back. If a node's EC2 instance appears healthy but never shows up in kubectl get nodes, this is the first thing to check — followed immediately by the VPC CNI add-on, per the next exercise.

kubectl get nodes

The aws-node pod is the VPC CNI plugin's per-node agent — one per node, exactly like kindnet was one-per-node on kind. Its job: assign real VPC IP addresses to pods and wire up routing so pod traffic behaves like normal AWS networking. Without it, this node would show as a healthy EC2 instance in the AWS console but would never appear in kubectl get nodes at all.

Reproduce the failure on purpose (optional, worth 5 minutes) To see exactly what Akhilesh meant by "if the CNI plug-in was not there you would not see this node here," try removing the VPC CNI add-on from Console → your cluster → Add-ons, then watch kubectl get nodes. The existing node will eventually go NotReady, and any new node group you provision afterward will show healthy EC2 instances that never join the cluster. Re-add the CNI add-on afterward to fix it before continuing.

07Deploy nginx & the default ClusterIP type

Do this

Goal: deploy the same dummy nginx app used in class, confirm the default (unspecified) Service type is ClusterIP, and reach it the only way ClusterIP allows — port-forward.

# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deploy
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          ports:
            - containerPort: 80
# service.yaml — note: no "type" field at all
apiVersion: v1
kind: Service
metadata:
  name: nginx-svc
spec:
  selector:
    app: nginx
  ports:
    - port: 8080
      targetPort: 80
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml

kubectl get svc nginx-svc
NAME        TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)
nginx-svc   ClusterIP   172.20.211.44   <none>        8080/TCP

Notice TYPE is ClusterIP even though the manifest never said so — this is EKS's (and every EKS cluster's) default, exactly as covered in class. It's also this same type that's recommended for production, precisely because it's private-only and pairs with an Ingress/Load Balancer Controller in front of it — the topic teed up for Class 4.

# the ClusterIP is not reachable from your laptop directly:
curl 172.20.211.44:8080
curl: (28) Failed to connect: Connection timed out

# the only way to reach it, exactly as demoed:
kubectl port-forward svc/nginx-svc 8080:8080
Forwarding from 127.0.0.1:8080 -> 80
# now open http://localhost:8080 — you'll see the nginx welcome page

08NodePort — and why it's a "security nightmare"

Do this

Goal: reproduce the NodePort demo end-to-end, including opening the security-group port and hitting the node's public IP directly — then feel exactly why the instructor called this a nightmare.

# service-nodeport.yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-svc-nodeport
spec:
  type: NodePort
  selector:
    app: nginx
  ports:
    - port: 8080
      targetPort: 80
      nodePort: 30380
kubectl apply -f service-nodeport.yaml
kubectl get svc nginx-svc-nodeport
NAME                  TYPE       CLUSTER-IP     PORT(S)
nginx-svc-nodeport    NodePort   172.20.9.201   8080:30380/TCP
  1. Note the nodePort must be in the 30000–32767 range — Kubernetes will reject anything outside it.
  2. Console → EC2 → find your node's security group → add an inbound rule: custom TCP, port 30380, source = your IP (never 0.0.0.0/0 even for a lab).
  3. Console → EC2 → your node instance → copy its public IPv4 address (only present because this lab used the default public VPC — see the callout below).
  4. Open http://<node-public-ip>:30380 in your browser — you should see the nginx page, reached with zero kubectl port-forward process running.
Why this is genuinely bad practice, made concrete You just: (1) exposed a specific node's IP directly to the internet, (2) opened a nonstandard, hard-to-remember port on a security group by hand, and (3) have no way to attach a normal domain name to ip:30380 without a DNS provider that supports SRV-style port records (most don't — Route 53 alias records map to an IP or ALIAS target, not a port). Multiply this by every node in an autoscaling group and every microservice you run, and you get exactly the "manual, cumbersome" mess Akhilesh described. This is why production EKS clusters essentially never use NodePort directly — it exists mostly as the plumbing that LoadBalancer and Ingress controllers configure automatically underneath the surface.

09LoadBalancer — and where it breaks down

Do this

Goal: let EKS provision a real AWS load balancer for you with zero extra plugins, reach the app over a real DNS endpoint, then run into the exact microservices-scaling problem raised in class.

# service-lb.yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-svc-lb
spec:
  type: LoadBalancer
  selector:
    app: nginx
  ports:
    - port: 80
      targetPort: 80
kubectl apply -f service-lb.yaml

# wait ~1-2 minutes for AWS to provision the load balancer
kubectl get svc nginx-svc-lb -w
NAME            TYPE           CLUSTER-IP     EXTERNAL-IP                                   PORT(S)
nginx-svc-lb    LoadBalancer   172.20.55.10   a1b2c3d4e5f6.us-east-1.elb.amazonaws.com     80:31980/TCP

# open the EXTERNAL-IP hostname directly in your browser on port 80

Notice port 80 matters here specifically — Akhilesh flagged that leaving the default target port unaligned (e.g. forcing the browser to use :8080 against a load balancer only listening on 80) is a common self-inflicted mistake. Keep the Service's port at 80 to match what a plain HTTP request expects.

Now, the scaling problem — hands-on. Deploy one more "microservice" and give it its own LoadBalancer Service:

kubectl create deployment second-app --image=hashicorp/http-echo -- -text="hello from service 2"
kubectl expose deployment second-app --type=LoadBalancer --port=80 --target-port=5678

kubectl get svc -l 'kubernetes.io/service-type'
NAME            TYPE           EXTERNAL-IP                                    PORT(S)
nginx-svc-lb    LoadBalancer   a1b2c3d4e5f6...elb.amazonaws.com               80:31980/TCP
second-app      LoadBalancer   f6e5d4c3b2a1...elb.amazonaws.com               80:32011/TCP
The exact problem this exercise is meant to make you feel You now have two separate AWS load balancers, each billed independently, each with its own DNS name, with no shared HTTPS termination, no path-based or header-based routing between them, and no way to point one clean domain at both. Now imagine five services, ten services. This is precisely the "surplus of load balancers and significant manual work" Akhilesh warned about — and it's the reason Class 4 moves to an Ingress + Load Balancer Controller pattern: one load balancer, path/host-based routing to many backing Services, centralized HTTPS. Don't fix this in this lab — leave the feeling of "this doesn't scale" intact; it's the whole motivation for the next class.
Filling the gaps

10What Class 3 covered in theory but not hands-on

1. Fargate vs. Managed Nodes vs. Self-managed Nodes — side by side

This lab only used Managed Nodes (Exercise 5). Here's the full trade-off table from class, for reference when you're deciding on a real project:

OptionPatching / scalingEBS supportStartup speedCompliance visibilityBest for
FargateFully AWS-managedNo (EFS only)Slow (~50–60s per pod)Nodes never visible — nothing to scanStable microservices, no storage, no spiky scaling
Managed NodesAWS-managed autoscaling & patchingYesFaster, but autoscaler still not instantNodes visible in EC2 — needs Qualys/Trend Micro etc. in regulated environmentsGeneral workloads needing persistent volumes
Self-managed NodesYou own launch templates, ASG, patchingYesDepends entirely on your ASG configFull control, full responsibility for compliance toolingHeavy compliance needs (banking/healthcare) requiring your own security stack

Many real teams mix strategies — e.g. Fargate for stable stateless microservices, Managed Nodes for anything needing storage or custom security posture, exactly as Akhilesh described from his own KPMG banking project.

2. CAP-theorem trade-off: data consistency vs. availability

The long discussion with Jasleen Kaur about why the control plane doesn't run "HA like a database" comes down to one rule: you cannot have both perfect data consistency and 100% availability during a network partition. EKS's etcd is the cluster's single source of truth, so during a partition, EKS chooses consistency and accepts a small window of downtime (typically single-digit seconds) rather than risk a split-brain where two control planes both believe they're authoritative. This lab doesn't (and can't safely) simulate a real partition — but it's worth knowing this is why a "control plane HA" feature request doesn't really make sense the way "database read replica" does.

3. RTO and RPO — plan for failure, don't chase 100% uptime

Recovery Time Objective (RTO): how long you can tolerate being down. Recovery Point Objective (RPO): how much data loss (measured in time) you can tolerate. Akhilesh's framing: 100% uptime is not physically achievable for a stateful system, so real system design work is about picking your RTO/RPO targets deliberately and building automated recovery (fast etcd restore, in EKS's case) to hit them — rather than pretending failure won't happen. This is explicitly called out as system-design-interview material.

4. Two IAM layers — don't conflate them

You touched both in this lab but it's worth stating explicitly: the cluster IAM role (Exercise 1) governs what the control plane can do to AWS (create load balancers, manage ENIs). The node IAM role (Exercise 5) governs what a worker node can do (mount EBS, pull from ECR). A third, separate thing — IAM access entries (Exercise 3) — governs which humans can run kubectl commands against the cluster at all. Mixing these up is one of the most common EKS support-ticket categories.

5. Ingress Controller vs. Load Balancer Controller — not the same thing

Harsha Reddy's question in class ("is the load balancer controller the same as an ingress controller?") got a "not exactly, but they work together" — and that's genuinely all Class 3 covers. The Load Balancer Controller is what lets an Ingress object (or a type: LoadBalancer Service) actually provision and configure a real AWS ALB/NLB; the Ingress Controller/object is the Kubernetes-native routing layer. Full detail is explicitly deferred to Class 4's three-tier app.

6. VPC IP range sizing

Briefly mentioned: your VPC's CIDR block directly caps how many pods + nodes your cluster can ever have, because the VPC CNI assigns real VPC IPs to pods (not an overlay network like kind's 10.244.0.0/16). A /16 VPC (≈64,000 IPs) is roomy; smaller VPCs can silently become the reason pods go Pending with no nodes at fault at all. Worth checking Subnet → available IPv4 addresses in the console if you ever see unexplained scheduling failures on a real project.

7. Deprecated fourth Service type

Akhilesh mentioned Kubernetes deprecated a fourth Service type as of 1.35 and told the class not to bother learning it. That's ExternalName — it's being phased out of common use in favor of clearer DNS-based patterns; you're not missing a hands-on exercise here, just know the name if it comes up.

12Cleanup & homework checklist

Cleanup order matters — do it in this order Delete Services with type LoadBalancer first and confirm the underlying AWS load balancers are gone in the EC2 console before deleting anything else — if you delete the node group or cluster first, orphaned ELBs/ALBs can be left behind, silently billing you. 
# 1. delete LoadBalancer-type services and CONFIRM the ELB/ALB disappears in console
kubectl delete svc nginx-svc-lb second-app

# 2. delete the rest of your workloads
kubectl delete -f service.yaml -f service-nodeport.yaml -f deployment.yaml

# 3. delete the node group (console: Compute tab -> delete node group)
aws eks delete-nodegroup --cluster-name august-cluster --nodegroup-name aug-ng-1

# 4. only after the node group is fully gone, delete the cluster
aws eks delete-cluster --name august-cluster

# 5. double-check nothing billable is left
aws elbv2 describe-load-balancers
aws ec2 describe-instances --filters "Name=instance-state-name,Values=running"

13Glossary

Control plane
The decision-making core of Kubernetes (API server, etcd, scheduler, controller-manager). On EKS, AWS runs and hides this entirely.
etcd
The key-value store holding the cluster's entire state — the single source of truth EKS protects via consistency-over-availability during failures.
VPC CNI
The AWS-native networking add-on that assigns real VPC IP addresses to pods; without it, nodes can't join the cluster.
CSI driver (EBS / EFS)
Add-ons that let Kubernetes mount AWS block storage (EBS) or network file storage (EFS) as persistent volumes.
Cluster IAM role
Control-plane-side permissions — lets EKS talk to EC2/VPC APIs to manage nodes and load balancers.
Node IAM role
Worker-node-side permissions — lets nodes mount storage, pull images, and join the cluster.
IAM access entry
Grants a specific human IAM user/role Kubernetes-level access (separate from AWS-level access); replaces the legacy aws-auth ConfigMap.
Fargate
Serverless compute for pods — no nodes to patch or scale, but slower startup, no EBS, and higher cost.
Managed node group
AWS-handled EC2 worker nodes with autoscaling and patching, but nodes remain visible in EC2 (compliance implication).
ClusterIP
Default Service type; private, cluster-internal only IP. The type actually used in production, paired with Ingress.
NodePort
Opens the same port (30000–32767) on every node's IP; functional but considered a security/manageability anti-pattern.
LoadBalancer
EKS calls the AWS API to provision a real load balancer automatically; fine for one app, doesn't scale cleanly to many microservices.
RTO / RPO
Recovery Time Objective / Recovery Point Objective — how long you can be down, and how much data-loss time you can tolerate.
Split-brain
The failure mode where two control planes both believe they're authoritative over the same state — the scenario EKS's consistency-first design exists to prevent.
