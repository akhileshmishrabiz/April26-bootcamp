Exercise 2 · Part 7

02TLS 1.2 in full: symmetric vs. asymmetric, the handshake, the CA

Concept — deep dive, interview-critical

Goal: be able to explain, from first principles and without notes, why TLS needs two different kinds of encryption rather than one.

The core problem TLS solves: a client and server want to encrypt everything they send each other, but the very first message between them travels over an unencrypted channel — so they can't just agree on a shared secret key by sending it in the clear.

Two encryption mechanisms, and why neither alone is enough:

  • Symmetric encryption — one key encrypts and decrypts. Fast, and the right choice for large volumes of data (this is what actually encrypts the bulk traffic once a connection is established). The unsolved problem: both sides need the same key, and there's no safe way to hand it over on a channel that isn't encrypted yet.
  • Asymmetric encryption — a mathematically linked key pair: whatever the public key encrypts, only the matching private key can decrypt (and vice versa, depending on direction). The public key can be handed out freely — an eavesdropper who captures it gains nothing, because they still don't have the private key.
The trick TLS 1.2 uses Don't try to send a symmetric key over an unencrypted channel directly. Instead, use asymmetric encryption just once, to smuggle the symmetric key across safely — then switch to fast symmetric encryption for the actual session. This is why you'll hear both terms in the same breath when people describe TLS: asymmetric crypto bootstraps the connection, symmetric crypto carries the traffic.

The handshake, step by step (the "hello server / hello client" exchange):

  1. Client Hello — the client sends the server a list of cipher suites it supports (which encryption algorithms it can do).
  2. Server Hello — the server picks one cipher suite from that list (historically often RSA) and confirms it back.
  3. Server sends its public key — generated fresh as part of a key pair. Anyone sniffing the wire can see this public key; that's fine by design.
  4. Client encrypts a session key using that public key and sends it back. Only the server's private key can decrypt it — so even though the public key travelled in the clear, the session key that was encrypted with it is safe.
  5. Server decrypts the session key with its private key. Both sides now hold the same symmetric key, and all further traffic uses fast symmetric encryption.

The man-in-the-middle problem this creates, and the fix (Certificate Authorities): step 3 above has a gap — how does the client know the public key it just received actually came from the real server, and not from an attacker who intercepted the connection and substituted their own key? If a hacker injects their own public key at that point, the client would unknowingly encrypt its session key for the attacker, not the real server.

The fix is a trusted third party: a Certificate Authority (CA) issues a certificate binding a public key to a specific domain, and signs it. The server now sends its public key plus this CA-signed certificate. The client verifies the signature against a CA it already trusts (built into the browser/OS), confirming the public key genuinely belongs to the domain it's connecting to — this is exactly the padlock icon and "connection is secure" indicator in a browser.

TLS 1.2's two named shortcomings 1. Single point of failure: the server's private key is the one thing standing between an attacker and every session key ever exchanged with it. If that private key is ever compromised, an attacker who recorded encrypted traffic in the past can retroactively decrypt it. 2. Latency — three full round trips before any application data can flow (hello/hello, key exchange, confirmation), plus the CPU cost of the encrypt/decrypt work itself on both ends — referred to in the industry as SSL/TLS offloading cost.
Exercise 3 · Part 7

03TLS 1.3: removing the single point of failure, cutting round trips

Concept — deep dive, interview-critical

Goal: be able to name specifically what changed between 1.2 and 1.3, not just that "1.3 is faster."

TLS 1.3 makes two concrete changes, both worth stating precisely in an interview rather than as "it's more secure and faster":

ChangeTLS 1.2TLS 1.3
Cipher suite freedomClient proposes a list; server picks one (e.g. RSA)Algorithm choice is largely hardcoded/standardized — much less negotiation surface
Key exchange mechanismClient encrypts a session key with the server's public key (RSA-style)Diffie–Hellman key exchange — both sides derive the same shared secret mathematically, without ever transmitting a private key or a pre-formed session key across the wire
Single point of failureYes — compromise the private key, decrypt past recorded trafficRemoved — no dependency on holding onto one static private key for the whole exchange
Round trips (new connection)ThreeOne
Round trips (resumed connection)ThreeZero

The Diffie–Hellman mechanics themselves were explicitly not derived from scratch in class ("high-quality mathematics... I won't go too deep into it") — the interview-relevant takeaway is knowing what problem it solves and what it replaces, not reproducing the algorithm.

How to actually answer this in an interview Don't open with terminology. Open with the goal: "the point of TLS is to get a client and server, who start with no shared secret over an unencrypted channel, to a point where they share one securely." Then walk into symmetric/asymmetric, the handshake, and only then the CA and the 1.2→1.3 delta. Leading with the destination, not the vocabulary, is exactly the "precise summary first" communication pattern flagged in Exercise 1.
Exercise 4 · Part 6

04Stateful vs. stateless: why databases don't fit the Deployment model

Concept

Goal: be able to state, in one line, why a database can't just be "a container with a disk attached" — this exact framing was flagged as an imprecise interview answer in an earlier class.

Stateless workloads (most web/API microservices) don't need to retain data beyond their own lifecycle — kill any pod, a fresh replacement comes up, nothing is lost because nothing important lived inside it. Stateful workloads (databases, message queues, anything with durable data) are fundamentally different: the data is the point, and it must survive pod restarts, rescheduling, and node failure.

This single distinction cascades into everything a standard Deployment gets wrong for a database:

  • Random pod naming — a Deployment's replacement pods get new, randomly-suffixed names every time. A database client needs a stable, predictable endpoint to keep connecting to the same instance.
  • No startup ordering — a Deployment starts all replica pods roughly simultaneously. A primary/replica database topology needs the writer up and healthy before readers start, or readers come up pointing at nothing.
  • No strict volume-to-pod mapping — in a plain Deployment + PVC setup, you (the human) are responsible for correctly wiring which pod gets which disk. Get it wrong once, and a replacement pod could attach to the wrong node's data.
  • Storage/node affinity — a volume is physically attached to a specific node. Whatever pod claims it has to be scheduled onto that same node, every time it restarts. Deployments have no built-in concept of "always schedule near this specific disk."
Exercise 5 · Part 6

05Database scaling: vertical scaling, read/write splitting, consistency trade-offs

Concept

Goal: know why "just add more replicas" — which works for stateless apps — does not work for a database's write path.

A stateless Deployment scales horizontally: add replicas, a load balancer spreads traffic, done. A database's writes do not scale this way. You cannot point two independent database instances at the same disk and let both accept writes — that's a direct path to data corruption, since neither instance knows what the other just wrote.

The practical pattern instead:

  • Vertical scaling for writes — give the single writer instance more CPU/memory/storage. Modern platforms increasingly support resizing live, without downtime, which is why vertical scaling is still a relevant, actively-used technique even though horizontal scaling gets more attention for stateless workloads.
  • Read replicas for reads — additional instances that continuously sync from the primary and serve read-only queries, which does scale horizontally, since read traffic can be spread across many replicas safely.
  • Application-level routing responsibility — it's the application's job to send writes to the primary and reads to a replica endpoint; the database doesn't do this automatically. This is one direct reason databases in Kubernetes use headless Services rather than a normal ClusterIP Service — the application needs to address a specific instance, not "any healthy pod behind this Service."
  • Eventual vs. strong consistency — read replicas lag the primary by some small delay (milliseconds to seconds) while they sync, so a read immediately after a write might not reflect it yet. Many applications (social media feeds, for example) tolerate this fine — it's called eventual consistency. Systems where a stale read is unacceptable (banking transactions, for example) require strong consistency, which trades away some of that read-scaling benefit to guarantee every read reflects the latest write.
Exercise 6 · Parts 6 & 7

06Storage fundamentals: StorageClass, PersistentVolume, PersistentVolumeClaim

Concept

Goal: be able to explain the three-object chain (StorageClass → PV → PVC) and what each one is actually for, using the coach's own analogy.

Three objects, three distinct jobs — this is the piece students most often blur together:

ObjectWhat it actually isCoach's analogy
StorageClassTells the cluster how to talk to a given storage backend — which provisioner/driver to use, and volume-binding behavior."Like installing a driver so your OS knows how to talk to new hardware." Must exist before anything can claim storage from it.
PersistentVolume (PV)Represents one actual chunk of storage — the real disk resource, wherever it physically lives.The disk itself, or in cloud terms, the provisioned EBS/EFS volume.
PersistentVolumeClaim (PVC)A pod's request for storage — "I need this much space, with these access characteristics." Kubernetes matches the claim to an available PV.An entitlement/reservation, not the disk itself — the thing the pod actually references.

On local (kind) clusters, you provision StorageClass/PV/PVC by hand, as below. In a real cloud environment (EKS + the EBS or EFS CSI driver), the StorageClass and PV creation are largely automated — you mostly just write the PVC, and the driver provisions a real EBS/EFS volume to match it.

Once claimed, the PVC is mounted into the pod at a specific filesystem path (e.g. /data) via the pod spec's volumes and volumeMounts — that mount point is where the application's writes actually persist beyond the pod's own lifecycle.

Clarified live — "pods don't touch raw disks" A student question drew out an important precision point: a pod never interacts with a physical disk directly. It interacts with a volume — an abstraction Kubernetes maintains — and the underlying infrastructure (kubelet, CSI driver, cloud provider) is responsible for the actual physical attach/detach to a node. For the purposes of this class, treat "volume" as a virtualized disk that the pod's filesystem paths point into.

07Hands-on: data survives a pod's death (Demo 1)

Live demo — matches coach's rebuilt code

Goal: watch, and then reproduce yourself, a pod dying and its replacement picking up exactly where the old one left off.

This is the demo that broke in Part 6 and was rebuilt for Part 7. The rebuilt version, matching the coach's current stateful-workload-k8s/demo1-pod-persistence/ folder, is a single-replica Deployment whose container appends a timestamped line to /data/events.log every 5 seconds, tagged with its own pod name:

k8s/storage.yaml — StorageClass + PV + PVC, in one file

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-host
provisioner: kubernetes.io/no-provisioner
volumeBindingMode: WaitForFirstConsumer
---
apiVersion: v1
kind: PersistentVolume
metadata:
  name: demo1-volume
spec:
  capacity:
    storage: 1Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: local-host
  hostPath:
    path: /mnt/host-volume/host-volume-data/demo1
    type: DirectoryOrCreate
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: demo1-claim
  namespace: demo1-persistence
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: local-host
  volumeName: demo1-volume
  resources:
    requests:
      storage: 1Gi

k8s/deployment.yaml — the writer pod

apiVersion: apps/v1
kind: Deployment
metadata:
  name: data-writer
  namespace: demo1-persistence
spec:
  replicas: 1
  selector:
    matchLabels: {app: data-writer}
  template:
    metadata:
      labels: {app: data-writer}
    spec:
      containers:
        - name: writer
          image: busybox:1.36
          command: ["sh", "-c"]
          args:
            - |
              mkdir -p /data
              echo "=== Pod started: ${POD_NAME} at $(date -u) ===" >> /data/events.log
              while true; do
                echo "$(date -u +%Y-%m-%dT%H:%M:%SZ) | pod=${POD_NAME}" >> /data/events.log
                sleep 5
              done
          env:
            - name: POD_NAME
              valueFrom: {fieldRef: {fieldPath: metadata.name}}
          volumeMounts:
            - {name: data, mountPath: /data}
      volumes:
        - name: data
          persistentVolumeClaim: {claimName: demo1-claim}

What was proved live, exactly as shown in the class recording:

  1. Before the PVC exists, the pod stays stuck in Pending — kubectl describe pod shows 0/2 nodes are available: persistentvolumeclaim "demo1-claim" not found. This is the "pod has a strict dependency on its PVC" point made concrete: no scheduling decision even gets attempted until the claim resolves.
  2. Once the PVC is applied, the pod schedules, pulls its image, and starts writing to /data/events.log — visible in real time with kubectl exec ... -- tail -f /data/events.log.
  3. Deleting the pod (kubectl delete pod -l app=data-writer) produces a new pod name, but reading the log afterward shows both the old pod's lines and the new pod's lines in the same file — direct proof the PV outlived the pod. The coach repeated the kill four times live to hammer the point home.
Named production gap, stated directly by the coach A bare PV like this one is not itself a backup strategy. If someone accidentally deletes the volume, the data is gone. The stated real-world practice: schedule regular snapshots of any production persistent volume, independent of whatever reclaim policy you've set.

08Hands-on: three pods, one disk (Demo 2, ReadWriteMany)

Live demo — matches coach's rebuilt code

Goal: understand exactly what has to be true — on both the PVC and the storage backend — before multiple pods can safely share one volume.

Same overall shape as Demo 1, but a 3-replica Deployment, and the access mode changes from ReadWriteOnce to ReadWriteMany (RWX):

# storage.yaml — the only meaningful diffs from Demo 1
apiVersion: v1
kind: PersistentVolume
metadata:
  name: demo2-shared-volume
spec:
  capacity: {storage: 1Gi}
  accessModes:
    - ReadWriteMany        # <-- was ReadWriteOnce in Demo 1
  persistentVolumeReclaimPolicy: Retain
  storageClassName: local-host
  hostPath:
    path: /mnt/host-volume/host-volume-data/demo2
    type: DirectoryOrCreate
# deployment.yaml — 3 replicas, all mounting the same PVC
spec:
  replicas: 3
  ...
      containers:
        - name: writer
          image: busybox:1.36
          command: ["sh", "-c"]
          args:
            - |
              mkdir -p /data/pods
              while true; do
                LINE="$(date -u +%Y-%m-%dT%H:%M:%SZ) | pod=${POD_NAME} | node=${NODE_NAME}"
                echo "${LINE}" >> /data/shared.log
                echo "${LINE}" > "/data/pods/${POD_NAME}.txt"
                sleep 5
              done

What was proved live: tailing /data/shared.log from any one of the three pods shows lines from all three pod names interleaved in the same file — direct evidence that concurrent writes from different pods to the same disk are landing correctly.

Named explicitly as the trap to avoid "By default you don't mount [a volume] to multiple pods — you have to be very careful here... if you think about databases, you're never going to allow a disk to attach to two nodes at the same time. Two different pods across two nodes writing to the same disk for a database will cause a blunder." ReadWriteMany is a deliberate, narrow-use-case decision (shared log/asset storage being the classic example) — never a database's data directory. Also: on kind, RWX "works" here only because every node bind-mounts the same host folder (see kind-config-vol.yaml's extraMounts) — that's a local-lab convenience, not how RWX works in the cloud (see Exercise 9).

10Init containers vs. sidecar containers

Concept

Goal: know both the functional difference and the YAML structural difference — this was asked twice, once conceptually and once as a "could I fake this with a command override?" trick question.

Init containerSidecar container
When it runsBefore the main container starts; must complete and exit firstConcurrently, for the pod's whole lifetime
Typical useWait for a dependency (DB reachable?), run a one-time setup/lookup taskOngoing supporting role — log forwarding, a proxy, a metrics exporter
Where it's defined in the pod specinitContainers: — a separate, pod-spec-level listInside the same containers: list as the main application

The trick question, and why the answer is "no": a student asked whether overriding a container's entrypoint/command could substitute for an init container. The coach's distinction: overriding a command changes what the main container itself executes instead of its default — it's still one container, one lifecycle. An init container is a fundamentally separate container object with its own lifecycle that completes and exits before the main container is even created. They solve different problems and aren't interchangeable.

Practical guidance given: don't try to memorize exact YAML syntax — focus on understanding the structural difference (pod-spec-level list vs. container-list member), since that structural placement is what actually determines the behavior.

Exercise 11 · Part 6

11Taints and tolerations: restricting where pods can land

Concept — full hands-on demo deferred to a later class

Goal: know the mental model (taint = lock, toleration = key) well enough to reason about scheduling, even without having run the demo yet.

A taint is applied to a node to repel pods from scheduling there by default (e.g. the built-in NoSchedule taint control-plane nodes carry, so ordinary workloads never land on them). A toleration is applied to a pod to say "I am explicitly allowed onto nodes with this specific taint" — described in class as "a special pass."

The named real-world use case: separating GPU-backed ML workloads from ordinary CPU-based web workloads to control cost — taint the expensive GPU nodes so nothing lands there by accident, then give only the ML pods that actually need a GPU the matching toleration (and typically an affinity rule pulling them toward those nodes too, which is a related but separate mechanism).

Exercise 12 · Part 7

12Why StatefulSets exist: identity, order, and strict volume binding

Concept

Goal: state precisely — not vaguely as "it's for databases" — what a StatefulSet actually guarantees that a Deployment does not.

Building directly on Exercise 4's stateless/stateful distinction, a StatefulSet is "just like a Deployment, but it behaves in a different way" — same basic job (keep N replicas running), three additional guarantees layered on top:

  • Stable, predictable pod names — ordinal suffixes (postgres-0, postgres-1, postgres-2), not random hashes. If postgres-0 dies, its replacement is also named postgres-0 — never a different name.
  • Ordered, sequential startup — pods come up one at a time, in ordinal order, each one reaching Ready before the next one starts. This is what lets a primary/replica topology guarantee the writer is healthy before any reader starts.
  • Strict, automatic pod-to-volume binding — each ordinal gets its own dedicated PVC via volumeClaimTemplates, and the StatefulSet controller itself enforces that postgres-0's replacement always reattaches to postgres-0's original volume — a pod's IP is not stable enough to use for this mapping (IPs change constantly), so the controller uses the pod's name as the durable key instead. You never hand-wire this mapping yourself the way you would with a plain Deployment + PVC — this was named directly as removing a whole category of human error.
Honest caveat, stated from the coach's own production experience "Everything breaks in the real world, no matter how well it sounds in theory." Named failure modes: a node can get corrupted such that a mounted volume simply won't detach cleanly; a volume can end up believing it's still bound to a node that no longer exists, requiring manual detach/reattach. This is given as the actual reason "a lot of people avoid running databases on Kubernetes" historically — not because the StatefulSet model is wrong, but because operational failure handling is genuinely harder than the clean-demo version suggests. Better tooling (see Exercise 15, CNPG) is what's changed the calculus.

  name: postgres
  namespace: demo1-statefulset

  serviceName: postgres      # <-- must name the headless Service above
  replicas: 3
  podManagementPolicy: OrderedReady
  selector:
    matchLabels: {app: postgres}
  template:
    metadata:
      labels: {app: postgres}
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          env:
            - {name: POSTGRES_USER, value: postgres}
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef: {name: postgres-secret, key: POSTGRES_PASSWORD}
            - {name: PGDATA, value: /var/lib/postgresql/data/pgdata}

            initialDelaySeconds: 10
            periodSeconds: 5
          livenessProbe:
            exec: {command: ["sh", "-c", "pg_isready -U postgres"]}
            initialDelaySeconds: 30
            periodSeconds: 10
          volumeMounts:
            - {name: data, mountPath: /var/lib/postgresql/data}
  volumeClaimTemplates:      # <-- this is what Deployments don't have
    - metadata: {name: data}
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: standard
        resources: {requests: {storage: 1Gi}}

Exercise 14 · Part 7

14Sharding is not horizontal scaling

Concept — interview-flagged, system design

Goal: state the distinction precisely — this was explicitly called a "must know" topic for system design interviews, not optional background.

Direct correction made in class, worth repeating precisely: sharding is not horizontal scaling. Horizontal scaling (as used for stateless workloads) means the same requests can be served by any of several identical replicas. Sharding means something structurally different: write traffic is split across multiple, independent writer instances based on some partitioning key (the class example: user ID ranges) — user A's data always lives on shard 1, user B's always on shard 2, and so on. No single instance holds all the data; each shard is its own self-contained database.

This requires an intermediary routing layer that decides, per request, which shard owns the relevant data — described as application-layer logic, not something the database or Kubernetes provides automatically.

Named failure mode — "hot shards" Sharding by a naive key (like raw user ID) can produce uneven load: in a platform like Instagram, a small fraction of accounts (high-follower creators) generate disproportionate read/write volume compared to typical users. If those accounts happen to land on the same shard, that shard becomes a bottleneck even though the overall system has capacity elsewhere. This is exactly why sharding strategy is treated as a serious system-design topic rather than a mechanical detail.
Exercise 15 · Part 7 hands-on

15CloudNativePG: why nobody hand-rolls database lifecycle scripts

Concept + live demo (basic install only — see the note above)

Goal: understand the operator pattern generally, and CNPG's specific value, well enough to explain why "just write a StatefulSet" stops being good enough in production.

Exercise 12 showed a raw StatefulSet gives you stable names and disks — but nothing about automated backups, TLS, connection pooling, or monitoring. The tempting next step is writing your own cron-job-based backup/restore scripts on top of the StatefulSet. The coach's explicit warning against this: custom, unverified automation for database lifecycle management is high-risk precisely because the blast radius of getting it wrong is large, and because a widely-used tool has already had its edge cases found and fixed by a large community — a bespoke script has not.

Enter CloudNativePG (CNPG) — a Kubernetes operator (9.2k+ GitHub stars, actively maintained) purpose-built for running PostgreSQL. The operator pattern in one line: a CRD teaches the API server a new resource type (here, Cluster, from the postgresql.cnpg.io API group), and the operator's own running Pods watch instances of that resource and do the real work — provisioning StatefulSet-backed Postgres instances, wiring replication, and handling the lifecycle tasks a raw StatefulSet can't.

Installing the operator, and the basic Cluster CR actually shown live

# Operator install — one manifest, standard for any CNPG version
kubectl apply --server-side -f \
  https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/release-1.30/releases/cnpg-1.30.0.yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: demo-pg
  namespace: demo2-cnpg
spec:
  instances: 3          # 1 primary + 2 replicas, chosen by the operator
  imageName: ghcr.io/cloudnative-pg/postgresql:16.4
  storage:
    size: 1Gi
  resources:
    requests: {memory: 256Mi, cpu: 100m}
    limits: {memory: 512Mi}
  bootstrap:
    initdb:
      database: appdb
      owner: appuser
      secret: {name: demo-pg-app-user}   # operator creates the DB + user for you

What was shown live: applying one Cluster manifest, then watching the operator create the primary and replica pods, the read/write and read-only Services, and Secrets — described directly as "you wrote one manifest; the operator built everything else." The coach also opened the CRD's fields in an editor to show the breadth of what's configurable through this one resource (backup target, TLS, connection pooling, monitoring hooks) without walking through each in depth.

Exercise 16 · Part 7 Q&A

16Startup, readiness, and liveness probes, in the right order

Q&A — Sai Kumar Rayudu asked directly, sequence clarified

Goal: know the actual sequencing relationship between these three probes — this is a commonly-confused topic and was asked about explicitly.

ProbeJobWhat happens on failure
StartupBlocks readiness checks from even beginning until the app has had enough time to fully initialize (useful for slow-starting apps — 10–20 minutes was given as a real example)If it never succeeds within its own timeout, the container is considered failed and restarted — but critically, it exists to prevent premature readiness failures, not to gate traffic directly
Readiness"The traffic gatekeeper" — decides whether this pod's IP gets added to the Service's routable endpointsPod stays running but is removed from/never added to the Service's endpoint list — no traffic reaches it
Liveness"A circuit breaker" — an ongoing health check for a pod that's already been serving trafficContainer is killed and restarted by the kubelet

The sequencing question, answered directly: for a typical web app with no unusually slow startup, you generally only need readiness and liveness — a startup probe becomes necessary specifically when an app needs meaningfully more time to initialize than you'd want readiness retries to tolerate. When present, a startup probe runs first and gates readiness — readiness checks don't even begin until the startup probe has succeeded (or its own failure threshold is hit). Once startup succeeds, readiness and liveness both run on their own ongoing schedules for the rest of the pod's life.

Concretely, why this matters: without a startup probe, an app that genuinely needs 10 minutes to initialize would fail its readiness probe's retry budget (say, 5 attempts over 100 seconds) long before it's actually ready — and get marked permanently unready, or restarted, for no real problem at all. The startup probe exists purely to prevent that false negative.

Exercise 17 · Part 7 Q&A

17Troubleshooting: "non-authoritative", and CoreDNS

Q&A — Sai Kumar Rayudu's real-world issue, diagnosed live

Goal: know the first two things to check when in-cluster DNS lookups behave unexpectedly, since this is a genuinely common real-world Kubernetes networking issue.

A student reported getting nslookup failures with a "non-authoritative" style response against certain in-cluster addresses in their own organization's cluster. The coach's diagnosis, given as the two most likely causes to check first:

  • Where you're running the lookup from matters. nslookup against a cluster-internal DNS name only resolves correctly from inside the cluster's network — running it from your own laptop terminal, outside the cluster, will not work the same way. The demo in Exercise 13 deliberately ran the lookup from a temporary pod inside the cluster for exactly this reason.
  • Cross-namespace network policies may be blocking the query entirely. Some organizations deliberately restrict cross-namespace traffic. Since DNS resolution is served by CoreDNS pods (typically living in kube-system), a restrictive policy can prevent your pod from ever reaching CoreDNS to begin with — producing exactly this kind of confusing, partial-looking failure.

The recommended troubleshooting step: deploy a disposable debug pod inside the same namespace as the resource you're trying to reach (or inside kube-system itself, where CoreDNS lives) and re-run the lookup from there. If it works from inside kube-system but not from your original namespace, that isolates the problem to a namespace-scoped network policy rather than CoreDNS itself being broken.

Production readiness review

Where the coach's demo would need to change for real production

The demo code is deliberately minimal — that's correct for teaching the mechanics on a local kind cluster in ~45 minutes. Below is what would actually need to change before any of this ran against a real workload on EKS. Treat this as a checklist for your own app-infra/k8s-services work whenever you introduce your first stateful component there.

AreaWhat the demo doesWhat production needs instead
Storage backendhostPath + a no-provisioner StorageClass, RWX only "works" because kind bind-mounts one host folder into every nodeA real CSI driver — the EBS CSI driver for block storage (ReadWriteOnce, most databases), or the EFS CSI driver for genuinely shared (ReadWriteMany) storage. hostPath has no place on a multi-node cloud cluster.
BackupsVerbally mentioned ("schedule regular snapshots"), not automated in either demoAutomated, tested backups: EBS snapshot lifecycle policies (DLM) for raw PVs, or CNPG's own ScheduledBackup + object-storage target (S3, not just MinIO) once you're past the basic Cluster CR shown here.

The one-line summary, if asked in an interview "The class demo proves the mechanics — stable identity, ordered startup, strict volume binding, and an operator handling lifecycle concerns a raw StatefulSet can't. Production hardens every one of those same primitives: real CSI-backed storage instead of hostPath, tested automated backups, anti-affinity across AZs, a PodDisruptionBudget, and secrets pulled from a secrets manager rather than committed to Git."

Glossary

Symmetric encryption
One key encrypts and decrypts. Fast, ideal for bulk data — but both sides need the same key, and safely sharing it is the hard part.
Asymmetric encryption
A linked public/private key pair — whatever the public key encrypts, only the private key can decrypt. Used to safely bootstrap a symmetric key exchange, not for bulk traffic itself.
Certificate Authority (CA)
A trusted third party that signs a certificate binding a public key to a domain, so a client can verify a server's public key genuinely belongs to that server rather than an attacker.
Diffie–Hellman
The key-exchange algorithm TLS 1.3 uses instead of RSA-style key transport — both sides derive the same shared secret without transmitting it, removing the single-private-key dependency.
SSL/TLS offloading
The CPU/latency cost a server pays to encrypt and decrypt traffic — one of the two named shortcomings of TLS 1.2 (the other being the three-round-trip handshake).
StorageClass
Tells the cluster how to provision storage from a given backend/driver — the "driver install" step that must exist before anything can claim storage from it.
PersistentVolume (PV)
The actual provisioned storage resource in the cluster — a real disk, wherever it physically lives.
PersistentVolumeClaim (PVC)
A pod's request/entitlement for storage, matched by Kubernetes to an available PV.
ReadWriteOnce (RWO) / ReadWriteMany (RWX)
PV access modes — RWO allows one node to mount the volume read-write at a time (the right default for a database's data directory); RWX allows multiple nodes to mount it simultaneously (shared logs/assets, not database data directories).
Init container
A container that runs to completion before a pod's main container(s) start — defined in a separate initContainers list at the pod-spec level. Used for setup/dependency checks.
Sidecar container
A container running alongside the main application for the pod's whole lifetime, defined in the same containers list. Used for ongoing supporting roles like log forwarding.
Taint
Applied to a node to repel pods from scheduling there unless they carry a matching toleration.
Toleration
Applied to a pod to permit it onto nodes carrying a specific taint.
StatefulSet
A workload controller like Deployment, but adding stable per-pod naming, strictly ordered startup/scale-down, and automatic strict pod-to-PVC binding via volumeClaimTemplates.
Headless Service
A Service with clusterIP: None — instead of load-balancing across pods behind one virtual IP, it provides individual DNS records per pod (<pod>.<svc>.<ns>.svc.cluster.local), letting clients address a specific replica.
Vertical scaling
Increasing a single instance's own CPU/memory/storage capacity — the scaling pattern a database's write path relies on, since writes cannot be horizontally distributed across independent instances the way stateless reads can.
Sharding
Splitting write traffic across multiple independent database instances by a partitioning key (e.g. user ID range) — distinct from horizontal scaling, which serves the same requests from any of several identical replicas.
Hot shard
A shard receiving disproportionate load relative to others because the partitioning key didn't distribute traffic evenly.
CRD (Custom Resource Definition)
A schema that teaches the Kubernetes API server to accept a new resource type. Inert alone — defines the shape, does nothing by itself.
Operator
Running software (Pods) that watches instances of a custom resource and performs the real work implied by it. CNPG is an operator for the Cluster CRD.
CloudNativePG (CNPG)
A widely-used Kubernetes operator for running PostgreSQL, providing automated backups, TLS, connection pooling (via a Pooler), and monitoring on top of a StatefulSet-based foundation — the production alternative to hand-rolled database lifecycle scripts.
Startup probe
Delays readiness checks until a slow-starting app has had enough time to initialize, preventing false "not ready" failures during a long boot.
Readiness probe
Controls whether a pod's IP is added to its Service's routable endpoints — "the traffic gatekeeper."
Liveness probe
An ongoing health check on an already-serving pod — failing it causes the kubelet to kill and restart the container ("a circuit breaker").
CoreDNS
The cluster-internal DNS server (typically in kube-system) that resolves Service and pod DNS names — the first thing to check when in-cluster nslookup behaves unexpectedly.
