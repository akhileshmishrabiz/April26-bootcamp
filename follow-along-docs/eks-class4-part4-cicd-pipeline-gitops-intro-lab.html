Exercise 1

01One flexible pipeline, not one per action

Concept

Goal: understand why the coach built a single workflow_dispatch pipeline with a choice input instead of one pipeline per infra component.

The class already has one pipeline that builds and pushes application images on push to main (eks-3tier-build-deploy.yaml). Infrastructure is a different problem: you don't want eks-core-infra/ (the cluster itself), k8s-services/ (the AWS Load Balancer Controller and other cluster add-ons), or 3-tier-app/infra (the app's own RDS/K8s resources) to redeploy automatically on every push — these change rarely and a mistake here is expensive. So the new pipeline is triggered manually, and the dropdown covers all three, not two:

on:
  workflow_dispatch:
    inputs:
      region:
        description: 'AWS Region'
        required: true
        default: 'ap-south-1'
      path_to_infra:
        description: 'Path to Terraform infrastructure code'
        required: true
        type: choice
        options:
          - Kubernetes-world/EKS/eks-core-infra
          - Kubernetes-world/EKS/k8s-services
          - Kubernetes-world/3-tier-app/infra

Note region is a plain string with a default, not a choice — only path_to_infra is constrained to a fixed dropdown. The job uses that choice to decide which directory to cd into before running terraform init/apply: cd ${{ inputs.path_to_infra }} && terraform init && terraform apply -auto-approve. One workflow file, three deployable components, zero duplicated pipeline logic.

Why choice and not just a free-text string A string input lets someone typo a path and fail the run (or worse, silently point at the wrong directory). A choice input constrains the person to a fixed, valid set of options defined in the workflow itself — the UI simply won't let you submit anything else. This is the same instinct as an enum type in a strongly-typed language: constrain the input space to what's actually valid, don't validate free text after the fact.
Exercise 2

02Reusing OIDC: the same trust, a new workflow

Concept

Goal: recognize that OIDC trust is set up once (an IAM role), and any workflow in the repo can use it — you don't reconfigure AWS per pipeline.

The coach reuses the same AWS-auth approach from eks-3tier-build-deploy.yaml in the new eks-infra.yaml, with permissions set at the job level rather than the workflow level:

jobs:
  infra-apply:
    runs-on: ubuntu-latest
    # environment: dev
    permissions:
      id-token: write
      contents: write
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ env.AWS_ROLE_ARN }}
          aws-region: ${{ inputs.region }}

id-token: write is the permission that lets this specific job request a short-lived OIDC token from GitHub, which AWS then trusts (via the IAM role's trust policy) instead of a long-lived access key. Because the trust relationship lives on the AWS side (the IAM role) and not inside any one workflow file, every workflow in the repo can reuse the exact same role — there's no new AWS-side setup required just because you added a second pipeline.

The unresolved class bug, and a likely root cause found in your own repo's Terraform Mid-session the plan/apply approval flow started failing with a permissions error that hadn't shown up before — the plan job (no environment: attached) worked fine, but the same OIDC config under a job with environment: dev attached did not. That's exactly why environment: dev is commented out above rather than active — it was never fixed on-air. Reviewing your own aws-github-oidc/oidc.tf, there's a strong candidate for the actual cause: your trust policy's sub-claim condition only matches repo:<org>/<repo>:ref:refs/heads/main. GitHub's OIDC token issues a different sub shape the moment a job has environment: attached — repo:<org>/<repo>:environment:dev — which your current condition list has no entry for, so the assume-role call is silently denied. The fix, when you get to writing your own gated job, is adding that second sub shape to the trust policy's StringLike condition values alongside the existing branch-ref one. Worth testing before assuming the workflow YAML itself is wrong.
Exercise 3

03Multi-environment code without duplicating anything

Concept

Goal: internalize the principle before you ever write a staging/prod split — don't copy code per environment, branch behavior inside one codebase.

Explicitly stated as a rule to live by: the same Terraform codebase should be able to deploy to multiple environments (dev, staging, prod) without duplicating resource blocks. Differences between environments — instance sizes, replica counts, whether a resource exists at all — are handled with variables, conditionals, and for_each/map-based transformations inside the existing code, not by maintaining prod/main.tf and staging/main.tf as separately-copied files that drift apart over time.

# conceptual sketch — not literal code to copy in
variable "environment" {
  type = string
}

locals {
  instance_size = {
    dev  = "db.t3.micro"
    prod = "db.t3.medium"
  }
}

resource "aws_db_instance" "postgres" {
  instance_class = local.instance_size[var.environment]
  # ...rest identical for every environment
}

The coach pointed to his own past ECS pipeline work as a concrete example of this pattern already implemented, and flagged it as something worth reading through independently rather than re-deriving from scratch — the underlying skill (building structure that scales across environments) matters more in interviews than raw Terraform syntax speed.

Confirmed — this is the exact reference file You've since shared it: a workflow named Terraform ECS 3 Tier infra, pointed at day13-ecs-3-tier/infra — the "date 13 ECS3" file named live in class. It's a real, working illustration of one relevant piece of this exercise: a single environment choice input (dev/prod) feeds both -backend-config=vars/${{ inputs.environment }}.tfbackend and -var-file=vars/${{ inputs.environment }}.tfvars — one job, one codebase, environment-specific backend and variables selected by input rather than by duplicating the whole file. Worth reading in full once you write your own multi-environment setup. One thing to notice, not copy: that file's environment: ${{ inputs.environment }} gates the entire job, including the plan step — meaning even a read-only plan against prod would wait on human approval. Whether that's the right call for your own pipeline (plan-needs-approval vs. only-apply-needs-approval) is worth deciding deliberately rather than copying either way.
Exercise 4

04GitHub Environments: the real approval gate

Concept

Goal: know exactly what a GitHub "Environment" configures, and why it's the mechanism — not a script, not a Slack bot — that companies actually use to require human sign-off before a deploy.

Under repo Settings → Environments, the coach created a dev environment and set:

  • Required reviewers — specific people (or teams) who must approve before a workflow run tied to this environment is allowed to proceed.
  • Prevent self-review — if the person who triggered the run is also a required reviewer, they cannot approve their own run. This is the technical enforcement of a real governance rule: the person requesting a change and the person approving it must be different people.
  • Wait timer — an optional forced delay before a deployment can proceed, even after approval.
  • Allow administrators to bypass configured protection rules — an explicit escape hatch, used deliberately in this demo since the coach is the repo admin and needed to demo both the gated and ungated paths.

In a real team, individual named reviewers don't scale — instead, companies define a CODEOWNERS file (in the repo's .github/ folder) that maps paths in the repo to a team, not an individual username. Approval authority then belongs to a role/team, survives someone leaving the company, and doesn't require editing environment settings every time headcount changes.

Exercise 5

05Two things named "environment," and they are not the same thing

Concept — a real mistake made live, worth learning from directly

Goal: never confuse these two again — the naming collision is genuinely confusing the first time.

GitHub Actions has two completely unrelated things that both use the word "environment," and the coach caught himself starting to type the wrong one live in class:

KeywordScopePurpose
env:Local to this one workflow file (job or step level)Sets shell/step environment variables for this run — e.g. env: TF_VERSION: 1.5.1
environment:References a named Environment configured in repo SettingsForces the job to satisfy that Environment's protection rules (required reviewers, wait timer, etc.) before running
jobs:
  apply:
    runs-on: ubuntu-latest
    environment: dev   # ← this is what triggers the approval gate
    env:
      TF_VERSION: 1.5.1  # ← this is just a plain variable, unrelated

Putting the job-level environment: dev key on a job is what actually activates the protection rules configured in Exercise 4. Without it, the Environment settings exist in GitHub's UI but have zero effect on any workflow run — they're inert until a job explicitly opts in via this keyword.

Exercise 6

06Splitting Plan and Apply so approval means something

Concept

Goal: understand why "approve this deploy" is meaningless unless the approver can actually see what they're approving first.

The first version of the pipeline gated the single Terraform-apply job behind approval — but a reviewer clicking "approve" with zero visibility into what was about to change isn't really reviewing anything; they're rubber-stamping. The fix: split into two separate jobs, plan (ungated, runs immediately, shows the diff) and apply (gated with environment: dev, only runs after the human sees the plan output and approves):

jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - run: terraform plan   # no approval needed — just information

  apply:
    needs: plan
    environment: dev           # approval gate lives here, not on plan
    runs-on: ubuntu-latest
    steps:
      - run: terraform apply

In real corporate/compliance-driven pipelines, this is taken further: the plan job writes its output to durable external storage — a GitHub Wiki page or an S3 bucket — so there's an audit trail proving exactly what was reviewed before the reviewer clicked approve, and so the apply job can be made to apply that saved plan file specifically (terraform apply <saved-plan-file>) rather than re-planning and trusting it produced the identical result. That two-step "plan-then-apply-the-saved-plan" pattern wasn't built live this session, but was named as the real-world version of what this simpler split is approximating.

What actually shipped is neither of these — worth knowing before you write your own The coach's committed eks-infra.yaml does not have this split active. The infra-plan job is present in the file but entirely commented out, and environment: dev on infra-apply is also commented out — almost certainly because of the OIDC sub-claim issue from Exercise 2, which was never resolved live. What ships is one ungated job running terraform apply -auto-approve directly. The plan/apply split above is the target pattern to build in your own version, not something you can assume is already working if you start from the coach's file as a base.

Your turn

When you write your own eks-infra.yaml, decide deliberately: keep it as one ungated job for now (matching what actually shipped, simplest to get working first), or build the real plan/apply split with the OIDC trust-policy fix from Exercise 2 applied first (matching what the class demoed but didn't finish). Either is a legitimate place to start — just know which one you're building and why, since "the coach's file already has this" isn't true of the gate itself.

Exercise 7

07LGTM, and the speed-vs-control trade-off

Culture / interview context

Goal: know this term cold — it's assumed vocabulary the moment you join any engineering team.

LGTM — "Looks Good To Me" — is the near-universal shorthand engineers use to approve a pull request or deployment. The coach was explicit that not knowing this term when he moved companies made him look inexperienced despite having the technical skills, and that a bootcamp graduate not recognizing it in an interview raises the same flag.

The deeper point behind teaching it here: approval gates are a genuine trade-off, not a free win. They add real delay (a plan that takes 5–10 minutes, a reviewer who has to notice the email, check it, and respond) in exchange for better control and a documented decision trail. Some teams — especially smaller, high-trust startups — deliberately choose to skip heavy gating and instead build a culture of ownership and accountability, where the person running a change is directly responsible for its outcome. Neither is objectively correct; which one a company chooses depends on its compliance requirements, size, and risk tolerance. Being able to articulate this trade-off — not just implement the YAML — is exactly the kind of answer this bootcamp keeps steering you toward for interviews.

Exercise 8

08Where the migration job actually belongs in the pipeline

Concept — connects directly to Part 3's migration Job

Goal: place the migration step correctly relative to build and deploy, and explain why the order is non-negotiable.

Part 3 built the migration Job and ran it manually. This session named where it belongs for real: after the new image is built, and before the new Deployment is applied — never after the deploy. The reasoning is a direct extension of the backward-compatibility discussion from Part 3:

  1. Suppose you migrate after deploying the new app version. For the window between deploy and migration, the new code (which may already assume a changed schema) is running against the old schema — a guaranteed crash window.
  2. Suppose instead the running app assumes tables that a migration is about to drop, and you migrate too early relative to a slow rollout. The still-running old Pods lose their tables mid-flight.
  3. The only safe order is: build → migrate → then deploy the new Pods — and the schema change itself must be backward-compatible with whichever app version is currently serving traffic, exactly as covered in Part 3 (keep old tables/columns around for a few revisions, drop them gracefully later — never breaking-change and clean up in the same step).

This is also why Terraform's actual failure behavior matters here (also from Part 3): if the migration job fails, a correctly-designed pipeline should block the deploy step entirely rather than attempt any kind of automatic rollback — Terraform itself never touches already-applied resources on a failed apply, and neither should your migration-failure handling invent a rollback that guesses at partial DB state.

Microservices and blast radius — the related architecture point raised alongside this A monolith with one shared database means one migration mistake can break the entire application. Microservices, each owning its own database, shrink the "blast radius" of any single migration or deploy mistake to just that one service — a real, concrete reason (beyond independent scaling) that companies choose microservices, and a good one-line answer if asked in an interview why microservices help operationally, not just architecturally.

09Secrets management: three strategies, one used today

Concept

Goal: be able to name and compare all three approaches, and explain why the current setup (option 1) is a legitimate choice given the project's actual compliance needs — not a shortcut.

StrategyHow it worksBest fit
1 · Terraform + AWS Secrets Manager (used now)random_password generates the DB password; aws_secretsmanager_secret / _version store the connection string; rotation can be automated via a scheduled Lambda or a forced re-applySingle AWS account, no hard cross-account compliance requirement — exactly this project's current context
2 · HashiCorp VaultSecrets live centrally in Vault, independent of any one AWS account; Terraform (and Kubernetes) reference Vault entries rather than owning secret values directlyMultiple AWS accounts needing one consistent rotation/audit story, rather than per-account Secrets Manager silos

10Automating Ingress → ALB → Route 53 → ACM entirely from Terraform

Concept

Goal: understand the full automated chain from "Terraform apply" to "HTTPS works on a real domain," and why each link exists.

The reasoning for keeping Ingress inside Terraform (rather than plain YAML) was made explicit this session: once the Ingress resource creates the ALB, Terraform can read that ALB's generated DNS name straight back out and feed it into a Route 53 record — fully automating domain mapping with no manual console click. The full chain, walked through live and confirmed against the coach's current (several-classes-ahead) code:

  1. Look up the existing hosted zone for your domain — data "aws_route53_zone" "main" { name = var.domain_name }.
  2. Request an ACM certificate for your subdomain, DNS-validated — aws_acm_certificate with validation_method = "DNS".
  3. Write the validation record ACM asks for automatically — aws_route53_record.cert_validation, looping over domain_validation_options — then wait for validation via aws_acm_certificate_validation, so terraform apply doesn't move on until the certificate authority confirms domain ownership. This is the CNAME-record step described in class: proving you own the domain before any CA will issue you a cert for it.
  4. Attach the validated certificate to the Ingress via annotations — the AWS Load Balancer Controller does the rest (creates the HTTPS listener on port 443, handles the TLS handshake) without you touching the ALB console: 
    annotations = {
  "alb.ingress.kubernetes.io/certificate-arn" = aws_acm_certificate.app.arn
  "alb.ingress.kubernetes.io/listen-ports"    = "[{\"HTTP\": 80}, {\"HTTPS\": 443}]"
  "alb.ingress.kubernetes.io/ssl-redirect"    = "443"
}
  5. Point the subdomain at the ALB — an aws_route53_record alias record, whose target is the ALB's own DNS name and zone ID, both pulled dynamically (see Exercise/Clinic below on why this has to be dynamic, not hardcoded).
Route 53 Zone ID vs. ALB Zone ID — the distinction that caused real confusion live These are two completely different values that happen to look similar and are easy to confuse: the Route 53 hosted-zone ID identifies your domain's DNS zone (one per hosted zone you own); the ALB's own zone ID is a fixed, AWS-published, per-region constant every Application Load Balancer in that region shares (needed by Route 53 to resolve an alias record correctly). Hardcoding the ALB zone ID per region works but is brittle and undocumented in your own code; the better pattern — what the coach eventually landed on — is pulling it dynamically: 
data "aws_lb" "ingress" {
  tags = {
    Name = "${var.app_subdomain}-ingress"   # matched via the ALB tag set in the Ingress annotations
  }
  depends_on = [kubernetes_ingress_v1.app_ingress_tls]
}

resource "aws_route53_record" "app" {
  zone_id = data.aws_route53_zone.main.zone_id     # ← Route 53's zone ID
  name    = "${var.app_subdomain}.${var.domain_name}"
  type    = "A"
  alias {
    name    = data.aws_lb.ingress.dns_name
    zone_id = data.aws_lb.ingress.zone_id          # ← the ALB's own zone ID, pulled dynamically, not hardcoded
  }
}
Forward-looking, not yet your own pattern This full chain (ACM + validation + alias record + dynamic ALB lookup) is real code from the coach's current repo, several classes ahead of where your own app-infra stands. Treat the exercise above as the target shape to build toward once HTTPS is formally assigned as your own exercise — don't feel behind if your current Ingress doesn't have this yet.
Exercise 11

11The teardown trap: Secrets Manager & KMS retention windows

Concept — a real operational gotcha, demoed live

Goal: know this failure mode exists before it costs you 20 confused minutes the way it did in class.

When you terraform destroy infrastructure that included an aws_secretsmanager_secret (or a KMS key), AWS does not delete it immediately — by default it enters a mandatory recovery window (a minimum of 7 days, configurable up to 30) during which the secret is "scheduled for deletion" but still technically exists. If you then re-run terraform apply to rebuild the same infrastructure before that window elapses, the create call fails: a secret with that exact name/ID already exists in AWS's backend, even though it's invisible in the console as "deleted."

aws secretsmanager delete-secret \
  --secret-id "db/<app>-db" \
  --force-delete-without-recovery

This bypasses the recovery window entirely and deletes immediately — appropriate for lab/dev teardown-and-rebuild cycles, and explicitly not something to reach for casually against a real production secret, since it forfeits the safety net the recovery window exists to provide (accidental-deletion recovery).

Live Debugging Clinic

Chasing the dynamic ALB zone ID

One extended live-debugging arc dominated the middle of this session — worth walking through for the process, not just the fix.

Symptom: Route 53 alias record rejected — "zone ID is not valid" After getting the Ingress to successfully create an ALB (confirmed by seeing a real DNS name appear in the Ingress's status), the coach tried to point a Route 53 alias record at it and hit a rejected zone ID. The value being used had been typed in by hand from an earlier lookup and no longer matched — or was never the right kind of value to begin with (the classic Route-53-zone-ID-vs-ALB-zone-ID mix-up from Exercise 10).
Diagnostic process — worth copying, not just the outcome Rather than dig through Terraform provider docs (described as slow and easy to get wrong), the coach asked ChatGPT and Cursor directly for "how to dynamically get the ALB zone ID in Terraform," giving full project context so the suggestion would actually fit the existing code rather than being generic boilerplate. The first suggestion used the ALB's ARN as a lookup key; a second attempt used a tag-based lookup instead (data "aws_lb" { tags = {...} }) — which is what ended up working, matching the coach's own real code shown in Exercise 10. The interview-relevant lesson stated explicitly: AI tools are genuinely useful for closing a "I know this is possible but forgot the exact syntax" gap quickly — but only when paired with enough judgment to evaluate whether the suggested approach is actually right for your specific setup, not simply accepted because it's syntactically valid and appeared instantly.
Smaller bugs hit in the same stretch A port mismatch resurfaced (Ingress backend pointed at 8000 when the actual Service was listening on 8080 after a code change) — caught by directly checking the Service's actual port rather than assuming the Ingress config was still correct. A "not the right shape of value" error on an ALB lookup (using the ARN where a tag or name was expected) was also hit and corrected before landing on the working tag-based lookup shown in Exercise 10.
Meta-lesson, consistent with Part 3's Clinic Every one of these was solved by inspecting the actual, current, live state — the real port a Service is forwarding to right now, the real DNS/zone values AWS is returning right now — rather than trusting what the code was assumed to say. The tool changed (AI assistant vs. AWS Console vs. curl) but the underlying discipline from Part 3's Clinic holds: verify live state, don't just re-read the code and hope.
Interview Communication Drill

Answer precisely, then elaborate

A significant chunk of this session was an explicit, named communication drill — not incidental class chatter. Two students answered technical questions with accurate but overly-detailed implementation-first answers, and the coach used both as live teaching moments about how to structure an interview answer.

The pattern being taught

Goal: lead every answer with a one-line, precise summary before diving into implementation detail — regardless of how much detail you actually know.

Question asked: "If you don't want to run your database inside RDS, what other option do you have?"

What was said (marked as imprecise)What the coach modeled instead
"We can attach the EBS CSI driver and give it a PersistentVolumeClaim and PersistentVolume.""We can run it on-prem, or on Kubernetes." — the actual top-level answer to the question asked — then, only if asked "how, specifically, on Kubernetes," go into StatefulSets, custom operators (e.g. CNPG for Postgres), and PVC/PV mechanics.
"You can run it as a container with access to a PVC where you put the data."Same correction: a database is not just another container — it carries consistency and durability requirements a stateless container doesn't, so the precise answer names the pattern (StatefulSet, or a purpose-built operator) rather than describing it as "a container with a disk attached."

The stated reason this matters, from the coach's own experience: giving accurate-but-unstructured, overly-detailed answers cost him a job offer despite passing every technical round — the interviewer's read was that the answers weren't precise, even though they were correct. Named explicitly as a common pattern among Indian engineers specifically, and something worth deliberately practicing against.

Framework example — Kubernetes vs. ECS, structured properly

Goal: have a reusable structure ready for "why would you choose X over Y" questions, not just facts about X and Y.

Applied live to "when would you choose Kubernetes over ECS for microservices": don't default to Kubernetes just because a workload is "microservices" — ECS runs microservices fine. Choose Kubernetes specifically when you need one of:

  • More control over deployment behavior, configuration, and visibility than ECS's simpler abstraction offers.
  • Existing high-quality open-source tooling that solves your specific problem and doesn't have an ECS equivalent — the concrete example given: CNPG (CloudNativePG), a mature Postgres operator with no comparably mature ECS-ecosystem equivalent, making "run Postgres reliably on Kubernetes" a solved problem in a way it isn't on ECS.
  • An existing standard platform already built out at your company (monitoring, observability, deployment tooling already standardized on Kubernetes) — a new microservice joining an existing Kubernetes-based ecosystem is a much smaller decision than picking Kubernetes cold for a single new service.

The coach was candid that his own live answer to a related question (should front-end and back-end ever share one Pod?) was correct but not structured — a useful, honest admission that getting the content right is necessary but not sufficient; building a repeatable answer structure is a separate skill worth practicing deliberately, and one he described as still actively working on himself.

Looking ahead

The GitOps problem (full pattern tomorrow)

With about ten minutes left, the class shifted entirely to concept — no code — setting up tomorrow's Argo CD session. This is worth understanding well before that class starts, since the coach explicitly asked everyone to research it independently first.

Concept — the actual problem, before the tool name

Goal: be able to explain why GitOps exists before you ever hear the words "Argo CD" — the problem is the interview-relevant part, the tool is just one implementation of the answer.

Walked through as a diagram: code is pushed to GitHub → CI builds and pushes a new image → a pipeline step runs kubectl set image deployment/<name> <container>=<new-image> to trigger the rollout. This works, but has a structural weakness: anyone with cluster credentials can run that same kubectl command manually, at any time, completely outside the pipeline — bypassing code review, bypassing the pipeline's record of what was deployed, bypassing everything. When that happens, what your Git history/pipeline logs say is running and what's actually running in the cluster silently disagree. This gap is called configuration drift, and it's the core problem GitOps exists to close.

The GitOps answer: make your Git repository the single source of truth for desired cluster state, and run a tool inside the cluster that continuously watches Git and reconciles the live cluster state back to match it — automatically undoing any manual, out-of-band change, and refusing to let drift persist silently.

Why this also solves a security/access problem, not just a drift problem Before GitOps became common (and before OIDC was widely adopted), pipelines like Jenkins needed their own long-lived, directly-provisioned Kubernetes credentials — another set of secrets to rotate and secure. Individual developers needing to run kubectl commands against the cluster also needed their own direct credentials and had to understand cluster-level commands just to ship a change — extra cognitive load and a wider blast radius of who has direct cluster access. A GitOps controller centralizes cluster write-access into one trusted, in-cluster component; developers interact with Git (or the GitOps tool's own UI) instead of running kubectl directly.
Argo CD vs. Flux — named, not yet taught Two tools became the standard GitOps implementations: Flux and Argo CD. Both are real and still used, but Argo CD has become the dominant one industry-wide (framed simply as "the tool that got broader adoption becomes the default") — which is why tomorrow's class is built entirely around it rather than Flux.
Also previewed, explicitly not taught yet — save these terms, don't research them deeply now Two topics were named as "coming soon, more detail tomorrow/later" and deliberately not explained in depth this session: (1) how Argo CD actually handles rollout strategies (rolling, blue-green, canary) — flagged as a much bigger topic than "how the Pod comes up," extending into how users are shifted between old/new versions and how failures are recovered from; and (2) the two core rolling-update parameters, maxSurge (how many new Pods can come up at once above the desired count) and maxUnavailable (how many existing Pods can be down at once during the rollout) — walked through with a whiteboard example (5 Pods, maxSurge: 2) showing new Pods entering Pending → Running → passing health checks before an old Pod is killed, one-for-one. Glossary

workflow_dispatch
A GitHub Actions trigger that allows a workflow to be started manually from the UI (or API) rather than automatically on push/PR — used here so infra changes are never accidentally auto-deployed.
choice input type
A workflow_dispatch input constrained to a fixed set of options, shown as a dropdown — prevents free-text typos from silently pointing at the wrong resource.
GitHub Environment
A named deployment target configured under repo Settings, carrying its own protection rules (required reviewers, wait timer, self-review prevention) — inert until a job references it via the environment: key.
environment: (job-level key)
Attaches a job to a configured GitHub Environment, forcing that Environment's protection rules to be satisfied before the job runs. Not to be confused with env:.
env:
Sets plain environment variables scoped to a workflow/job/step — has no connection to GitHub Environments or approval gates.
CODEOWNERS
A file (in .github/) mapping paths in a repo to the team or individuals responsible for approving changes to them — the scalable alternative to naming individual usernames as required reviewers.
LGTM
"Looks Good To Me" — standard shorthand for approving a pull request or deployment; assumed vocabulary on any engineering team.
Terraform plan/apply split
Running terraform plan as an ungated, informational job and gating only terraform apply behind approval, so a human reviewer can see the actual diff before signing off — as opposed to approving a job that shows nothing.
Backward compatibility (schema)
Designing a database migration so the currently running app version continues to work against the new schema, typically by keeping old columns/tables for several revisions before finally dropping them — necessary because rollbacks and rolling deploys both require old and new code to briefly coexist against one database.
Blast radius
The scope of impact a single failure or mistake can cause. Microservices with per-service databases shrink blast radius versus a monolith with one shared database and one shared migration path.
AWS Secrets Manager recovery window
A mandatory minimum delay (7–30 days) before a "deleted" secret is actually purged from AWS's backend — causes name-collision errors on rapid destroy/recreate cycles unless bypassed with --force-delete-without-recovery.
ACM (AWS Certificate Manager)
AWS's service for issuing and managing TLS certificates; DNS-based validation proves domain ownership via a CNAME/validation record before a cert is issued.
Route 53 hosted-zone ID
Identifies a specific DNS zone (domain) you own in Route 53 — distinct from an ALB's own zone ID, a common source of confusion.
ALB zone ID
A fixed, AWS-published constant shared by every ALB in a given region, required by Route 53 to correctly resolve an alias record pointing at that ALB. Best retrieved dynamically via a data "aws_lb" lookup rather than hardcoded.
Configuration drift
The state where a system's actual running configuration no longer matches what its source of truth (e.g. Git, or a CI pipeline's records) claims it should be — typically caused by manual, out-of-band changes.
GitOps
An operational pattern making a Git repository the source of truth for desired system state, with an in-cluster controller continuously reconciling live state to match it — closing the configuration-drift gap and centralizing cluster write-access.
Argo CD
The most widely-adopted GitOps controller for Kubernetes; watches a Git repo and reconciles cluster state to match it. Subject of the next class.
Flux
The other major GitOps controller for Kubernetes — still actively used, but with smaller market share than Argo CD industry-wide.
maxSurge / maxUnavailable
The two core rolling-update parameters controlling, respectively, how many extra Pods can be created above the desired count during a rollout, and how many existing Pods can be taken down at once — previewed this session, full depth promised in an upcoming class.
