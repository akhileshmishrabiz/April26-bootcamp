Exercise 1

01Why short-lived OIDC beats static AWS keys

Concept

Goal: be able to explain, in an interview, why nobody should paste an AWS access key/secret into a GitHub Actions secret anymore.

Any time compute or a third party needs to call AWS, the answer is a role, never a long-lived credential. Inside AWS, this is trivial — attach an IAM role to an EC2 instance or EKS node (exactly what you relied on in Part 1 for ECR pulls). GitHub is not inside AWS — it's a third party — so it can't just "have" an IAM role. The bridge is OIDC (OpenID Connect): GitHub proves its identity via a signed token, AWS's STS (Security Token Service) verifies that token and hands back a short-lived, scoped credential, and the credential expires automatically when the job ends. No secret ever sits in a GitHub repo waiting to be leaked.

The same exact problem — and the same fix — applies one layer down: your Kubernetes pods (frontend, backend) also need to talk to AWS sometimes, and Kubernetes is conceptually a third party to AWS too, even though it's running inside EKS. (That's IRSA/Pod Identity — mentioned in class as a "later" topic, not built yet in this session.)

Don't mix these up An IAM role and a Kubernetes service account are two unrelated concepts that happen to rhyme. A role is AWS-side identity. A service account is Kubernetes-side identity. IRSA/Pod Identity is the mechanism that links them — but that's a future class, not this one.
Exercise 2

02The three pieces of trust: provider, role, conditions

Concept

Goal: know the exact three AWS objects OIDC federation needs, and what each one is for.

  1. An IAM OIDC identity provider — registers GitHub's own OIDC endpoint (token.actions.githubusercontent.com) with AWS. Without this, AWS has no idea what "GitHub" even is; you're explicitly telling IAM to trust tokens signed by that issuer.
  2. An IAM role whose trust policy's Principal is Federated (pointing at the provider from step 1), and whose Action is sts:AssumeRoleWithWebIdentity — not the plain sts:AssumeRole you'd use for an EC2-to-role trust.
  3. Conditions on that trust policy — this is the part people skip and regret. Without conditions, any GitHub repository anywhere could assume your role. Conditions restrict by sub (subject — encodes org/repo/branch/tag) and aud (audience — always sts.amazonaws.com for this use case).

The sub claim's format is worth memorizing since you'll hand-build these patterns:

# pin to one branch:
repo:OWNER/REPO:ref:refs/heads/main

# allow any ref (any branch, tag, environment — wide open):
repo:OWNER/REPO:*

# pin to a tag pattern, e.g. v1.x.x releases only:
repo:OWNER/REPO:ref:refs/tags/v*
The mafia analogy, translated to IAM terms Your instructor's framing, minus the color: federation establishes that GitHub-as-an-entity is allowed to talk to AWS at all. Conditions establish that this specific repository, on this specific branch is the one allowed to actually use the role. Skipping conditions is the equivalent of authenticating the whole organization instead of one named person — technically works, catastrophically over-permissioned.

Exercise 3

03Templating the trust policy for N repos, dynamically

Concept

Goal: make the trust policy extend to new repos/branches without anyone rewriting the resource block.

The pattern: define a plain list of maps (repo, owner, branch), then use a Terraform for expression to transform that list into the exact sub string format each entry needs, wrapped in distinct() to de-duplicate. This is the same "map transformation" technique referenced from earlier ECS material — worth being fluent in it, since it's a very common senior-level Terraform pattern (config-as-data, not config-as-code-you-edit-every-time).

locals {
  github_repo = [
    { user = "yourhandle", repo = "your-repo-1", branch = "main" },
    { user = "yourhandle", repo = "your-repo-2", branch = "*" },
  ]

  github_oidc_subjects = distinct([
    for r in local.github_repo :
    r.branch == "*" ?
    "repo:${r.user}/${r.repo}:*" :
    "repo:${r.user}/${r.repo}:ref:refs/heads/${r.branch}"
  ])
}

That github_oidc_subjects list is what plugs directly into the trust policy's StringLike condition from Exercise 2.

Design principle worth internalizing Your instructor drew a real distinction here: the template (the for expression, the resource block) should stay boring and simple, since other engineers — who may not know advanced Terraform — need to extend it just by adding a line to the github_repo list. Cleverness belongs in the template's construction, not in what a day-to-day contributor has to touch.
Your turn

Refactor Exercise 2's hardcoded repo/branch into this locals + for pattern. Add a second fake repo entry to prove the loop actually scales without touching the resource block. Output the role ARN (output "aws_iam_role_arn") — your GitHub Actions workflow will need it next.

Exercise 4

04Wire the role into a GitHub Actions workflow

Concept

Goal: understand the two things a workflow needs before OIDC will even attempt to authenticate.

  1. Job-level permission — without permissions: id-token: write on the job, GitHub simply won't mint the OIDC token in the first place. This trips up almost everyone the first time; the symptom is a generic auth failure with no obvious cause.
  2. The role ARN itself, passed to aws-actions/configure-aws-credentials (or equivalent) as role-to-assume. Note there's no access key, no secret key anywhere in this step — just the ARN and a region.
permissions:
  id-token: write
  contents: read

jobs:
  build:
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::<account-id>:role/aws-github-oidc-aug26
          aws-region: us-east-1
Your turn

Add the permissions block and the credentials step to a workflow file in your app repo. Don't build the image build/push steps yet — just confirm this step alone succeeds (check the job log for "assumed role with web identity") before adding anything else.

Exercise 5

05Matrix builds: parallel, not sequential

Concept

Goal: build frontend and backend images at the same time, from one job definition, not two copy-pasted jobs.

GitHub Actions' strategy.matrix takes a list and spins up one parallel job instance per entry — same job definition, different input each time. For a 2-service app this feels like overkill; the real payoff shows up at 20–30 microservices, where sequential builds would make every pipeline run take unacceptably long.

strategy:
  matrix:
    services:
      - name: frontend
        path: 3-tier-app/src/frontend
        ecr_repo: augk8s26-frontend
      - name: backend
        path: 3-tier-app/src/backend
        ecr_repo: augk8s26-backend

steps:
  - name: Build and push
    run: |
      docker buildx build \
        --platform linux/amd64 \
        --cache-from type=registry,ref=${{ matrix.services.ecr_repo }}:buildcache \
        --cache-to type=registry,ref=${{ matrix.services.ecr_repo }}:buildcache \
        -t ${{ env.AWS_ACCOUNT_ID }}.dkr.ecr.${{ env.AWS_REGION }}.amazonaws.com/${{ matrix.services.ecr_repo }}:${{ github.sha }} \
        --push \
        ${{ matrix.services.path }}

Two more things worth knowing: docker buildx (not plain docker build) is what enables registry-based build caching on ephemeral GitHub-hosted runners — a fresh runner has no local Docker layer cache, so without --cache-from/--cache-to type=registry, every build starts from zero. And the commit SHA (github.sha) as the image tag isn't decoration — it's the traceability link between "this exact image in ECR" and "this exact code state," used later for manual/automated deploys.

Your turn

Add the matrix strategy and the docker buildx build --push step to your workflow. Run it and confirm the Actions UI shows two parallel jobs (build (frontend, ...) and build (backend, ...)), not one sequential job doing both.

Exercise 6

06The registry-path bug — a real live-class postmortem

What actually happened

Goal: recognize this exact failure signature yourself, because it's genuinely easy to reproduce by accident.

The class's pipeline failed at the push step with:

ERROR: failed to push augk8s26-backend:sha... failed to authorize: failed to fetch
oauth token: unexpected status from GET request to
https://auth.docker.io/token?scope=repository%3Alibrary%2Faugk8s26-backend...
401 Unauthorized: access token has insufficient scopes

The debugging trail is worth following, because it's a realistic interview-style "walk me through how you'd debug this":

  1. First hypothesis (Jasleen): the IAM policy ARN on the role attachment was missing the AWS account ID. Plausible-sounding, but wrong — arn:aws:iam::aws:policy/AdministratorAccess is an AWS-managed policy, and AWS-managed policy ARNs use the literal string aws in the account-ID segment, not a real account number. That ARN was correct all along.
  2. Second clue: OIDC login itself had already succeeded (visible earlier in the job log) — so the authentication layer was fine. The failure was specifically at the push step, later in the pipeline.
  3. Root cause, found by re-reading the actual error: auth.docker.io — Docker Hub's auth endpoint — was being contacted, not ECR's. The image tag was missing the full ECR registry hostname, so Docker's client silently assumed docker.io/library/<name> instead of failing loudly with "no registry specified."
Tag writtenWhat Docker assumes
augk8s26-backend:${{ github.sha }}Docker Hub — docker.io/library/augk8s26-backend (wrong)
<account>.dkr.ecr.<region>.amazonaws.com/augk8s26-backend:${{ github.sha }}Your private ECR repo (correct)
The actual fix Always use the fully-qualified ECR URI in both the image tag and the buildx cache references — a Docker image tag with no registry hostname is not an error, it's a silent default to Docker Hub. This is precisely why Exercise 5's skeleton above already has the full <account>.dkr.ecr.<region>.amazonaws.com/ prefix baked in — write yours the same way from the start rather than hitting this live.
Interview-grade takeaway "ECR login succeeded but the push failed with a Docker Hub auth error" is a specific, memorable failure signature — a wrong/missing registry hostname in the tag, not an OIDC or IAM permissions problem, even though the symptom (401 Unauthorized) looks identical to a permissions issue at first glance. Knowing to check the hostname in the error URL, not just the status code, is the actual debugging skill here.
Exercise 7

07Namespace, Secrets, and ConfigMaps in Terraform

Concept

Goal: define Kubernetes objects as Terraform resources instead of YAML, specifically for anything holding dynamic/sensitive values.

The kubernetes Terraform provider gives you kubernetes_namespace, kubernetes_secret, kubernetes_config_map, etc. — same objects you'd write in YAML, just expressed as HCL, which means they can reference other Terraform resources directly (your RDS instance's address, a freshly generated random_password) with zero copy-pasting of values between systems.

resource "kubernetes_namespace" "devopsdozo" {
  metadata {
    name   = "devopsdozo"
    labels = { name = "devopsdozo" }
  }
}

resource "kubernetes_secret" "backend_secret" {
  metadata {
    name      = "backend-secret"
    namespace = kubernetes_namespace.devopsdozo.metadata[0].name
  }
  data = {
    DB_LINK     = aws_secretsmanager_secret_version.dbs_secret_val.secret_string
    SECRET_KEY  = random_password.backend_secret_key.result
    DB_USERNAME = aws_db_instance.postgres.username
    DB_PASSWORD = random_password.db_password.result
  }
  type = "Opaque"
}

resource "kubernetes_config_map" "backend_config" {
  metadata {
    name      = "backend-config"
    namespace = kubernetes_namespace.devopsdozo.metadata[0].name
  }
  data = {
    DB_HOST         = aws_db_instance.postgres.address
    DB_PORT         = aws_db_instance.postgres.port
    DB_NAME         = aws_db_instance.postgres.db_name
    ALLOWED_ORIGINS = "http://localhost:3000,http://localhost:80"
  }
}

The rule of thumb the class used to split secret vs. config-map: sensitive values (credentials, tokens, anything you wouldn't want in `kubectl describe` output in plain text) go in the Secret; everything else — hostnames, ports, feature flags — goes in the ConfigMap. Note Kubernetes Secrets are base64-encoded, not encrypted, at this layer — "sensitive" here means "don't put in a ConfigMap," not "cryptographically protected."

Why the deployments themselves stay in YAML Notice the pattern: Namespace, Secret, ConfigMap, Service went into Terraform (static-ish, changes rarely, benefits from referencing other TF resources) — but the Deployment (which changes on every image push) stayed in plain YAML, applied separately with kubectl apply. This mirrors Part 1's "separate what changes on a different lifecycle" principle from state-management, just applied one layer down inside a single app.
Your turn

In 3-tier-app/infra/k8s.tf, write the namespace, backend secret, backend config map, frontend config map, and both `kubernetes_service` resources (ClusterIP, ports 8000 and 3000 per the app's own docker-compose.yml). Exercise 8

08Resource requests & limits — the double-ratio pattern

Concept

Goal: know what number to reach for by default, and be able to justify it, not just recite it.

Requests = the minimum a pod needs to be scheduled at all. The scheduler will not place a pod on a node that can't satisfy its request — set it too low and the pod may crash-loop on startup with an OOM (out-of-memory) event before it even finishes booting; set it unrealistically high and pods sit Pending forever because no node has that much free capacity.

Limits = the ceiling a pod is allowed to consume before Kubernetes kills and restarts it. Skip limits entirely and a single pod with a memory leak can consume an entire node's memory, starving every other pod on that node — a "noisy neighbor" failure mode that's entirely avoidable.

Workload typeStarting point (class's stated numbers)
General-purpose lab/demo baselinerequest: 128Mi / 0.25 CPU
General-purpose production baseline (never go below this in prod)request: 256Mi / 0.5 CPU
AI/ML workloadsrequest: ~2Gi RAM, 1–2 CPU (often GPU too)
Databasesfixed allocation sized to real projected capacity — don't expect these to autoscale the way stateless app pods do

The double-ratio pattern: set limits to roughly double whatever you set for requests. This isn't arbitrary — it gives a pod headroom to absorb real traffic spikes and helps the Horizontal Pod Autoscaler (HPA) actually function, since HPA scales based on observed CPU/memory usage relative to requests; with no limit set, usage can't cleanly cross a threshold that triggers scaling, because there's nothing bounding it.

resources:
  requests:
    memory: "256Mi"
    cpu: "250m"
  limits:
    memory: "512Mi"
    cpu: "500m"
Two distinct OOM causes — don't conflate them in an interview answer (1) Startup OOM — request set too low, the app can't even finish initializing within its allotted memory, dies immediately, repeats (`CrashLoopBackOff`). (2) Runtime OOM — the app started fine but a memory leak (or genuine traffic growth) causes usage to climb past the limit over time, at which point Kubernetes kills the process and a fresh pod replaces it. The limit is what turns an unbounded leak into a bounded, self-healing restart instead of an entire node going down.
Your turn

Add resources.requests and resources.limits to both the backend and frontend Deployment YAML, using the production baseline (256Mi/0.5 CPU request) and the double-ratio rule for limits. Be ready to explain, out loud, why you didn't use the 128Mi lab-default number.

Exercise 9

09Readiness, liveness, and startup probes

Concept

Goal: cleanly distinguish all three probe types — this is one of the most commonly confused topics in Kubernetes interviews, per your instructor's own experience.

ProbeQuestion it answersWhat happens on failure
Readiness"Is this pod ready to receive traffic right now?"Pod is pulled out of the Service's routing (removed from the endpoint list) — it stays Running but gets zero traffic until it passes.
Liveness"Is this already-running, already-serving pod still healthy?"Kubernetes kills the pod and a replacement is scheduled — this is the "circuit breaker" your instructor described.
Startup"Has this slow-booting app finished initializing yet?"Delays when readiness/liveness even begin checking — prevents a legitimately-slow-starting app (stateful sets can take up to ~20 minutes) from being killed by liveness before it ever had a chance to start.

The concrete failure readiness probes prevent: without one, a brand-new pod gets an IP and is immediately added to the Service's routing table the instant it's Running — even if the app inside hasn't finished connecting to its database yet. Real requests get routed there and fail. A readiness probe is the gate that withholds traffic until an HTTP check (or command) actually succeeds.

readinessProbe:
  httpGet:
    path: /health
    port: 8000
  initialDelaySeconds: 10
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3

livenessProbe:
  httpGet:
    path: /health
    port: 8000
  initialDelaySeconds: 20
  periodSeconds: 15
  timeoutSeconds: 3
  failureThreshold: 3
The exact bug the class hit live — worth memorizing the symptom The backend pods entered a restart loop (readiness failing repeatedly) because the probe's path pointed at /health while the actual application endpoint was /healthy — a one-word mismatch. The failure mode looked alarming (`Pending`, then restarts) but the fix was a single string in the YAML/config map. Lesson: before assuming a networking, IAM, or database problem, verify the probe path against the app's actual exposed route — this class of bug is extremely common and extremely cheap to fix once found.
Your turn

Exercise 10

10Cluster-internal DNS: how frontend finds backend

Concept

Goal: know the exact DNS naming convention CoreDNS generates automatically, and why it's needed at all.

Service names aren't globally unique across a cluster — two different namespaces can both have a service called backend-service, the same way two different companies can both have an employee named "Sam." CoreDNS (running as a DaemonSet on every node — you saw it back in Part 1's kube-system pods) solves this by auto-generating a fully-qualified, cluster-unique DNS name for every Service the instant it's created:

<service-name>.<namespace>.svc.cluster.local

# concretely, for this app:
backend-service.devopsdozo.svc.cluster.local
frontend-service.devopsdozo.svc.cluster.local

This is the value you put in the frontend's BACKEND_URL config-map entry — never a pod IP (those change on every restart) and never localhost (that only works inside a single pod's own network namespace, not across pods).

Your turn

Set the frontend's BACKEND_URL config-map value to the full DNS name for the backend service, including port (backend-service.devopsdozo.svc.cluster.local:8000). Then move to Exercise 13 to actually prove this resolves.

Exercise 11

11Namespace scope vs. cluster scope, for real

Concept

Goal: be able to state, without hesitating, which common Kubernetes objects live inside a namespace and which don't.

Namespace-scoped (bound to one namespace)Cluster-scoped (no namespace)
Secrets, ConfigMaps, Deployments, Services, Pods, IngressNodes, PersistentVolumes, StorageClasses, ClusterRoles

Why the split: namespaces are a logical organizing layer, not a physical one. A Deployment referencing a Secret in a different namespace simply fails — namespaces enforce that kind of local grouping. But storage (which physical disk backs a volume) and networking (how packets actually flow between nodes, via the CNI) operate at the node/cluster level regardless of which namespace a pod happens to live in — which is exactly why cross-namespace communication needs the DNS mechanism from Exercise 10 rather than some namespace-aware shortcut.

12Authenticating Terraform's kubernetes provider — and the gap left open

Concept, honestly framed

Goal: understand what the class actually did here, and why it's explicitly not the final answer.

Once you add kubernetes_* resources to Terraform, the provider block needs a way to authenticate to the cluster's API — the same "AWS access ≠ Kubernetes access" boundary from Part 1 applies here too, just at the Terraform-execution layer instead of your own kubectl.

provider "kubernetes" {
  config_path = "~/.kube/config"   # reads your local kubeconfig — laptop-only
}
This is a deliberate shortcut, not the recommended pattern — the class said so live config_path pointing at a local kubeconfig file only works because it's your laptop's file, with your personal IAM identity's cached credentials. It will not work inside a GitHub Actions runner — there's no kubeconfig there, and no persistent identity to generate one from. Your instructor flagged this explicitly as "a bad way, I'll do the better way" and did not build the fix in this session — the real answer (likely aws eks get-token via a data source, or an EKS-specific exec-based auth block) is unresolved as of this class and is fair game to ask about, or look into yourself, before Part 3.
Your turn

Add the kubernetes provider block using config_path for now — it's fine for local terraform apply runs while you're building this out. But don't wire your GitHub Actions workflow to run terraform apply against the kubernetes_* resources yet; that authentication gap is real and unresolved. Exercise 13

13Debugging with a throwaway pod: nslookup, dig, psql

Do this

Goal: prove DNS resolution and database connectivity actually work, using disposable debug pods — a technique you'll reuse constantly in real cluster work.

# DNS resolution check — confirms CoreDNS is mapping the service name correctly
kubectl run dns-test --rm -it \
  --image=busybox:1.36 \
  --restart=Never \
  -- nslookup backend-service.devopsdozo.svc.cluster.local

Server:    172.20.0.10
Address:   172.20.0.10:53
Name:      backend-service.devopsdozo.svc.cluster.local
Address:   172.20.149.129

# database connectivity check — confirms nodes can actually reach RDS on port 5432
kubectl run pg-test --rm -it \
  --image=postgres:16 \
  --restart=Never \
  -- psql "postgresql://<user>:<pass>@<rds-endpoint>:5432/<dbname>" -c "SELECT 1;"

Both commands follow the same shape: spin up a minimal, purpose-built image (busybox has nslookup/dig built in; the official postgres image ships psql), run one command, --rm deletes the pod immediately after. This isolates the test — if DNS resolves here but your app still can't reach the backend, the bug is in your app's own config, not the cluster's networking.

Why this matters more than it looks This is the "is it DNS?" instinct made concrete — instead of guessing whether a connectivity failure is your app's code, its config map, cluster networking, or the database's security group, each of these throwaway-pod tests isolates exactly one link in that chain. The class used this exact technique to rule out "database unreachable" as the cause of the backend's actual failure (which turned out to be the /health vs /healthy bug from Exercise 9) — a wasted hypothesis check, but a legitimately good habit: verify infrastructure-level connectivity before assuming application-level bugs, or vice versa.
Code Review Clinic

Every bug the class hit live, and why

Unlike Part 1's clinic (which compared your repo against static class code), these are bugs the instructor and students hit live, on camera, in this exact session — arguably more valuable, since you get the full debugging trail, not just the fixed version.

Bug 1 — Docker image tag missing the ECR registry hostname Covered in full in Exercise 6. Symptom: 401 from auth.docker.io, not ECR. Root cause: tag was <ecr-repo-name>:<sha> instead of <account>.dkr.ecr.<region>.amazonaws.com/<ecr-repo-name>:<sha>. Fix: always fully-qualify the registry in both the tag and the buildx cache refs.
Bug 2 — Readiness probe path didn't match the app's real health endpoint Covered in full in Exercise 9. /health configured, /healthy actually exposed. Symptom: backend stuck restarting, no useful application logs (logs only appear if the app itself is configured to emit them — a pod restart loop from a failed probe doesn't automatically produce log output explaining why).
Bug 3 — Kubernetes ConfigMap key with invalid characters Applying the frontend config map failed with a validation error: ConfigMap/Secret keys must be lowercase alphanumeric plus -, _, or . only — no uppercase, and the specific value that broke it here came from a key that didn't follow that pattern. Fix was reformatting the key name in the Terraform-defined config map. Worth internalizing as a rule, not just a one-off fix: keys in K8s object metadata/data maps follow this pattern everywhere, not just ConfigMaps.
Bug 4 — Frontend deployment missing the backend URL environment variable entirely The frontend pods failed readiness not because of a wrong value, but because the environment variable pointing at the backend wasn't wired into the Deployment's envFrom/env section at all — it existed in the config map (Exercise 10) but the Deployment spec never referenced it. A reminder that defining a ConfigMap value and actually consuming it in a pod spec are two separate steps; Terraform/YAML won't catch a config map key you forgot to map into a container's env block.
Meta-lesson across all four None of these were exotic failures — a missing hostname, a typo'd path, an invalid character, a forgotten env reference. Your instructor's own framing, almost verbatim: "in the real world your AI will not be that helpful no matter how good it is — I had to manually look up and fix this myself." The debugging skill (read the actual error, check the actual endpoint, verify the actual key) is the transferable interview-relevant skill here, more than any individual fix.
Direct from the Q&A

Terraform vs. Helm — why the class chose Terraform for K8s config

Deepak asked the question worth having a real answer for in an interview: why Terraform instead of Helm charts for Kubernetes configuration? The instructor's answer, condensed:

  • Static credentials never belong in a Helm chart, full stop — if you're managing databases, secrets, or anything dynamic via Terraform anyway, keeping Kubernetes config in the same tool avoids ever having to copy a live credential out of Terraform state into a chart's values file.
  • This is a genuine production pattern, not a bootcamp simplification — the instructor's own team runs a full-Terraform approach for infra, with plans to layer in HashiCorp Vault + External Secrets Operator for credential management as microservices scale up.
  • The dividing line that emerged through the session: dynamic infra state → Terraform (namespace, secrets, config maps, services — things that reference other Terraform-managed resources), fast-moving deploy state → plain YAML applied via kubectl (Deployments, since the image tag changes on every push and you don't want to run a full Terraform plan/apply cycle just to roll a new image).
  • Alternatives exist and are valid — Vault, External Secrets Operator — but "never put secrets directly in a Helm chart" was stated as a near-universal rule regardless of which tool you pick for the dynamic side.

Glossary

OIDC (OpenID Connect)
An identity federation protocol that lets a third party (GitHub) prove its identity to AWS via a signed token, without a static credential.
STS (Security Token Service)
The AWS service that verifies OIDC tokens and issues short-lived, scoped credentials in response — the actual mechanism behind AssumeRoleWithWebIdentity.
Federated principal
An IAM trust-policy principal type for external identity providers, as opposed to an AWS-native principal like an EC2 service or another AWS account.
Matrix strategy
A GitHub Actions feature that runs one job definition once per entry in a list, in parallel, instead of requiring separate copy-pasted job blocks.
Buildx registry cache
Docker Buildx's mechanism for persisting build-layer cache in a remote registry, needed because ephemeral CI runners have no local disk cache between runs.
Readiness probe
A per-pod health check that gates whether a pod receives traffic from its Service — failing it removes the pod from routing without killing it.
Liveness probe
A per-pod health check that, on failure, causes Kubernetes to kill and replace the pod — a circuit breaker for already-running-but-unhealthy pods.
Startup probe
A delay mechanism for slow-booting apps that postpones readiness/liveness checking until initialization has had time to complete.
Requests (resources)
The minimum CPU/memory a pod needs to be scheduled onto a node at all.
Limits (resources)
The maximum CPU/memory a pod may consume before Kubernetes throttles (CPU) or kills (memory) it.
CoreDNS
The cluster-internal DNS service that auto-generates a <service>.<namespace>.svc.cluster.local endpoint for every Kubernetes Service.
Namespace-scoped vs. cluster-scoped
Whether a Kubernetes object type is bound to one namespace (Secrets, Deployments, Services) or exists cluster-wide (Nodes, PersistentVolumes, StorageClasses).
