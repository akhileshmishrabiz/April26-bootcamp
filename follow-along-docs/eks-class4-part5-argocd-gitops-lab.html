Exercise 1

01Database migrations must be version-controlled too

Concept — interview-flagged

Goal: be able to state, precisely, what "rolling back a deployment" actually requires when a database is involved — this was named directly as a frequent, difficult interview question.

Opening five minutes, before any Argo CD content: a reminder that rollback strategies are genuinely complicated and worth independent research (carried over from Part 4). The concrete addition this session: database migrations need their own version history, tracked deliberately, the same way application code has commit history. Each migration version represents one state of your schema — add a column, add a table, and you have a new version, kept alongside the old ones rather than overwritten.

The reason this matters for rollback specifically: rolling back "the app" by itself is not enough. Rolling back the application code without also rolling back the database migration state leaves you with new code (or old code) running against a mismatched schema — which is exactly the kind of crash window Part 3 and Part 4 already walked through from the deploy-ordering side. Different companies solve the "how do we track and apply this" problem differently — some keep migrations in a separate repository maintained by a data-focused team, others fold it into the same app pipeline — but the requirement itself (version your schema changes, roll back code and schema together) doesn't change.

Assigned, not covered This was flagged as homework, not classroom content: research the different rollback patterns companies actually use for both application code and database migrations, specifically because it comes up in interviews and is "complicated" enough to need real study rather than a one-line answer.
Exercise 2

02CRDs and Operators: how Kubernetes learns new tricks

Concept

Goal: define both terms precisely enough to use them correctly in a sentence, and know which one does which job.

Kubernetes, out of the box, only understands its own built-in resource types — Deployment, Service, Job, and so on. It doesn't know what "Argo CD" is, or what a Postgres cluster managed by a third-party tool should look like. To teach it, Kubernetes exposes an API extension mechanism with two distinct halves:

PieceWhat it actually isJob
CRD — Custom Resource DefinitionA schema. Defines a brand-new resource type Kubernetes will now accept — the shape of the YAML, what fields exist.Lets you write kind: Application (or whatever the new type is called) and have the API server accept it as valid, the same way it already accepts kind: Deployment.
OperatorA running piece of software (itself deployed as one or more Pods) that watches instances of that new custom resource type.Does the actual work implied by the custom resource — creates the real underlying objects, keeps them healthy, reacts when reality drifts from what the custom resource says should exist.

A CRD alone is inert — it just makes a new kind of YAML syntactically legal. Nothing happens when you apply one on its own. The operator is what turns "Kubernetes now accepts this shape of object" into "Kubernetes now actually does something when you create one."

Why companies package whole applications this way The example given: a complex multi-component product (built on Zookeeper, Kafka, a custom search engine, its own internal services) that takes roughly 40 minutes to start correctly, in a strict order, with dependencies configured a very particular way. If a vendor just handed you the raw containers and said "figure out the startup order yourself," every customer would burn significant engineering time getting it right — and get it wrong in different ways. Instead, the vendor packages the entire application, dependency graph and all, as a CRD plus an operator. You deploy one custom resource; the operator handles the 40-minute correct-order startup internally. You don't need to understand or reproduce their internal architecture — you only need to know what your own environment has to provide (e.g., if a piece of it is a StatefulSet, you need persistent storage configured correctly).

Exercise 3

03Why Kubernetes' own control loop isn't enough for Argo CD

Concept — from a real, extended Q&A (Jas N)

Goal: this exact question gets asked in interviews almost verbatim — "Kubernetes already reconciles, so why do you need another tool for it?" Be ready with the precise answer, not a vague one.

First, the baseline everyone already has from earlier parts: a control loop is a mechanism that continuously compares desired state to current state and acts to close any gap. Kubernetes has this built in for its native resources — kill a Pod that's part of a Deployment, and Kubernetes' own control loop notices the current replica count no longer matches the desired count and creates a replacement, with zero third-party tooling involved.

The precise answer to "why isn't that enough": Kubernetes' built-in control loops only know about Kubernetes' own built-in resource types. They reconcile a Deployment back to its desired replica count because Deployment reconciliation is logic Kubernetes itself ships with. Kubernetes has no opinion at all about which Git commit's manifests should be the source of truth — that's not a concept native Kubernetes resources know about or care about. Argo CD's operator exists specifically to run that control loop: "does the live cluster state match what's declared in this Git repo path, right now" — a comparison Kubernetes itself has no built-in mechanism for, because Git isn't a Kubernetes concept.

So the two control loops operate at genuinely different layers, and both are running simultaneously, unbothered by each other: Kubernetes' native loop keeps a Deployment's replica count correct; Argo CD's loop keeps the definition of that Deployment (which image tag, how many replicas it's supposed to want) aligned with what Git says it should be. Argo CD itself even runs as a Kubernetes Deployment — so if an Argo CD Pod dies, Kubernetes' own native loop restarts it, the same as any other Pod. Argo CD doesn't replace or duplicate Kubernetes' reconciliation; it adds a new kind of reconciliation Kubernetes was never designed to know about.

Close, but not the same thing: Argo CD sync vs. Terraform idempotency A student compared Argo CD's reconciliation to Terraform's idempotency directly. Worth being precise about the difference if this comes up: idempotent describes an operation that produces the same result no matter how many times you run it — running terraform apply twice in a row with no changes does nothing the second time. Argo CD's reconciliation is a different property: it's continuous and standing, not "run-once-and-done." It doesn't wait to be manually re-triggered; an operator Pod is always running, checking on an interval (by default, roughly every 3 minutes — see Exercise 8), actively watching for drift rather than only acting when a human invokes a command.
Exercise 4

04Argo CD ships as a Helm chart, on purpose

Concept

Goal: understand the adoption logic — this is a general pattern for any serious open-source Kubernetes tool, not an Argo-CD-specific quirk.

Argo CD is not part of Kubernetes — it's an open-source project a group of engineers built to solve the exact drift/source-of-truth problem named at the end of Part 4, which then got adopted broadly enough to become close to a de facto standard. Whoever builds a tool like this faces an adoption problem: if they just publish raw source code and tell you to write your own CRDs and operators against their logic, almost nobody adopts it — people don't want to read an unfamiliar codebase just to figure out how to install something.

So the maintainers do the packaging work themselves: Argo CD is distributed as a Helm chart that includes its own CRDs and its own operator Pods already wired up correctly. Installing it is "point Helm at the chart," not "hand-write operator logic yourself." This is the same underlying pattern named in Exercise 2 for the Zookeeper/Kafka example — package the complexity once, at the source, so every downstream user gets a one-command install instead of reimplementing internals.

Assigned, not covered — Helm 3 vs. Helm 4 Named explicitly as independent research, not classroom content this session: look up what changed between Helm 3 and Helm 4 (Helm 2 preceded both and is no longer relevant). Framed as good interview-prep background on how the tool your helm_release resources depend on has itself evolved.

05Installing Argo CD: CLI first, Terraform for real

Concept + live demo

Goal: see the manual path once, understand exactly why it's the wrong one to keep, before Exercise 14 replaces it.

Demoed first, deliberately, as the thing not to keep doing: raw Helm CLI commands run directly against the cluster.

helm repo add argo https://argoproj.github.io/argo-helm
helm install argocd argo/argo-cd -n argocd --create-namespace

This works — a real, healthy Argo CD install comes up, namespace and all. The problem named explicitly: components installed this way are effectively infrastructure (long-lived, expected to still be there in six months), but running the install as a bare CLI command leaves no record anywhere of what was installed, with which values, or how to reproduce it. "Infra-feeling" components belong in Terraform for the same reason the EKS cluster itself does — repeatable, reviewable, versioned, not "whatever a person happened to type into their terminal that day."

The manual install was torn back down before moving on — both the Argo CD Application config, and the underlying Helm release itself (helm uninstall from the argocd namespace) — so the Terraform-managed version in Exercise 14 wasn't fighting a leftover manual one.

06Getting into the UI: port-forward and the initial admin secret

Concept + live demo

Goal: know the two-step "get in for the first time" ritual cold — you'll do this on every fresh Argo CD install.

Before any Ingress/HTTPS exposure exists (that's Exercise 15), the fastest way to reach the UI locally is standard Kubernetes port-forwarding to the argocd-server Service:

kubectl port-forward service/argocd-server -n argocd 8080:443

Then open https://localhost:8080 and accept the self-signed certificate warning. Username is always admin; the initial password is auto-generated at install time and stored as a Kubernetes Secret — retrieved, not chosen:

kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d
Documented best practice, named but not demoed Argo CD's own getting-started guide recommends deleting argocd-initial-admin-secret after the first login, once a real admin password/identity provider is configured — the initial secret is meant to be a one-time bootstrap credential, not a standing one. Not acted on live in this session (the class kept regenerating and re-reading it repeatedly through the demo), but worth doing for real once your own install is stable.
Exercise 7

07The Argo CD Application: teaching it what "source of truth" means

Concept + live demo

Goal: know exactly which fields on an Argo CD Application matter and what each one answers.

Creating an Application in the UI (equivalent to applying an argoproj.io/v1alpha1 Application custom resource — see Exercise 2) is how you tell Argo CD which Git path is the source of truth for which cluster resources. The fields that matter, walked through live:

  • Repository URL — the Git repo Argo CD should watch.
  • Revision — HEAD (tracks whichever branch is currently checked out/default) vs. an explicit branch or tag. For this demo, HEAD against main was used — explicitly called out as not the real-world pattern (see Exercise 13).
  • Path — must be a directory, not a single file. Argo CD watches everything matching inside that directory.
  • Cluster URL — which cluster to deploy into. Argo CD can manage multiple remote clusters from one install; this demo used the local, in-cluster option since Argo CD is running in the same EKS cluster it's deploying to.
  • Destination namespace — must match the namespace your actual workload manifests are already scoped to.
  • Directory recursion — if the target path has nested subfolders each containing more manifests, a recursive option tells Argo CD to walk the whole tree rather than only the top level. Not needed for this flat demo layout, but named as relevant for larger repos.
Exercise 8

08Sync policy: manual vs. automatic, and what "3 minutes" means

Concept + live demo, with a real unresolved bug

Goal: know precisely what triggers a sync, since "Argo CD watches Git" undersells what's actually happening.

Sync policy on an Application is either Manual (a human clicks "Sync" in the UI, or runs the CLI equivalent, every time) or Automatic (Argo CD applies changes on its own once it detects the live cluster is out of sync with Git). A direct student question — "does it just check the latest commit ID?" — got a precise correction worth remembering: Argo CD is not simply diffing commit IDs. It continuously evaluates the actual rendered manifests at the configured path against live cluster state. The commit ID is relevant context, but the comparison that actually drives a sync decision is manifest-content-vs-live-state, not "is this a new SHA."

On automatic sync's cadence: it re-checks on an interval — roughly every 3 minutes by default (the coach's own approximate figure, not quoted as an exact, documented constant) — rather than reacting instantly to every Git push via a webhook. A manual "Sync Now" is always available in the UI to force an immediate check rather than waiting out that window.

Real bug hit live, never fully resolved this session After a manual deployment change was made outside Git (to demonstrate drift), the Application correctly flagged itself OutOfSync — but automatic sync did not fire and self-correct within the expected ~3-minute window, despite Auto-Sync being enabled. The coach acknowledged this directly on-air and guessed that some sync-policy setting likely needed adjustment, without identifying exactly which one. If you hit the same thing in your own install: don't assume your Application config is definitely wrong — this was flagged as a known rough edge in the class's own live environment, not something confirmed as a specific misconfiguration. Worth testing your own syncPolicy.automated block carefully once you write it, rather than assuming "Automatic" alone is sufficient.
Exercise 9

09GitOps as policy enforcement, not just automation

Concept — the "why" behind the whole session

Goal: be able to explain GitOps to a non-technical stakeholder, not just to another engineer — this framing is what the coach explicitly said made it click for the class.

Walked through with an organizational example: a company has stakeholders (who may themselves just be relaying requirements from an external client), developers, and DevOps engineers. A stakeholder doesn't want to run kubectl get deployment to confirm a feature shipped — they want to look at something they already trust (a ticket, a merged pull request, a commit) and assume that what's in Git is what's actually running. If a feature's PR is merged, the expectation is: that is now live. No further verification should be necessary.

GitOps is what makes that assumption safe to hold rather than just optimistic. By making Git the enforced source of truth — with a controller actively reconciling any divergence back to it — nobody needs to manually check the cluster to know what's running; the guarantee is structural, not a matter of trusting that nobody made an unrecorded manual change. This reduces configuration drift (the live cluster state silently diverging from what the repository claims) and gives the whole organization, technical and non-technical alike, one place to look for the true state of the system.

Exercise 10

10Control plane vs. data plane: what's actually in the argocd namespace

Concept + live demo

Goal: use "control plane" and "data plane" correctly and specifically when describing any third-party tool's footprint in your cluster — not just for Argo CD.

A student asked directly what's actually sitting inside the argocd namespace. The answer, demonstrated by walking the running Pods: argocd-server, argocd-repo-server, argocd-application-controller, argocd-applicationset-controller, argocd-notifications-controller, and argocd-redis — a StatefulSet, several Deployments, and their supporting Pods, all doing the actual work of watching Git, computing diffs, and issuing reconciliation actions.

The framing that ties it together: Argo CD's own components (everything in the argocd namespace) are its control plane — the tracking-and-decision layer. Your actual application workloads (the frontend/backend Deployments, wherever their namespace is) are the data plane — what the control plane acts upon, but is not itself part of. The Application custom resource that ties a Git path to a destination namespace isn't visible as a "normal" workload resource, but conceptually sits on the data-plane side of that boundary — it describes the data plane's desired state, even though the object itself lives in the argocd namespace.

Exercise 11

11Prerequisites you can't skip: network path and repo auth

Concept

Goal: two checklist items to verify before assuming an Argo CD install is broken when it's actually just unreachable.

  • Network connectivity to GitHub. Argo CD's argocd-repo-server Pod, running inside your private cluster subnets, needs outbound internet access to reach github.com (or wherever your repo is hosted) to poll for changes. This depends on the same NAT gateway concept from earlier parts — no NAT, no outbound path, no way for Argo CD to ever see your commits, regardless of how correctly the Application resource itself is configured.
  • Repository authentication, for private repos. This demo's repo was public, so no auth was needed to read it. For a private repository, Argo CD needs credentials — either a GitHub personal access token, or a registered GitHub App/integration — configured in Argo CD's own repository-connections settings before it can read anything at the configured path.
Exercise 12

12Scoping: what Argo CD will and won't touch

Concept — direct answer to a student question

Goal: be able to state, without hedging, exactly where the Terraform/Argo CD boundary sits by default — this is a favorite "do you actually understand the architecture" interview probe.

Asked directly: if Argo CD reconciles drift, does it also need AWS permissions to reconcile infrastructure-level drift? No, by default. Argo CD's job is reconciling Kubernetes manifests and application state — it does not manage AWS infrastructure (VPCs, RDS instances, IAM roles, the EKS control plane itself) unless you deliberately configure it to manage Kubernetes-level representations of those things.

The framing offered: you, the engineer, choose the boundary. Put your Kubernetes Deployment/Service/Ingress manifests under Argo CD's watch, and keep your AWS resources (RDS, IAM, VPC, the cluster itself) in Terraform, applied through your own CI pipeline as before — that's the default, and the boundary used throughout this class. Nothing stops you from being more aggressive about what Argo CD owns, but going further than "Kubernetes objects only" is a deliberate choice with real implications, not something that happens by accident.

Exercise 13

13Branching strategy: why Argo CD should never point at main

Concept — explicitly named as "not what we're doing today"

Goal: know the real pattern even though this session's demo intentionally didn't use it — this gap between "demo simplicity" and "the real pattern" was called out directly, twice.

Stated as a rule for production use, not followed in this session's demo: never point a production-facing Argo CD Application at your main branch. The reasoning: your CI pipeline is what updates image tags automatically (Exercise 18) — and that automation should not be writing directly to a protected branch that's also the branch humans merge reviewed pull requests into. Doing so risks an automated commit landing on the same branch a human just merged a change to, with no clean separation between "code review happened here" and "CI just pushed here."

The real pattern named: separate branches per environment — argo-dev, argo-prod were the example names given — each with its own Argo CD Application pointed specifically at that branch. A change destined for dev has the pipeline update image tags on argo-dev only; the Application watching argo-dev deploys it. Promoting to production is then a separate, deliberate action targeting argo-prod, not something that happens automatically just because main moved. This also generalizes to multiple clusters: a company with several real clusters (dev, staging, prod as physically separate clusters, not just namespaces) typically runs Argo CD once — often in a dedicated management cluster — with each Application targeting a different destination cluster, rather than installing a separate Argo CD instance per cluster.

What this session actually did instead, and why For the live demo, the coach deliberately stayed on main for both the Application's tracked revision and the CI job's commit target — explicitly flagged as the simplified, wrong-for-production version, kept that way only to avoid adding branch-management complexity to an already dense first session. Don't infer that main is an acceptable target from watching this demo; the coach said outright it isn't.

14Moving Argo CD itself into Terraform

Concept + live demo — coach's real code, shown on screen

Goal: recognize the shape of an argocd.tf before you write your own — same helm_release pattern you already used for the Load Balancer Controller in Part 3.

After tearing down the manual CLI install from Exercise 5, the coach rebuilt Argo CD as Terraform-managed, inside a new file (shown on screen as argocd.tf, alongside the existing aws-load-balancer-controller.tf in k8s-services). Structurally, this is the same pattern you already know from Part 3's LBC install — a namespace, then a helm_release pointed at the same public Argo Helm chart used manually in Exercise 5:

# conceptual shape, matching the on-screen structure — confirm exact syntax against your own Helm provider version
resource "kubernetes_namespace" "argocd" {
  metadata {
    name = "argocd"
  }
}

resource "helm_release" "argocd" {
  name       = "argocd"
  repository = "https://argoproj.github.io/argo-helm"
  chart      = "argo-cd"
  namespace  = kubernetes_namespace.argocd.metadata[0].name
}

One piece of cleanup named explicitly while reviewing the file against Terraform's own documentation: an earlier draft had a redundant namespace definition — the namespace being both hardcoded in one place and referenced elsewhere, cleaned up to a single source of truth for the namespace name, the same "don't duplicate the same value in two places" discipline from earlier parts' variable design.

15Exposing the Argo CD UI: Ingress, HTTPS, and reusing an existing cert

Concept + live demo — coach's real code, shown on screen

Goal: recognize this as the exact same Ingress + ACM + Route 53 pattern you already wrote for your own app in Part 4, applied to a second, different subdomain.

Port-forwarding (Exercise 6) doesn't scale to a real team — everyone needs their own tunnel, and it's not how anyone would actually access this day-to-day. The fix: a dedicated Argo CD subdomain (argo-cd.<domain>) with its own Ingress, using the tag-based ALB lookup and alias-record pattern you already built in Part 4's Exercise 10 — same mechanics, second subdomain.

Two deliberate simplifications named on-air, both worth flagging as "shortcuts taken for this demo," not as the pattern to copy blindly:

  • Authentication left as Argo CD's own built-in admin login, not wired to an identity provider. The real-world answer named (not implemented): an enterprise SSO provider like Azure AD or Okta, so Argo CD access is governed by the same identity system as everything else at a company. Okta specifically was named as relatively expensive to set up just for a training/trial environment, which is why it was skipped here rather than demonstrated.
  • Reused an already-issued ACM certificate rather than requesting a new one for this subdomain — explicitly to avoid extra DNS validation wait time mid-class, not because reusing an existing cert is always the right call.
Propagation-delay failure, resolved by reapplying — same pattern as Part 4's Clinic The first apply for this Ingress failed, with the certificate showing "pending validation" in ACM and the Route 53 record not yet resolving — a timing issue, not a code bug. Re-running apply a short while later, once ACM/Route 53 had caught up, succeeded and the app became reachable at the new subdomain. Consistent with the two-phase-apply timing lesson from Part 4: DNS/cert validation genuinely takes real wall-clock time, and a failed first apply immediately after creating a cert or record isn't necessarily a sign anything is wrong.
Exercise 16

16One load balancer, many Ingresses: the group.name pattern

Concept + live demo — coach's real code, shown on screen

Goal: know this annotation exists and what problem it solves — cost/resource efficiency at the ALB level, a real thing companies actively manage.

By default, every distinct Ingress resource causes the AWS Load Balancer Controller to provision its own separate ALB. With two Ingresses now in play (the main 3-tier app's, and Argo CD's new one from Exercise 15), that's two ALBs running — wasted cost and unnecessary resource sprawl for what's conceptually one logical entry point into the cluster. The fix, demoed live on both Ingresses:

# on BOTH the app's Ingress and Argo CD's Ingress — same value
annotations = {
  "alb.ingress.kubernetes.io/group.name" = var.alb_group_name
}

Any Ingresses sharing the same group.name value get consolidated onto a single physical ALB by the Load Balancer Controller, with each Ingress contributing its own routing rules to that one shared listener. Applying this to an existing Ingress that already has a physical ALB attached causes a real resource-transition conflict — the coach resolved it live by manually deleting the old, now-orphaned load balancer in the AWS Console so the controller could reconcile cleanly onto the new shared one, rather than trying to migrate it in place.

The real constraint this creates, and the deliberate shortcut taken around it Sharing one ALB across multiple Ingresses on different subdomains has a hard requirement: the shared ALB needs one HTTPS listener, which means one certificate covering every subdomain using it — normally solved with a wildcard ACM certificate (*.domain.com) rather than a separate exact-match cert per subdomain. Implementing that wildcard-cert restructuring correctly would have required changing the certificate resource in a way that risked breaking other students who hadn't reached this point in their own coursework yet — so the coach explicitly deferred it, keeping the existing single-subdomain certificate in place for now and promising the real wildcard-certificate implementation "when we get to the microservices section." Treat the wildcard-cert pattern as the correct target architecture, and this session's workaround as intentionally temporary, not a mistake to replicate.

The fix that made it work was adding use_local_config = true alongside server_addr, username, and password in the provider block — the argocd provider needs one of that specific set of connection-mode arguments, and server_addr alone wasn't sufficient on its own.
A deprecation warning surfaced, worth noting, not urgent Terraform flagged a deprecated-value warning on the app's own Ingress resource during this same stretch — a backend service name being read as a value in a way the provider schema has since deprecated in favor of a different syntax. Named on-screen but not fixed live in this session; worth checking your own provider's current documentation before it becomes a hard error in a future provider version rather than just a warning.
Exercise 18

18Wiring the build pipeline to Argo CD: the sed-and-push pattern

Concept + live demo — coach's real code, shown on screen

Goal: understand exactly how "GitOps" turns a built image into a live deployment with zero kubectl/terraform apply in the loop — this is the mechanism, made concrete.

A new workflow file, eks-3tier-argo-deploy.yaml, adds a second job after the existing image-build matrix job, gated with needs: build so it only runs once both frontend and backend images are successfully pushed to ECR:

update-k8s-images:
  needs: build
  runs-on: ubuntu-latest
  permissions:
    contents: write   # required — this job commits back to the repo itself
  steps:
    - name: Checkout branch
      uses: actions/checkout@v3

    - name: Point backend and frontend Deployments at the new images
      run: |
        BACKEND_IMAGE="${{ env.ECR_REGISTRY }}/augk8s26-backend:${{ github.sha }}"
        FRONTEND_IMAGE="${{ env.ECR_REGISTRY }}/augk8s26-frontend:${{ github.sha }}"

        sed -i "s|image: ${{ env.ECR_REGISTRY }}/augk8s26-backend:.*|image: ${BACKEND_IMAGE}|" \
          Kubernetes-world/3-tier-app/k8s/backend.yaml
        sed -i "s|image: ${{ env.ECR_REGISTRY }}/augk8s26-frontend:.*|image: ${FRONTEND_IMAGE}|" \
          Kubernetes-world/3-tier-app/k8s/frontend.yaml

    - name: Commit and push manifest updates
      run: |
        git config user.name  "github-actions[bot]"
        git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
        git add Kubernetes-world/3-tier-app/k8s/backend.yaml \
                Kubernetes-world/3-tier-app/k8s/frontend.yaml
        git commit -m "GitOps: bump image tags to ${{ github.sha }}"
        git push

Walk the flow end to end, since this is the whole point of the session: a developer pushes app code → the build job builds and pushes new frontend/backend images to ECR, tagged with the commit SHA → update-k8s-images runs sed to rewrite the exact image: line in backend.yaml/frontend.yaml to point at that new tag → that change is committed and pushed, as a normal Git commit, back into the branch Argo CD is watching → Argo CD's own control loop (Exercise 3, Exercise 8) notices the manifest content changed, and deploys it. No step in this pipeline runs kubectl apply or terraform apply against the cluster at all — the pipeline's only job is to make Git correct; Argo CD's job is making the cluster match Git.

On YQ vs. sed: the coach considered yq (a purpose-built YAML editor, more structurally correct for modifying YAML than a generic text-stream tool) but chose plain sed for this demo specifically to keep the pipeline simple while the migration-Job piece (referenced, not yet built into this pipeline) was still unintroduced — named as something likely to be revisited and improved once that piece is added.

Why no GitHub token was needed here — but would be, in a different layout This job pushes to the same repository the workflow is already running in, on the same branch, so the default, automatically-issued GITHUB_TOKEN (scoped by the permissions: contents: write block above) is sufficient — no personal access token or extra secret required. That would not hold if your manifests lived in a separate repository from your application code (a common real pattern, sometimes called a "config repo" or "GitOps repo") — cross-repository pushes need an explicit token with access to the target repo, since the default GITHUB_TOKEN is scoped only to the repo the workflow itself is running in.
Exercise 19

19Proof: watching self-healing kill a manual kubectl change

Live demo — the payoff of the whole session

Goal: this is the single clearest, most concrete demonstration of what "GitOps" buys you in practice — be able to describe this exact sequence if asked to explain GitOps with an example.

With the full pipeline from Exercise 18 working end to end (a real code change → build → sed-and-push → Argo CD auto-sync → new Pods live, confirmed in the browser), the coach then deliberately tried to break the guarantee: manually running kubectl set image deployment/frontend-deployment <container>=<older-image-tag> -n <namespace> to force a rollback to a previous image, entirely outside Git and outside the pipeline.

The manual change did not stick. New Pods briefly started coming up with the old, manually-specified image — and were then terminated and replaced again with the Git-defined (newer) image, without any human intervention. The Argo CD Application UI showed exactly what happened underneath: the manual kubectl change was detected as drift (the live state no longer matched the Git-declared state), and Argo CD's own control loop reconciled it straight back — undoing the manual rollback attempt as if it had never happened.

To prove the point conclusively, the coach then deleted the Argo CD Application itself and re-ran the same manual kubectl set image command. This time, the manual change held — nothing reverted it. That's the direct, live-demonstrated proof that Argo CD's control loop, specifically, was what had been undoing manual changes the whole time — not some other Kubernetes mechanism, and not coincidence.

What this means in practice, stated plainly Once Argo CD is managing a Deployment with automatic sync enabled, kubectl is no longer a reliable way to change that Deployment's running state — any manual change gets treated exactly like configuration drift and reverted on the next reconciliation pass. The only way to make a change stick is to make it the way the pipeline does: update the manifest in Git. This is the mechanism, not a side effect — it's precisely the "nobody can bypass the pipeline and have it stay bypassed" guarantee from Exercise 9's GitOps-as-policy-enforcement framing, made concrete and watchable.

Reference

Glossary

CRD (Custom Resource Definition)
A schema that teaches the Kubernetes API server to accept a brand-new resource type. Inert on its own — defines the shape, does nothing by itself.
Operator
Running software (Pods) that watches instances of a custom resource and does the actual work implied by it — the piece that turns a CRD's schema into real behavior.
Control loop
A continuously-running comparison between desired state and current state, with automatic action to close any gap. Kubernetes has built-in ones for native resources (Deployments, etc.); Argo CD adds one for "does the cluster match Git."
Control plane vs. data plane
Control plane = the tooling that tracks and decides (e.g. everything in the argocd namespace). Data plane = the actual workloads being acted upon (your app's Deployments/Pods).
GitOps
An operational pattern making a Git repository the enforced source of truth for desired cluster state, with an in-cluster controller continuously reconciling live state to match it.
Configuration drift
The live, running state of a system silently diverging from what its declared source of truth (Git) says it should be — typically from manual, out-of-band changes.
Argo CD Application
The custom resource (via Argo CD's own CRD) that tells Argo CD which Git repo/path/revision is the source of truth for which destination cluster/namespace.
Sync policy — Manual vs. Automatic
Manual requires a human to trigger reconciliation each time; Automatic lets Argo CD apply changes on its own once drift is detected, on a recurring check interval (roughly every 3 minutes by default in this class's install).
Self-healing (in this context)
Argo CD reverting an out-of-band manual change (e.g. a direct kubectl edit) back to whatever Git declares, on its next reconciliation pass — demonstrated live in Exercise 19.
alb.ingress.kubernetes.io/group.name
An Ingress annotation that consolidates multiple Ingress resources sharing the same value onto a single physical ALB, instead of one ALB per Ingress.
Wildcard ACM certificate
A single TLS certificate (e.g. *.domain.com) covering every subdomain of a base domain — the correct fix for the one-cert-per-shared-ALB requirement created by group.name, deferred in this session to the microservices section.
argocd Terraform provider
A dedicated Terraform provider (separate from AWS/Kubernetes/Helm) for managing Argo CD's own resources — e.g. argocd_application — as code, requiring a connection-mode argument such as use_local_config alongside server_addr.
GITHUB_TOKEN
The default, automatically-issued token available to a GitHub Actions job, scoped only to the repository the workflow is running in — sufficient for a same-repo commit/push (as in Exercise 18), not sufficient across repositories.
Config repo / GitOps repo
A pattern (named but not used in this class's demo) of keeping Kubernetes manifests in a separate repository from application source code — requires an explicit cross-repo token for CI to push to it, unlike the same-repo pattern this class actually built.
