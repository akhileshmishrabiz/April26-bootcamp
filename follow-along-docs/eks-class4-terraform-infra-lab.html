Exercise 1

01Size the VPC — CIDR math you must own for interviews

Concept

Goal: be able to derive "a /16 gives ~65,536 IPs" on a whiteboard, not recite it.

An IPv4 address is 32 bits, written as four 8-bit octets (10.0.0.0). A CIDR block like /16 tells you how many of those 32 bits are fixed as the network portion — the rest are free for hosts (in AWS terms: ENIs, which means pods and nodes under the VPC CNI).

# the math the instructor did live
total_bits        = 32
network_bits      = 16          # from the /16
host_bits         = 32 - 16 = 16
usable_addresses  = 2^16 - 2 = 65,534   # minus network + broadcast

Why this matters beyond trivia: with the AWS VPC CNI, every pod gets a real IP from your VPC's range (unlike overlay-network CNIs where pod IPs are virtual). That means your VPC's CIDR size is a hard ceiling on how many pods + nodes your cluster can ever run — pick too small a range early and you re-architect networking later to fix it. 10.0.0.0/16 is the conventional starting point precisely because it's large enough to not think about again for a long time.

Interview framing If asked "how would you size a VPC for a Kubernetes cluster," the strong answer isn't "use a /16" — it's: "figure out max expected pods × nodes across all subnets, add headroom, work backward to the smallest CIDR that covers it, understanding the VPC CNI ties pod IP consumption directly to VPC address space, unlike overlay CNIs like Calico/Flannel which don't." That contrast (VPC-native vs. overlay CNI) is a very common follow-up question.

Exercise 2

02Public vs. private subnets across 2 AZs

Concept

Goal: know exactly what goes public vs. private, and why "2 AZs" is the HA baseline, not a nice-to-have.

  • Public subnets — only the load balancer lives here (has a route to an Internet Gateway). Nothing else should.
  • Private subnets — the EKS control plane's ENIs, the worker nodes, and the database all live here. No route to the internet directly; outbound-only via NAT.
  • Two AZs, not one — if AWS loses a zone, resources in the other zone keep serving traffic. This is the disaster-recovery baseline every production VPC design starts from.

The trade-off the instructor called out explicitly: spreading a front-end and back-end across two AZs adds real cross-AZ data-transfer cost per request — small per call, real money at scale (millions of requests). You accept that cost for availability. This is the kind of trade-off senior interviews want you to be able to articulate, not just implement.

Exercise 3

03NAT Gateway vs. VPC endpoints — the cost/resilience trade-off

Concept

Goal: explain, unprompted, why private nodes need some path to the public ECR endpoint, and what the class chose and why.

Nodes sitting in private subnets need to pull container images from ECR's public API endpoint. Two ways to give them that path:

OptionHow it worksTrade-off
NAT GatewayPrivate subnet routes outbound traffic through a NAT in a public subnet, which has an internet route.Simple, works for everything (not just AWS APIs). Costs per-hour + per-GB processed. A single NAT (what the class chose) is cheaper but becomes a single point of failure if its AZ goes down — acceptable here only because the app itself would keep serving existing traffic even if new image pulls temporarily failed.
VPC EndpointA private, in-VPC route directly to specific AWS services — traffic never leaves AWS's network.Free for S3 and DynamoDB (Gateway endpoints); billed per-hour + per-GB for others like ECR (Interface endpoints). No single point of failure the same way, but you need one endpoint per service you talk to, and it doesn't help with non-AWS internet traffic.
The decision made in class Single NAT Gateway, not one-per-AZ, and not VPC endpoints. Reasoning given: it's the cheapest option that still works, and the resilience gap (NAT's AZ going down) is judged acceptable because it only blocks new image pulls, not already-running pods. This is a cost-vs-resilience call you should be ready to defend or challenge in an interview — "one-NAT-per-AZ" is the safer, pricier answer for production-grade HA.

Exercise 5

05EKS subnet tags — why the load-balancer controller needs them

Concept

Goal: explain what these tags do, not just paste them.

Kubernetes' AWS Load Balancer Controller doesn't know your account's subnet layout out of the box. When you create a Service type=LoadBalancer or an Ingress, the controller has to discover: "which subnets in this VPC am I allowed to place a load balancer's ENIs into, and are they public or private?" It answers that by scanning for specific tags:

public_subnet_tags = {
  "kubernetes.io/cluster/<cluster-name>" = "shared"
  "kubernetes.io/role/elb"               = "1"     # public-facing ELB eligible
}

private_subnet_tags = {
  "kubernetes.io/cluster/<cluster-name>" = "shared"
  "kubernetes.io/role/internal-elb"      = "1"     # internal ELB eligible
}

Without the kubernetes.io/cluster/<name> tag, the controller can't even confirm a subnet belongs to this cluster (imagine multiple clusters sharing one VPC). Without the role/elb or role/internal-elb tag, it doesn't know whether a load balancer placed there would be internet-facing or internal.

Bug to fix in your own repo In the code from class, private_subnet_tags has the kubernetes.io/role/internal-elb line commented out. That means the LB controller currently has no way to place an internal load balancer in your private subnets — only public ones would work. This was flagged as a "next step" item in the class notes ("Add Subnet Tags"). Uncomment it as part of Exercise 4's your-turn.
Exercise 6

06Repo layout & Terraform state — backend, locking, keys

Concept

Goal: know why infra is split into separate repos/paths, and how state isolation prevents accidental deletion.

  • Separate core EKS infra from app-level Kubernetes resources (Argo CD, LB controller, the app's own k8s.tf/RDS). Different lifecycles, different blast radii — you don't want an app-level terraform apply anywhere near the ability to touch the cluster itself.
  • S3 backend for state storage — durable, versioned, shared across a team.
  • Unique state key per environment/repo — this is not optional. The class hit a real incident live: the 3-tier app's infra was accidentally pointed at the same S3 key as the EKS core infra state, which risked one terraform apply silently destroying the other's resources. The fix is simply giving every distinct piece of infra its own key.
  • State locking — historically a DynamoDB table; newer S3 backends support native locking via a lockfile, avoiding the extra DynamoDB resource entirely.
terraform {
  backend "s3" {
    bucket       = "state-bucket-<account-id>"
    key          = "<team-or-project>/eks-core-infra/dev/terraform.tfstate"  # unique!
    region       = "ap-south-1"
    use_lockfile = true
  }
}
Why this is a real interview topic "How do you prevent two Terraform states from colliding" is a standard senior question. The honest answer from this class's own incident: naming convention discipline (<project>/<component>/<env>/terraform.tfstate) plus state locking to prevent concurrent applies — there's no magic flag that stops you from typing the same key twice, so the convention itself is the safeguard.
Exercise 7

07Pin your versions — Terraform, provider, module

Concept

Goal: understand three separate pinning decisions and why each matters.

  1. Terraform CLI version — pin exactly (required_version = "= 1.15.1"), managed locally via tfenv. Reasoning: dynamic/latest versions in CI/CD are a reproducibility risk — a version bump can silently change behavior between two runs of the same code.
  2. Provider version — pin a range (~> 6.0 for the AWS provider), not exact, so you get patch fixes without a surprise major bump.
  3. Public module version — pin to a stable, slightly-behind-latest version deliberately, not latest. Two stated reasons: (a) supply-chain risk — a compromised or buggy new release of a widely-used public module is a real attack surface; (b) the class hit an actual bug in terraform-aws-modules/eks/aws v20 where a VPC-CNI dependency ordering issue made nodes silently fail to join, fixed in v21. "One version behind latest, verified" is the working rule of thumb.
Myth: "pinning to latest keeps you most secure" It's the opposite instinct that's correct for infra-as-code: unpinned or always-latest dependencies are what let a compromised upstream release reach production automatically. Pinning + deliberate, reviewed upgrades is the secure pattern — the same logic as pinning npm/pip dependencies with a lockfile.

Cluster endpoint access — the three options from class Fully private: API server only reachable from inside the VPC (via VPN/bastion/Transit Gateway). Most secure, most operational overhead. Semi-private (public + CIDR-restricted): endpoint is technically public but the security group only allows specific IP ranges in (e.g. your office VPN egress IP) — the practical middle ground most teams actually run.

Exercise 9

09Node IAM & the ECR pull-permission demo

Do this

Goal: reproduce, hands-on, the exact "access denied pulling from ECR" moment the instructor assigned as a group exercise.

  1. Launch a plain EC2 instance in a default VPC, with no IAM instance role attached.
  2. Install/use the Docker or AWS CLI to attempt docker pull <your-account>.dkr.ecr.<region>.amazonaws.com/<repo>:<tag> against a private ECR repo.
  3. Confirm it fails with an authentication/permission error — no credentials means no access, by design.
  4. Now compare: your EKS worker nodes don't hit this problem, because the managed node group's EC2 instances get an IAM instance role (attached automatically by the node group, with the AWS-managed ECR read policy) — never a hardcoded access key/secret on the box.
Why this is the pattern, always Any time compute (EC2, Lambda, EKS nodes, ECS tasks) needs to talk to another AWS service, the answer is an IAM role attached to that compute, never long-lived access keys baked into config or environment variables. This is the same principle that later drives the OIDC decision for GitHub Actions (Part 2) — short-lived, role-based credentials over static secrets, everywhere.

10Apply, kubeconfig, and IAM access entries

Do this

Goal: go from terraform apply to a working kubectl get nodes, hitting the same permission wall the class hit.

terraform init
terraform apply
# ~15-20 minutes for a fresh EKS control plane + node group — this is normal, not a hang

aws eks update-kubeconfig --name <your-cluster-name> --region <your-region>
kubectl config rename-context <long-arn-context> my-cluster
kubectl config use-context my-cluster

kubectl get nodes
Error from server (Forbidden): ...cannot list resource "nodes"...

This is expected if the identity running terraform apply differs from the one running kubectl — or even the same identity, depending on how enable_cluster_creator_admin_permissions resolved. If you hit it, add an access entry:

aws eks create-access-entry --cluster-name <name> --principal-arn <your-iam-arn>
aws eks associate-access-policy --cluster-name <name> \
  --principal-arn <your-iam-arn> \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy \
  --access-scope type=cluster

kubectl get nodes
NAME                          STATUS   ROLES    AGE   VERSION
ip-10-0-1-142.ec2.internal    Ready    <none>   3m    v1.34.x
Confirms the "AWS access ≠ Kubernetes access" rule Same principle as Class 3's console-built cluster: an IAM identity having full AWS permissions says nothing about Kubernetes RBAC permissions inside the cluster. EKS access entries are the bridge between the two layers — you'll grant this explicitly, every time, for every new identity that needs cluster access.

11When nodes won't join — the 3 usual suspects

Concept

Goal: have a mental checklist for "EC2 instance exists, but not showing up in kubectl get nodes" — a very common real-world and interview scenario.

CauseWhat's happeningHow to confirm
VPC CNI plugin missing/misorderedNodes came up before the CNI add-on finished installing (this is exactly the v20 module bug from Exercise 7) — no pod networking means the node can never report Ready.Check the vpc-cni addon status in the console/CLI; confirm your module version enforces before_compute = true or equivalent ordering.

Glossary

CIDR
Classless Inter-Domain Routing — notation like /16 that defines an IP range's size by how many bits are fixed as "network."
VPC CNI
AWS's native Container Network Interface plugin — assigns pods real IPs from the VPC's own address space, unlike overlay CNIs.
NAT Gateway
Managed AWS resource in a public subnet that lets private-subnet resources make outbound-only internet connections.
VPC Endpoint
A private route from inside your VPC directly to a specific AWS service, without traversing the public internet.
Managed Node Group
AWS-managed EC2 Auto Scaling group wired into EKS — handles node provisioning, IAM role attachment, and lifecycle.
IAM Access Entry
The EKS-native mechanism (replacing the old aws-auth ConfigMap) that maps an IAM identity to Kubernetes RBAC permissions.
Terraform State Locking
A mechanism preventing two concurrent terraform apply runs from corrupting the same state file.
OIDC (in this context)
OpenID Connect — lets GitHub Actions authenticate to AWS using short-lived, auto-expiring tokens instead of static access keys. Built in Part 2.
