Exercise 1

01Why three Service types aren't enough

Concept

Goal: be able to explain why a growing app doesn't just keep using LoadBalancer-type Services as it adds more entry points.

Quick recap of the three Service types, since the class opened by re-grounding here:

  1. ClusterIP — private, internal-only. This is what backend-service and frontend-service already use from Part 2; nothing outside the cluster can reach them directly.
  2. NodePort — opens a static port on every node's own IP. Flagged explicitly as something to avoid in production: it exposes a raw port on infrastructure you don't want directly internet-facing, and it doesn't give you TLS, path routing, or centralized certificate management.
  3. LoadBalancer — provisions one real cloud load balancer (NLB by default on AWS) per Service. Works, but doesn't scale as an architecture: one load balancer per service means one bill per service, one certificate to manage per service, and manual routing logic duplicated everywhere instead of centralized.

The app currently has two Services that need external traffic (frontend for users, and potentially backend for direct API testing) but conceptually could have dozens as it grows. Paying for and manually wiring a separate `LoadBalancer` per Service doesn't scale — that's the gap Ingress exists to close.

Exercise 2

02Ingress is a rule, not a resource that runs

Concept

Goal: stop thinking of Ingress as "a thing" and start thinking of it as "a set of instructions."

This is the single most important reframing from this session, and it's easy to get backwards. An Ingress object is not a running process, a pod, or a physical resource — it's a declarative rule that says "route traffic matching this host/path to that Service, on that port," conceptually similar to an NGINX routing config file. Writing an Ingress manifest and applying it does nothing by itself unless something is watching for it and knows how to act on it.

Don't mix these up Applying a bare kubernetes_ingress_v1 resource with no controller running in the cluster will succeed at terraform apply — the API object gets created and stored — but nothing will actually happen. No load balancer appears, no traffic gets routed. The rule exists; nobody is enforcing it yet. That "enforcer" is the subject of Exercise 3.
Exercise 3

03Ingress Controller vs. Load Balancer Controller (the pair, not the same thing)

Concept

Goal: correctly answer "what's the difference between an Ingress Controller and the AWS Load Balancer Controller?" — a question that came up live and genuinely confused people.

Ingress ControllerAWS Load Balancer Controller (LBC)
Enforces the routing rule itself — path-based routing, host-based routing, TLS termination — options include NGINX Ingress Controller, Traefik, Kong, Istio.Bridges Kubernetes and AWS — makes the actual AWS API calls to provision an ALB or NLB, attach target groups, configure security groups, and register pod IPs as targets.
Can do all the routing/TLS work inside the cluster, needing only a plain NLB to let traffic in at all.Can do the routing/TLS work at the AWS layer instead, via ALB's own listener rules — reducing what needs to live inside the cluster.

Both are needed together when you choose the "let AWS do the routing" path (which this class did): the Ingress object plus its annotations is interpreted by the AWS Load Balancer Controller, which then creates and configures a real ALB on your behalf. One crucial clarification your instructor gave when someone asked if these controllers "live on the control plane": no — the EKS control plane (API server, scheduler, etcd) is fully managed and hidden by AWS; every controller, add-on, and workload — including the LBC itself — runs as an ordinary pod on your worker nodes, same as your app.

Why pods like kube-proxy/aws-node show "Pending" with zero nodes A side question that came up: why do certain system pods (CoreDNS, kube-proxy, the VPC CNI's aws-node) sit in Pending when a cluster has no worker nodes yet? Because kube-proxy and aws-node are deployed as DaemonSets — one copy is required per node, so with zero nodes there's nowhere to schedule them. This is the same reasoning as Part 1's node-group discussion, just showing up from a different angle.
Exercise 4

04ALB vs. NLB: where does routing/TLS actually happen?

Concept

Goal: pick the right load balancer type for a reason you can defend in an interview, not by default.

  • Application Load Balancer (ALB) — operates at Layer 7 (HTTP/HTTPS). Required when you need content-based or path-based routing (e.g. route by URL path, device type, geography, or subscription tier), and it's the natural place to terminate TLS/HTTPS at the application level.
  • Network Load Balancer (NLB) — operates at Layer 4 (TCP/UDP). No awareness of HTTP paths or hosts; just forwards connections. The right choice when an in-cluster Ingress Controller (NGINX, etc.) is already doing all the L7 routing and TLS work — the NLB's only job is getting traffic to the cluster at all.

This class chose the ALB path: let AWS's own load balancer handle routing and (eventually) TLS termination, via the AWS Load Balancer Controller acting on annotations in the Terraform-defined Ingress resource, rather than running a separate in-cluster Ingress Controller like NGINX.

Exercise 5

05Trusting the Load Balancer Controller: OIDC, again

Concept

Goal: recognize this as the exact same trust pattern from Part 2's GitHub Actions OIDC setup, just with a different federated identity — and know where the OIDC provider itself actually comes from.

The LBC needs to call AWS APIs (create ALBs, tag security groups, register targets) — but it's running as an ordinary pod inside the cluster, so it needs a way to prove its identity to AWS the same way GitHub Actions did in Part 2. The mechanism is the same shape: a trust relationship between a Kubernetes Service Account and an IAM Role, established via the EKS cluster's own OIDC endpoint — this is IRSA, IAM Roles for Service Accounts.

One detail worth being precise about, confirmed from the coach's actual code: if your eks-core-infra/ uses the official terraform-aws-modules/eks/aws module (yours does, per Part 1), the IAM OIDC provider already exists — that module registers it automatically as part of creating the cluster. You do not create a second one here; you reference the existing one via a data source:

# k8s-services/aws-load-balancer-controller.tf
data "aws_iam_openid_connect_provider" "eks" {
  url = data.aws_eks_cluster.cluster.identity[0].oidc[0].issuer
}

resource "aws_iam_role" "aws_load_balancer_controller" {
  name = "aws-load-balancer-controller-${var.cluster_name}"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = { Federated = data.aws_iam_openid_connect_provider.eks.arn }
      Action    = "sts:AssumeRoleWithWebIdentity"
      Condition = {
        StringEquals = {
          "${replace(data.aws_iam_openid_connect_provider.eks.url, "https://", "")}:sub" = "system:serviceaccount:kube-system:${var.awsloadbalancercontroller_sa}"
          "${replace(data.aws_iam_openid_connect_provider.eks.url, "https://", "")}:aud" = "sts.amazonaws.com"
        }
      }
    }]
  })
}

That replace(..., "https://", "") pattern is worth understanding, not just copying: the OIDC issuer URL comes back as a full https://oidc.eks.<region>.amazonaws.com/id/<id> string, but IAM's trust-policy condition keys need the bare hostname+path, without the scheme, as the condition key name itself. Stripping the scheme is a required transformation, not a style choice.

The IAM policy attached to that role is AWS's own official, published document for this controller (search "AWS Load Balancer Controller IAM policy" on AWS's GitHub and pin a version rather than hand-writing ~20 statements yourself) — scoping the LBC to exactly what it needs: describe/tag subnets and security groups, create/modify load balancers and target groups, register/deregister targets. Nothing broader.

Don't mix these up (same warning as Part 2, worth repeating) An IAM role and a Kubernetes service account are still two different, unrelated-looking things that happen to get linked by IRSA. GitHub's OIDC role (Part 2) and the LBC's OIDC role (this exercise) are two separate roles trusting the same cluster's OIDC provider for two completely different purposes — don't conflate them into "the OIDC role." And now a third nuance: the OIDC provider itself is one shared resource per cluster (created once, by the EKS module) — it's the roles that multiply per consumer, not the provider.

Check your own eks-core-infra/ — since you used the official EKS module in Part 1, confirm the OIDC provider exists (aws_iam_openid_connect_provider shows up in that module's created resources, or check the AWS Console under IAM → Identity providers). Then, in a dedicated module (see the callout in Exercise 6 for why this shouldn't live in app-infra/), write the IAM role + policy above, referencing the existing provider via the data source. Exercise 6

06Installing the controller with Helm, from Terraform

Concept

Goal: understand Helm's role here (package manager, not magic), why helm_release in Terraform beats a manual helm install, and where this code should actually live.

Helm was introduced with the analogy your instructor used directly: it's apt/yum for Kubernetes — a way to install pre-packaged, versioned, third-party software (like the AWS Load Balancer Controller) without hand-writing every Deployment, ServiceAccount, RBAC role, and CRD it needs. Terraform has a native helm provider so the install itself stays inside the same apply/plan/state workflow as everything else.

# k8s-services/providers.tf
data "aws_eks_cluster" "cluster" {
  name = var.cluster_name
}
data "aws_eks_cluster_auth" "cluster" {
  name = var.cluster_name
}
data "aws_vpc" "main" {
  filter {
    name   = "tag:Name"
    values = [var.vpc_name]
  }
}

provider "helm" {
  kubernetes = {
    host                   = data.aws_eks_cluster.cluster.endpoint
    cluster_ca_certificate = base64decode(data.aws_eks_cluster.cluster.certificate_authority[0].data)
    token                  = data.aws_eks_cluster_auth.cluster.token
  }
}

# k8s-services/aws-load-balancer-controller.tf
resource "helm_release" "aws_load_balancer_controller" {
  name       = "aws-load-balancer-controller"
  repository = "https://aws.github.io/eks-charts"
  chart      = "aws-load-balancer-controller"
  namespace  = "kube-system"
  version    = "1.11.0"   # pin a real version — don't float on "latest"

  set = [
    { name = "clusterName",                                                   value = var.cluster_name },
    { name = "region",                                                        value = var.region },
    { name = "vpcId",                                                         value = data.aws_vpc.main.id },
    { name = "serviceAccount.create",                                          value = "true" },
    { name = "serviceAccount.name",                                            value = "aws-load-balancer-controller" },
    { name = "serviceAccount.annotations.eks\\.amazonaws\\.com/role-arn",     value = aws_iam_role.aws_load_balancer_controller.arn },
  ]

  depends_on = [aws_iam_role_policy_attachment.aws_load_balancer_controller]
}

Two config values matter and are easy to skip: the chart needs the VPC ID and cluster name to know where to look for subnets and how to tag the resources it creates.

Real structural decision worth adopting: this is its own Terraform module In the coach's repo, this entire Helm/IAM/OIDC setup lives in a standalone module — k8s-services/ — sitting alongside eks-core-infra/, separate from the per-application app-infra/ module you've been writing in Parts 2–3. The reasoning fits the "different lifecycle → different state file" principle from Part 1: the Load Balancer Controller is cluster-level infrastructure (installed once, shared by every app deployed to the cluster), not something tied to any one application's release cycle. If you tore down app-infra/ tonight to rebuild the quiz app fresh, you would not want to also destroy and recreate the Load Balancer Controller — a separate state file makes that impossible to accidentally couple.
Syntax note if you're on a recent Helm provider version The coach's code uses set = [ { name = ..., value = ... }, ... ] — a single attribute holding a list of objects. Older Helm provider versions (v2.x) use a different, repeated-block form instead: set { name = "..." value = "..." }, once per value. Both exist in the wild depending on which provider version a given piece of code (or blog post) was written against — check required_providers in your versions.tf before copying either shape verbatim, since mixing the two forms won't validate.

Create a k8s-services/ module (new directory, new state key in your S3 backend — same "different lifecycle" pattern as aws-github-oidc/). Exercise 7

07Subnet tagging: how auto-discovery actually finds anything

Concept

Goal: know exactly what tags the LBC looks for before you hit the bug the class hit live (covered in full in the Debugging Clinic).

The LBC doesn't just "know" which subnets to put an ALB into — it discovers them by tag, the same discovery-by-tag pattern rds.tf already used in Part 2 to find the VPC and private subnets. Confirmed from the coach's actual VPC module call — this is set once, at the networking layer, for both public and private subnets:

# eks-core-infra/network.tf
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "6.6.1"
  # ...name, cidr, azs, private_subnets, public_subnets...

  public_subnet_tags = {
    "kubernetes.io/cluster/${var.eks_cluster_name}" = "shared"
    "kubernetes.io/role/elb"                        = "1"
  }

  private_subnet_tags = {
    "kubernetes.io/cluster/${var.eks_cluster_name}" = "shared"
    "kubernetes.io/role/internal-elb"               = "1"
  }
}

Note the private subnets get a different role tag (internal-elb, not elb) — relevant if you ever provision an internal-facing ALB (e.g. for an admin panel not meant to be public) rather than the internet-facing one this class builds. Two things have to be true simultaneously for public discovery to work: at least two subnets in different Availability Zones need both tags, and the ${var.eks_cluster_name} interpolation has to resolve to the exact same string the EKS module itself used as the cluster's real name — not a second, independently-typed copy of the name that can drift. That drift is exactly what broke during the live session (see the Clinic) — the fix was making both places reference the same variable instead of two separately-typed literals.

Your turn

In your own networking module, confirm both tag sets exist and that ${var.eks_cluster_name} (or whatever you named that variable) is the exact same variable your module "eks" block uses for its own name argument — not a separately hardcoded string that happens to currently match.

Exercise 8

08Writing the Ingress resource in Terraform

Concept

Goal: write an Ingress that the LBC can actually act on, using annotations as its instruction set — and use the current API convention, not a deprecated one.

Annotations are how you hand the LBC AWS-specific configuration that the plain Kubernetes Ingress spec has no vocabulary for — internal vs. internet-facing, target type, health check path all show up here, not in the spec's native fields. At this stage of the class — before TLS/ACM/Route 53, which the coach's repo has since added a few classes further ahead — the coach's actual annotation set was intentionally minimal:

# the coach's plain-manifest draft at this stage of the class (applied via kubectl, not yet Terraform):
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: devopsdozo-ingress
  namespace: devopsdozo
  annotations:
    alb.ingress.kubernetes.io/scheme: "internet-facing"
    alb.ingress.kubernetes.io/target-type: "ip"
    alb.ingress.kubernetes.io/healthcheck-path: "/"
spec:
  ingressClassName: alb
  rules:
  - http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: backend-service
            port:
              number: 8080
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 80

Two things worth noting precisely from this real snippet: it uses spec.ingressClassName: alb — the current, correct way to bind an Ingress to a controller — rather than the older kubernetes.io/ingress.class annotation, which is deprecated in current Kubernetes versions even though you'll still see it in a lot of older tutorials. And there's no healthcheck-port annotation at all here — it defaults to traffic-port (whatever port the Service itself forwards to), which is exactly what caused the health-check bug covered in the Clinic below.

Per your instructor's own stated decision mid-session (to move Ingress definition into Terraform specifically to later automate ACM certificate mapping and Route 53 DNS), here's that same shape ported into your app-infra/-style Terraform, matching your own resource-naming conventions from Parts 1–2:

resource "kubernetes_ingress_v1" "app_ingress" {
  metadata {
    name      = "devopsquiz-ingress"
    namespace = kubernetes_namespace_v1.k8_namespace.metadata[0].name
    annotations = {
      "alb.ingress.kubernetes.io/scheme"          = "internet-facing"
      "alb.ingress.kubernetes.io/target-type"     = "ip"
      "alb.ingress.kubernetes.io/healthcheck-path" = "/health"
    }
  }

  spec {
    ingress_class_name = "alb"

    rule {
      http {
        path {
          path      = "/api"
          path_type = "Prefix"
          backend {
            service {
              name = kubernetes_service_v1.backend_svc.metadata[0].name
              port { number = kubernetes_service_v1.backend_svc.spec[0].port[0].port }
            }
          }
        }
        path {
          path      = "/"
          path_type = "Prefix"
          backend {
            service {
              name = kubernetes_service_v1.frontend_svc.metadata[0].name
              port { number = kubernetes_service_v1.frontend_svc.spec[0].port[0].port }
            }
          }
        }
      }
    }
  }

  depends_on = [helm_release.aws_load_balancer_controller]
}

target-type = "ip" matters specifically for EKS: it tells the ALB to register pod IPs directly as targets (works with the VPC CNI's pod-level networking), instead of the older instance mode which registers whole worker nodes and relies on NodePort under the hood. The explicit depends_on on the Helm release isn't cosmetic — without it, Terraform has no inherent way to know the Ingress resource requires the controller to already be running and watching, since nothing in the Ingress spec's own attributes references the Helm release.

Set your health check path deliberately, don't leave it at "/" The coach's snapshot above uses "/" as the health check path — functionally fine only if that path actually returns a 200 on both services being fronted, which for a typical React frontend is usually true (it serves the app shell) but is a coincidence, not a design choice. Your own backend and frontend both already expose a real /health endpoint (Part 2, Exercise 9) — point the annotation at that explicitly rather than relying on / happening to work.

Exercise 9

09Why backend pods must never auto-create the schema

Concept

Goal: be able to explain, unprompted, why "just let the app create its own tables on startup" is a real production anti-pattern — this is a strong interview signal question.

With a single pod, having the backend app auto-create its own database schema/tables on first boot seems harmless — one process, one startup, one schema creation, done. The problem appears the moment you scale beyond one replica (which Part 2's Deployments already do — replicas = 2): every pod that starts runs the same startup logic simultaneously. Multiple pods racing to create the same tables at the same time against the same database is a recipe for request bombardment at minimum, and genuine data corruption in the worse case — the same endpoint/row being written from multiple sources at once.

The production pattern, stated plainly in class: migrations are a separate lifecycle concern from the running application, handled by its own step, not bundled into the application container's normal startup path.

This connects directly to a decision already made in Part 2 Your own Part 2 handoff notes flagged this exact distinction before this class even covered it explicitly: "migrations are a separate lifecycle concern (Job/initContainer pattern), not part of Deployment container spec." This class is the formal teaching behind that instinct — good sign that the earlier reasoning was already correct.
Exercise 10

10The migration Job: same image, different command

Concept

Goal: understand exactly how a Kubernetes Job reuses an existing image while making it do something completely different than what its Dockerfile normally starts — and where this fits relative to Terraform.

A Job is Kubernetes' object for "run this to completion once, then stop" — as opposed to a Deployment, which is built around "keep this running forever, restart if it dies." Rather than building a whole separate image just for migrations, the class reused the backend's own image (which already bundles a migrate.sh script) and overrode its default startup behavior using the same underlying idea as Docker's own ENTRYPOINT/CMD override mechanism — Kubernetes' command field on the container spec does exactly this at the pod level. This is the coach's actual Job manifest, applied directly via kubectl:

apiVersion: batch/v1
kind: Job
metadata:
  name: backend-job
  namespace: devopsdozo
  labels:
    app: backend
spec:
  backoffLimit: 3
  template:
    metadata:
      labels:
        app: backend
    spec:
      restartPolicy: Never
      containers:
        - name: backend
          image: <account-id>.dkr.ecr.<region>.amazonaws.com/augk8s26-backend:<git-sha>
          command: ["/bin/sh", "-c", "./migrate.sh"]
          resources:
            requests:
              memory: "256Mi"
              cpu: "250m"
            limits:
              memory: "512Mi"
              cpu: "500m"
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef: { name: backend-secret, key: DB_LINK }
            - name: SECRET_KEY
              valueFrom:
                secretKeyRef: { name: backend-secret, key: SECRET_KEY }
            - name: DB_USERNAME
              valueFrom:
                secretKeyRef: { name: backend-secret, key: DB_USERNAME }
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef: { name: backend-secret, key: DB_PASSWORD }
            # ...plus DB_HOST, DB_PORT, DB_NAME, ALLOWED_ORIGINS, APP_VERSION from the ConfigMap, same pattern with configMapKeyRef

Two design points worth internalizing, both raised implicitly through what actually broke live (see the Clinic): the Job needs the exact same environment as the backend Deployment, because migrate.sh needs to reach the same database with the same credentials. And restartPolicy: Never (not the pod-spec default of Always) is required for Jobs — a migration that fails should surface as a failed Job for a human to investigate, not silently restart forever.

Plain YAML here, not Terraform — and it's consistent with a boundary you already learned Notice this is a raw manifest, kubectl apply'd directly — not a kubernetes_job_v1 Terraform resource, even though the rest of this app's Kubernetes objects (Services, ConfigMaps, Secrets, the Ingress in Exercise 8) are Terraform-managed. This lines up exactly with the Terraform-vs-YAML boundary from Part 2's Q&A: dynamic infra state → Terraform (things that reference other Terraform-managed resources and don't change per-deploy), fast-moving deploy state → plain YAML (things whose defining characteristic — here, the image tag — changes on every real deploy). A migration Job's image tag needs to track whatever was just built, exactly like a Deployment's image tag does — so it falls on the YAML side of that line for the same reason.

Style difference worth noticing, not a bug: env vs. envFrom The coach lists every variable individually via env: - name: X valueFrom: secretKeyRef: .... Your own app-infra code (Part 2) consistently uses the terser envFrom (whole ConfigMap/Secret injected at once) instead. Both are functionally equivalent here since the Job needs every key from both objects anyway — envFrom is simply less to type when you want the whole object. The individual form only earns its keep when a container needs some keys from a ConfigMap/Secret but not all of them, or needs to rename a key on the way in (e.g. injecting a Secret's DB_LINK as DATABASE_URL, which is in fact exactly what the coach's snippet above does — worth spotting that rename, since it's doing real work, not just re-listing the same name).

Notice the image tag is a real commit SHA here — connect this back to your own Part 2 review The coach's Job hardcodes an actual git-SHA-tagged image (...backend:<git-sha>), not :latest. This is a live confirmation of exactly the ECR immutability + commit-SHA tagging conversation you and I had reviewing Part 2's app-infra code — by this point in the coach's own timeline, that piece has already been solved on their end. Worth keeping as a concrete forward-looking target for when your own pipeline work catches up to it.

What this Job does not solve yet Running this Job as a one-off kubectl apply works for this class, but running it safely as part of a real CI/CD pipeline — so it runs automatically on every real deploy, exactly once, before the new backend version starts serving traffic — was explicitly called out as a "critical requirement for future CI/CD pipeline deployments," not solved in this session. Worth flagging honestly if it comes up in an interview: this is a real open design question (Job triggered by pipeline step vs. Helm hook vs. init container with a locking mechanism), not a finished pattern yet.
Your turn

Write this Job as a plain YAML manifest against your own backend image/Secret/ConfigMap names — envFrom is fine here, no need to switch to individual env entries unless you want the practice. Live Debugging Clinic

Every bug the class actually hit

This session was unusually bug-heavy, and every one of them is a realistic production scenario, not a bootcamp contrivance. Walking through how each was diagnosed matters more than the one-line fix.

Bug 1 — Service targetPort pointed at the wrong container port Symptom: health checks failing, app unreachable, even though the Service and Deployment both looked individually correct. Root cause: the frontend container's actual listening port (from its own Dockerfile) didn't match the target_port the Service was forwarding to — a mismatch between what the container exposes and what the Service assumes it exposes. Diagnosed by going straight to the Dockerfile to check the real port rather than trusting the Kubernetes manifest's assumption. Lesson: the Service's port/target_port pair is only ever correct if it's been verified against the container's actual listening port, not copied from another service's config.
Bug 2 — ALLOWED_ORIGINS set to a static endpoint instead of a real, live reference Symptom: frontend couldn't reach backend even after the port fix. Root cause: the backend's CORS-adjacent origin config was pointing at a hardcoded, static value rather than something that actually tracked the frontend Service. The coach's real fix, confirmed from the current code — ALLOWED_ORIGINS = "http://${kubernetes_service.frontend_service.spec[0].cluster_ip}:${kubernetes_service.frontend_service.spec[0].port[0].port}" — derives the value directly from the frontend Service's own Terraform attributes (its ClusterIP and port) instead of typing either one in by hand. Worth noting for your own version: a Service's ClusterIP is stable for the Service's lifetime, so referencing it directly works, but referencing the Service's DNS name (<svc>.<ns>.svc.cluster.local, the pattern you already used correctly for BACKEND_URL in Part 2) is generally the more idiomatic choice — it reads clearly to a future maintainer and doesn't silently break if the Service were ever recreated with a new ClusterIP. Either fixes this bug; the DNS form is the better habit. Also worth remembering: ConfigMap changes don't retroactively update already-running pods — a restart (or a mechanism to trigger one) is required to pick up the corrected value.
Bug 3 — Backend couldn't find the database because the connection env var name was wrong Symptom: backend logs showed it falling back to a default/incorrect database name instead of connecting to the real RDS instance. Diagnosed via a genuinely instructive process: port-forward the backend Service locally, curl its real API endpoint, read the actual error, then nslookup the database hostname to confirm whether DNS resolution itself was the problem or whether the app simply never received the right environment variable name. The real root cause: the application code was looking for a specific env var name (its own DATABASE_URL-style variable) that didn't match what was actually being injected via the Secret. Lesson, and it's the single most reusable one from this whole session: when a connection fails, don't guess — reproduce the failure with a direct tool (port-forward + curl, then nslookup/dig) to isolate whether it's DNS, networking, credentials, or a mismatched variable name, in that order.
Bug 4 — ALB subnet discovery failing due to a cluster-name mismatch in subnet tags Symptom: the Ingress resource applied cleanly, but the LBC couldn't find any subnets to provision the ALB into — the ADDRESS field on kubectl get ingress stayed empty. Diagnosed by going directly into the AWS Console to inspect the actual tags on the public subnets, confirming the required tags existed at all, then discovering the specific tag value (the cluster name) didn't exactly match what the LBC was querying for. Root cause traced back to the Terraform code generating that tag value — a naming/reference mismatch, not a missing tag. Fixed by correcting the reference so both places (the cluster's real name and the subnet tag) derive from the same source of truth instead of two independently-typed strings.
Meta-lesson across all four Every single bug this session was a mismatch between two things that were each individually valid but disagreed with each other — a port here vs. a port there, a hostname here vs. a hostname there, a name here vs. a tag there. None required exotic debugging tools; all four were solved by directly inspecting the actual running state (Dockerfile, pod logs, AWS Console tags, DNS resolution) rather than re-reading the Terraform/YAML and hoping. That instinct — verify the live state, don't just re-read the code — is exactly what a senior debugging question in an interview is probing for.
Looking ahead

What's next (HTTPS / ACM / Route 53 preview)

The instructor got the ALB working end-to-end over plain HTTP by the end of this session, and named the immediate next steps explicitly. This isn't speculative — the coach's reference repo (several classes ahead of this transcript) already has this fully built, so here's exactly what it looks like once done, purely as a preview of where you're headed. None of this is a "your turn" yet — it depends on a real registered domain and comes after HTTPS is explicitly taught:

  • A real domain, looked up via data "aws_route53_zone" — the class's own domain already existed as a Route 53 hosted zone.
  • An ACM certificate (aws_acm_certificate, validation_method = "DNS") requested for the app's subdomain, validated automatically by writing the DNS validation record Route 53 needs (aws_route53_record.cert_validation) and waiting on it via aws_acm_certificate_validation — all three resources chained together so terraform apply handles the whole issuance/validation dance without anyone manually clicking "validate" in the ACM console.
  • Wiring the certificate into the Ingress via alb.ingress.kubernetes.io/certificate-arn, plus alb.ingress.kubernetes.io/listen-ports = '[{"HTTP": 80}, {"HTTPS": 443}]' and alb.ingress.kubernetes.io/ssl-redirect = "443" — at that point the ALB terminates TLS itself and automatically redirects any plain HTTP hit to HTTPS.
  • Pointing the domain at the ALB — a data source (data "aws_lb", found by the tag the Ingress annotations assign it) feeds the ALB's own DNS name into an aws_route53_record alias record, completing the chain from human-readable domain all the way to the ALB.
Known open item carried into whichever class covers this The health check on the ALB target group was still misconfigured at the very end of this session (defaulting to traffic-port with a "/" path rather than an explicit, verified path/port) — flagged live but not yet fixed in code. If your own Ingress resource's health-check annotations don't match your actual container's listening port and a real health endpoint, expect the same symptom (targets registered but marked unhealthy) until this is corrected.
Reference

Glossary

Ingress
A Kubernetes API object declaring routing rules (host/path → Service) — a rule, not a running process or physical resource.
Ingress Controller
Software that watches Ingress objects and enforces their rules — e.g. NGINX Ingress Controller, Traefik, Kong, Istio.
AWS Load Balancer Controller (LBC)
A pod running in-cluster that translates Ingress/annotations into real AWS API calls — provisioning ALBs/NLBs, target groups, and security groups.
ALB (Application Load Balancer)
Layer 7 AWS load balancer — content/path-based routing, HTTPS/TLS termination at the application layer.
NLB (Network Load Balancer)
Layer 4 AWS load balancer — raw TCP/UDP forwarding, no awareness of HTTP paths or hosts.
IRSA (IAM Roles for Service Accounts)
The OIDC-based mechanism linking a Kubernetes ServiceAccount to an IAM Role, letting an in-cluster pod call AWS APIs without static credentials.
Subnet auto-discovery (LBC)
The LBC's mechanism for finding which subnets to place a load balancer into, based on kubernetes.io/role/elb and kubernetes.io/cluster/<name> tags.
Helm
A package manager for Kubernetes — installs pre-packaged, versioned charts (Deployments, RBAC, CRDs bundled together) instead of hand-writing every manifest.
helm_release
Terraform's helm provider resource for installing/managing a Helm chart as part of the same plan/apply/state workflow as everything else.
Kubernetes Job
An object for "run to completion once, then stop" workloads — as opposed to a Deployment's "keep running forever" model. Used here for one-off database migrations.
command (container spec)
Kubernetes' field for overriding a container image's default startup command — the pod-spec equivalent of overriding Docker's ENTRYPOINT/CMD.
Database migration
The process of creating/updating a database's schema and seed data — deliberately run as a separate, single-shot step rather than automatically on every application pod's startup.
ACM (AWS Certificate Manager)
AWS's service for issuing and managing TLS certificates, tied to a domain name — a prerequisite for HTTPS on an ALB.
Route 53
AWS's DNS service — used to map a real domain name to the ALB's own generated DNS hostname.
