Part 1 · Foundations

01Linux Namespaces — the isolation primitive

Every container — whether it's a raw Docker container or a Kubernetes pod — is, at the kernel level, just a normal Linux process. There is no special "container" object in the Linux kernel. What makes a process feel like an isolated little machine is a kernel feature called namespaces, combined with a resource-limiting feature called cgroups.

A namespace wraps a global system resource in an abstraction that makes it appear to the processes within the namespace that they have their own isolated instance of that resource. Two processes in different namespaces can both think they are "process ID 1", both think they own eth0, both think they have their own / root filesystem — while actually sharing one physical machine and one kernel.

Key mental model Namespaces don't create new resources. They create restricted views of existing global kernel resources. A container's "own network stack" is really just the host's networking subsystem, sliced and hidden so the container can only see its own slice.

The eight namespace types

As of a modern Linux kernel (5.6+), there are eight namespace types. Kubernetes and Docker use most of these for every pod/container they create.

NamespaceKernel flagIsolatesUsed by containers to…
PIDCLONE_NEWPIDProcess IDsLet every container think its main process is PID 1, with its own independent process tree.
NETCLONE_NEWNETNetwork devices, IP addresses, routing tables, port numbers, iptables rulesGive each container its own eth0, its own IP, and its own routing table — this is the one this document spends the most time on.
MNTCLONE_NEWNSFilesystem mount pointsGive each container its own root filesystem view (this is what makes a container's / look like a fresh OS image).
UTSCLONE_NEWUTSHostname & NIS domain nameLet each container set its own hostname without affecting the host or other containers.
IPCCLONE_NEWIPCSystem V IPC, POSIX message queuesPrevent containers from being able to signal or share memory queues with unrelated processes.
USERCLONE_NEWUSERUser & group ID mappingsLet a process be "root" (UID 0) inside the container while mapping to an unprivileged UID on the host — a major security boundary.
CGROUPCLONE_NEWCGROUPCgroup root directory viewHide the host's full cgroup hierarchy so a container only sees its own slice of it.
TIMECLONE_NEWTIMEBoot & monotonic clocksAllow a container to have an offset system clock (used mainly for checkpoint/restore, rarely in everyday use).

You can inspect a running process's namespaces directly on any Linux host:

# list the namespace symlinks for PID 1234
ls -la /proc/1234/ns/
# typical output:
cgroup -> 'cgroup:[4026531835]'
ipc    -> 'ipc:[4026532210]'
mnt    -> 'mnt:[4026532208]'
net    -> 'net:[4026532213]'
pid    -> 'pid:[4026532211]'
time   -> 'time:[4026531834]'
user   -> 'user:[4026531837]'
uts    -> 'uts:[4026532209]'

# the number in brackets is the namespace's inode ID.
# two processes that show the SAME number for a given
# namespace type are literally sharing that namespace.

Docker (and the Kubernetes container runtime under it) creates most of these namespaces fresh for every container. Kubernetes, notably, shares the NET and IPC namespaces across all containers in the same pod — which is precisely why containers in one pod can reach each other over localhost. More on this in the CNI section.

02Network namespaces in detail

The network namespace (netns) is the one that matters most for everything you'll do with Kubernetes. Each network namespace gets its own, completely independent:

  • Set of network interfaces (a fresh namespace starts with only a loopback interface, lo, and it's down by default)
  • IPv4/IPv6 routing table
  • Firewall / netfilter (iptables / nftables) rule set
  • Socket / port number space — so two namespaces can each bind port 80 independently, with zero conflict
  • /proc/net and /sys/class/net view

You can play with network namespaces directly using the ip netns tool — this is exactly the primitive Docker and the CNI plugins build on top of:

# create two isolated network namespaces
sudo ip netns add ns1
sudo ip netns add ns2

# list them
ip netns list

# run a command *inside* a namespace
sudo ip netns exec ns1 ip addr show

# a brand-new namespace only has 'lo', and it's DOWN:
1: lo: <LOOPBACK> mtu 65536 qdisc noop state DOWN

A namespace with nothing but a loopback interface can't talk to anything — not even the host. To connect it to the outside world, you need a veth pair, covered next.

03veth pairs & Linux bridges

veth: the virtual patch cable

A veth (virtual Ethernet) device is always created in an interconnected pair. Think of it as a virtual Ethernet cable with a plug at each end — anything sent in one end comes out the other instantly. One end typically stays in the host's root namespace; the other end is moved into the container's/pod's namespace.

ip link add veth0 type veth peer name veth1
# veth0 and veth1 are now a linked pair, both currently in the host namespace

ip link set veth1 netns ns1
# veth1 has been "teleported" into ns1 — from inside ns1 it now just looks like a normal NIC

Point-to-point veth pairs work for connecting exactly two namespaces. But a real host runs dozens of containers. For that you need a switch — which on Linux is a bridge.

The bridge: a virtual Layer-2 switch

A Linux bridge (brctl/ip link add type bridge) is a software switch living in the kernel. Instead of wiring veth pairs directly between namespaces, one end of every container's veth pair is plugged into the bridge instead. The bridge then forwards Ethernet frames between all attached interfaces based on MAC address, exactly like a physical switch.

This is precisely how Docker's default bridge network (docker0) works, and it's the same pattern kind, kubeadm-based clusters, and many CNI plugins use inside a node.

How traffic actually flows

  • Same bridge (container ↔ container): Frames go straight through the bridge, switched by MAC address — like a physical LAN switch. No NAT, no iptables routing needed.
  • Container → outside world: The packet leaves via the container's veth, hits the bridge, gets routed by the host's IP routing table (since the destination isn't on the bridge's subnet), and exits via the host's real NIC. An iptables rule of type MASQUERADE rewrites the source IP from the container's private IP to the host's real IP — this is Source NAT (SNAT).
  • Outside → container (published ports): Handled by a DNAT (-p / port-publish) rule in iptables that rewrites the destination from host_ip:hostPort to container_ip:containerPort before the routing decision.
Why this matters for Kubernetes later Everything you'll learn about iptables/nftables rules being managed by kube-proxy, and Services having a "virtual" ClusterIP that isn't attached to any interface, is built directly on top of these same primitives — namespaces, veths, bridges, and netfilter rules. Kubernetes doesn't invent new plumbing; it automates the exact commands shown above, per pod, per node, at scale.

Docker driverWhat it does

Common misconception "Kubernetes doesn't use Docker anymore, so it doesn't use containerd." In reality, Docker Engine has always used containerd internally as its low-level runtime — Docker just adds a lot of tooling (CLI, build, volumes, networking UX) on top. Modern Kubernetes talks to containerd (or CRI-O) directly through the Container Runtime Interface (CRI), skipping the Docker Engine layer entirely — but the underlying namespace/cgroup mechanics are identical either way.
Part 2 · Networking contract

05CNI — the Container Network Interface

CNI is not a piece of software you install. It is a specification — a contract — published by the Cloud Native Computing Foundation, that defines how a container runtime should talk to network plugins in order to wire up a container's network namespace. Kubernetes doesn't implement networking itself; it delegates that job entirely to whichever CNI plugin you install.

The CNI project bundles three things:

  • A specification — the exact JSON config format and the exact executable-invocation contract plugins must follow.
  • Reference/example plugins — simple building-block plugins (bridge, host-local, loopback, portmap) maintained by the CNI project itself, usable standalone or chained together.
  • Libraries (mainly in Go) that make it easy to build new plugins that follow the spec correctly.
The core idea in one sentence A CNI plugin is just an executable binary that the container runtime runs and hands a JSON blob to on stdin — the binary's job is to configure networking inside a given network namespace, and hand back a JSON result on stdout.

The CNI verbs

CommandCalled when…Plugin must…
ADDA new pod sandbox is createdAllocate an IP (via IPAM), create the interface inside the namespace, set up routes, return the assigned IP/routes as JSON.
DELA pod is being torn downRelease the IP address, remove interfaces/veth ends, clean up any iptables/route entries.
CHECKPeriodically, to verify healthConfirm the pod's networking still matches what was configured; if not, the runtime may tear down and re-create it.
VERSIONRuntime wants plugin capabilitiesReturn which CNI spec versions the plugin supports.
GCGarbage collection passClean up any stale resources left behind by crashed operations.

06How CNI is actually invoked — step by step

Here is the literal sequence of events from "scheduler assigns a pod to a node" to "pod has an IP and can send packets":

  1. Scheduling. The scheduler picks a node; the API server records this in etcd. kubelet on that node is watching the API server and notices a new pod assigned to it.
  2. kubelet asks the runtime to create a "pod sandbox". This request goes over the CRI (Container Runtime Interface) to containerd (or CRI-O). The "sandbox" is essentially an empty pause/infra container whose only job is to own the shared Linux namespaces for the pod.
  3. The runtime creates a fresh network namespace for the sandbox (kernel call: unshare(CLONE_NEWNET)), before any application container starts.
  4. The runtime reads CNI config from /etc/cni/net.d/*.conf(list) on the node, and finds the CNI plugin binary in /opt/cni/bin/.
  5. The runtime executes the CNI plugin binary directly (it is not a daemon/service — just a short-lived executable) with environment variables and a JSON config on stdin: 
    CNI_COMMAND=ADD
CNI_CONTAINERID=<sandbox id>
CNI_NETNS=/var/run/netns/<id>
CNI_IFNAME=eth0
CNI_PATH=/opt/cni/bin
/opt/cni/bin/<plugin> < /etc/cni/net.d/10-plugin.conf
  6. The plugin does the actual work: creates a veth pair, moves one end into the pod's namespace as eth0, plugs the other end into the node's bridge (or configures whatever networking model the plugin uses — overlay, BGP route, cloud ENI, etc.), and calls its IPAM sub-plugin to allocate an IP from the configured pool.
  7. Plugin returns a JSON result on stdout containing the assigned IP address, routes, and DNS info.
  8. kubelet records the pod IP and reports pod status back through the API server, which is why kubectl get pod -o wide shows an IP.
  9. Application containers are started inside the sandbox's namespaces — after networking exists, not before.
Common misconception (from class discussion) "kube-proxy is what lets pods talk to each other." It is not. The CNI plugin is what gives pods their IP addresses and pod-to-pod/node-to-node reachability. kube-proxy has a narrower job: it programs iptables/nftables/IPVS rules so that traffic sent to a Service's virtual ClusterIP gets redirected to one of the real pod IPs behind it. Some CNIs (Cilium, Calico in certain modes) can now implement kube-proxy's job themselves via eBPF, which is why newer clusters can sometimes run without kube-proxy at all.

07CNI plugin types & the ecosystem

Reference / chainable plugins (the CNI project's own building blocks)

PluginTypeRole
bridgeMain (interface)Creates a Linux bridge on the node and a veth pair per pod, exactly as diagrammed in Fig. 2.
host-localIPAMAllocates IPs from a locally-configured CIDR range, tracked in files on disk — the simplest possible IPAM.
loopbackMainBrings up the lo interface inside the namespace.
portmapMeta / chainedAdds iptables DNAT rules for hostPort-style port publishing.
macvlan/ipvlanMainGives a container a virtual interface that appears directly on the physical network segment, bypassing a bridge entirely.

These reference plugins can be chained — for example bridge → portmap — where each plugin in the chain does one focused job and passes its result to the next.

Full-featured production CNIs (what you actually install on a real cluster)

PluginNetworking modelNotable trait
FlannelOverlay (VXLAN by default)Simple, widely used, minimal feature set — good for learning, not much policy support.
CalicoDirect routing via BGP (or overlay mode)Strong NetworkPolicy enforcement; can run without an overlay for near-native performance.
CiliumeBPF-based, can bypass iptables entirelyCan replace kube-proxy's function using eBPF; deep L3–L7 observability and policy (Hubble).
AWS VPC CNINative — pods get real VPC IPsDefault on EKS; pods are directly addressable/routable on the AWS VPC, using ENIs attached to the node.
Azure CNI / GKE's CNICloud-native, VPC-routedSame idea as AWS VPC CNI — cloud provider-specific implementations tightly integrated with their networking stack.
kindnetSimple overlay (based on the ptp/bridge model + a basic controller)The default, minimal CNI shipped with kind, good enough for local dev/testing, not meant for production.
Without a CNI installed, a cluster is broken A node cannot fully join a cluster, and pods cannot get IPs, until a CNI plugin is running on every node. This is why a freshly kubeadm init'd cluster shows nodes stuck in NotReady until you apply a CNI manifest — kind hides this step from you by installing kindnet automatically on cluster creation.

Why the Service IP "isn't real" — the exact mechanism A ClusterIP has no interface, no MAC address, nothing to ping. When you create a Service, its ClusterIP + port are registered as an iptables (or IPVS) DNAT rule on every node: "packets destined for 10.96.10.20:80 → rewrite destination to one of {10.244.0.5:80, 10.244.0.6:80, 10.244.0.7:80}, chosen at random." kube-proxy is the controller that watches Endpoints objects and keeps that rule set in sync as pods come and go — which is exactly the self-healing "IP changed but the Service kept working" behavior demonstrated live in class.
Part 3 · Local Kubernetes

09kind — Kubernetes IN Docker

kind (Kubernetes IN Docker) runs an entire Kubernetes cluster using ordinary Docker containers as "nodes." It was originally built by Kubernetes SIG Testing to run Kubernetes' own conformance test suite, and has since become the standard tool for fast, disposable local clusters.

The core trick

Each "node" in a kind cluster is itself a Docker container, running a specially built image (kindest/node) that contains a full containerd runtime, kubelet, and all standard Kubernetes control-plane or worker components inside it. This is genuinely mind-bending: Kubernetes — a container orchestrator — has its own nodes running as containers, orchestrated by Docker underneath.

Because of this, kind clusters have two layers of container nesting that matters when you're troubleshooting networking (exactly the issue hit live in class trying to curl a pod IP from the host):

  • Layer 1: Docker containers = kind "nodes," connected to each other over a Docker bridge network on the host.
  • Layer 2: Inside each node-container, its own containerd runs the actual pods (which are themselves containers, each with their own netns, wired up by kindnet, the default CNI).

This is exactly why you couldn't reach a pod's IP directly from your laptop's shell — that IP only exists on the Docker bridge network inside the kind-node container, one level of isolation deeper than your host.

What kind gives you out of the box

  • A full, CNCF conformance-tested Kubernetes cluster in under a minute, with no VM/hypervisor overhead.
  • Multi-node and multi-control-plane (HA) topologies, defined declaratively in a YAML config.
  • Automatic installation of a default CNI (kindnet), so — unlike a raw kubeadm cluster — nodes come up Ready immediately.
  • Works identically on Linux, macOS, and Windows, wherever Docker (or Podman/nerdctl) runs.

Everyday commands

CommandWhat it does

Multi-node config example

By default, a single container plays both control-plane and worker (which is why the demo pod scheduled onto a node labeled control-plane — something that does not happen on a real cluster, where the control plane is normally tainted to repel workloads). To get a realistic topology, define nodes explicitly:

# kind-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
  # add extraPortMappings under a node to expose services on localhost, e.g.:
  #   extraPortMappings:
  #   - containerPort: 30080
  #     hostPort: 8080
kind create cluster --config kind-config.yaml --name multinode
kubectl get nodes
# multinode-control-plane   Ready   control-plane
# multinode-worker          Ready   <none>
# multinode-worker2         Ready   <none>
Gotcha Reaching a Service or Pod IP from your host browser/terminal generally doesn't work directly against a kind cluster, because those IPs live on the Docker network inside the node containers. Use kubectl port-forward, a NodePort Service combined with extraPortMappings in the kind config, or docker exec into a node, exactly as shown live in the class demo.
Part 4 · Command-line control

11kubectl — the Kubernetes CLI

kubectl is the client that turns your commands into authenticated HTTPS calls to the kube-apiserver. It never talks to etcd, the scheduler, or kubelets directly — everything goes through the API server, exactly like the "receptionist" analogy from class.

Install

# macOS
brew install kubectl

# Linux
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
chmod +x kubectl && sudo mv kubectl /usr/local/bin/

# enable shell autocompletion (bash example)
echo 'source <(kubectl completion bash)' >> ~/.bashrc
echo 'alias k=kubectl' >> ~/.bashrc
echo 'complete -o default -F __start_kubectl k' >> ~/.bashrc

Context & config

Your ~/.kube/config file (the "kubeconfig") stores cluster addresses, credentials, and named contexts — a context bundles "which cluster + which user + which default namespace" under one name, letting you switch between multiple clusters (e.g. kind, EKS, a friend's cluster) instantly.

kubectl config get-contexts
kubectl config current-context
kubectl config use-context kind-multinode
kubectl cluster-info

Reading kubectl describe pod — the Events section

This was called out in class as the single most important troubleshooting habit. A healthy pod's Events read like a story, in order:

Events:
  Type    Reason     Age   From               Message
  ----    ------     ----  ----               -------
  Normal  Scheduled  40s   default-scheduler  Successfully assigned default/my-pod to kind-worker
  Normal  Pulling    39s   kubelet            Pulling image "nginx:latest"
  Normal  Pulled     35s   kubelet            Successfully pulled image "nginx:latest"
  Normal  Created    35s   kubelet            Created container nginx
  Normal  Started    34s   kubelet            Started container nginx

When something is broken, the Events section tells you exactly which stage failed: stuck on Pending/Scheduled often means insufficient resources or an unsatisfied node selector; failures around Pulling/Pulled mean an image or registry-auth problem; anything after Started failing points at the application itself (check kubectl logs next).

Part 5 · Visual tooling

12Freelens — a visual Kubernetes IDE

Freelens is a free, open-source, MIT-licensed desktop application for browsing and managing Kubernetes clusters visually. It is a community-maintained fork of OpenLens (the open-source core that used to power the original Lens Desktop app), created after Lens's commercial owner, Mirantis, restricted the free version and development on OpenLens stalled. Freelens is the actively maintained continuation of that free lineage.

What it actually gives you

  • Cluster list & context switcher — reads your existing ~/.kube/config directly, so every cluster you can already reach with kubectl (including kind clusters) shows up automatically.
  • Live resource views — Pods, Deployments, Services, Nodes, ConfigMaps, Secrets, etc., with real-time status, searchable/sortable tables, in place of typing kubectl get repeatedly.
  • Built-in terminal — both a cluster-wide terminal (pre-authenticated kubectl context) and a per-pod "exec into container" terminal, without typing the full kubectl exec -it … -- sh command.
  • Live log viewer — streaming, searchable, syntax-aware log tailing per container, equivalent to kubectl logs -f but with UI scrollback and highlighting.
  • Resource graphs — CPU/memory usage over time per pod/node (requires metrics-server in-cluster, same as kubectl top).
  • YAML editing in place — view and edit any resource's live YAML directly, equivalent to kubectl edit.
  • Helm support — browse repos and install/upgrade Helm charts through the UI.
  • Extension ecosystem — many original Lens extensions have been ported/are compatible.
  • Ships with bundled kubectl and Helm binaries internally, so it works even on a machine without those tools separately installed.

# Windows — download the installer .exe from GitHub Releases

Connecting Freelens to your kind cluster

  1. Make sure your kind cluster is running and its context exists in ~/.kube/config (this happens automatically when you run kind create cluster).
  2. Open Freelens. It scans your kubeconfig and lists every context it finds, including kind-<cluster-name>, on the cluster catalog / "Hotbar" screen.
  3. Click the kind cluster's tile to connect. Freelens opens a dedicated tabbed pane for it.

Using the built-in console / terminal — step by step

Freelens actually exposes two different kinds of terminal, and it's worth knowing which one you're opening:

1. The cluster terminal (a pre-authenticated kubectl shell)

This is a general-purpose terminal, already pointed at the connected cluster's context — equivalent to opening your own terminal after running kubectl config use-context kind-<name>.

  1. With a cluster open, look at the bottom-right of the window (or the terminal/>_ icon in the top toolbar, depending on version) and click the terminal icon.
  2. A terminal panel slides up from the bottom of the app, docked below the resource view — it behaves like a normal terminal tab (you can open several, each gets its own tab along the bottom edge).
  3. It drops you into a shell with kubectl, helm, and (for kind) usually docker already on the PATH, and KUBECONFIG/context already set to the cluster you have open — so you can type kubectl get pods immediately with no extra setup.
  4. By default this runs a sandboxed /bin/sh bundled with the app, not your real login shell. If you want it to be your actual host shell (so your own aliases, zsh/bash config, and tools are available), go to Preferences → Terminal and set the "Terminal Shell Path" (on Linux this is often pointed at a helper such as host-spawn to escape the app's sandbox; on macOS/Windows you can usually just point it at /bin/zsh, /bin/bash, or powershell.exe).
  5. Close a terminal tab with its ×, or the whole panel with the same terminal-icon toggle.

2. A pod shell (the visual equivalent of kubectl exec -it)

  1. Go to Workloads → Pods in the left sidebar.
  2. Click directly on a pod's name to open its detail page (Overview, Events, and a live YAML view).
  3. On the detail page — or via right-click on the pod's row in the list — find the Shell (sometimes shown as a small terminal/>_ icon next to the pod, or a "Pod Shell" entry in the context menu) and click it.
  4. If the pod has more than one container, Freelens shows a dropdown to pick which container to exec into — the same choice kubectl exec -c <container> makes explicit.
  5. A new terminal tab opens at the bottom, already running the equivalent of kubectl exec -it <pod> -c <container> -- sh -c "clear; (bash || ash || sh)" — it tries bash first and falls back to ash/sh for minimal images (Alpine, distroless-with-shell, etc.).
  6. Type normally; exit with exit or by closing the tab, exactly like leaving an SSH session.

3. Logs (not a shell, but lives in the same area)

  1. From a pod's detail page, click Logs (or the small document icon on its row).
  2. A log panel opens at the bottom with live-tailing output, a search box, timestamp toggle, and a container picker for multi-container pods — the visual equivalent of kubectl logs -f <pod> -c <container>.
  3. You can pop the log view into its own larger window, download the log to a file, or wrap/unwrap long lines from the small toolbar above the log text.
If the pod shell hangs on "Connecting…" or errors This is a known, fairly common rough edge (tracked in Freelens's GitHub issues), usually caused by: the container image genuinely lacking any shell (very minimal/distroless images), an RBAC role missing the pods/exec permission, or a proxy/port conflict on the machine. If the in-app shell won't connect, the reliable fallback is the plain command it's trying to run for you: kubectl exec -it <pod> -n <namespace> -- sh — if that also fails the same way, the problem is the cluster/RBAC/image, not Freelens.

4. Node shell (SSH-like access to a node, not just a pod)

Selecting a node under Nodes and choosing Shell from its menu asks the cluster to schedule a temporary privileged debug pod onto that node and drops you into it — this is Freelens's equivalent of kubectl debug node/<node> -it --image=busybox. On a kind cluster this is rarely needed (you can just docker exec -it kind-control-plane bash instead, since the "node" is already a container on your host) — it's more useful on real cloud clusters where you don't have direct SSH/console access to nodes.

5. Port-forwarding from the UI

  1. Go to Network → Services (or Workloads → Pods for a single pod).
  2. Open the Service you want to reach, and find the Forward / "Port Forward" control near its connection details.
  3. Pick the local port to bind to and click Start — Freelens keeps this tunnel running in the background (recent versions let you pin it to a specific local address), equivalent to leaving a kubectl port-forward svc/<name> 8080:80 command running in a terminal.
How to think about it Freelens doesn't talk to your cluster differently than kubectl does — it's making the exact same authenticated calls to the same kube-apiserver, using the same kubeconfig credentials, and its built-in terminal/shell/logs features are thin visual wrappers around the exact kubectl exec/kubectl logs/kubectl port-forward commands shown above. Everything you see in Freelens, you could reconstruct by typing enough kubectl commands yourself — Freelens just makes it faster to browse, click into, and spot problems across many pods, namespaces, or clusters at once.
Reference

13Glossary

Namespace (Linux)
Kernel feature that gives a process a restricted, isolated view of a global system resource (network, PIDs, mounts, etc.). Not to be confused with a Kubernetes Namespace, which is an unrelated, higher-level concept for organizing API objects.
cgroups
The companion kernel feature to namespaces — limits and accounts for how much CPU, memory, and I/O a process (or group of processes) may use. Namespaces provide isolation; cgroups provide resource limits.
veth pair
A linked pair of virtual Ethernet interfaces; a packet sent into one end appears instantly on the other. The standard way to connect a namespace to a bridge or to another namespace.
Linux bridge
An in-kernel virtual Layer-2 switch. Interfaces (usually veth ends) are attached to it and it forwards frames between them by MAC address.
iptables / nftables
The Linux kernel's packet filtering and NAT rule engines. Used for container port publishing (DNAT), outbound NAT (MASQUERADE), and — inside Kubernetes — implementing Service ClusterIP redirection.
CNI (Container Network Interface)
A CNCF specification defining how a container runtime should invoke executable network plugins to configure a container's network namespace. Not software itself — a contract that plugins implement.
IPAM
IP Address Management — the sub-task (often a separate, delegated CNI plugin like host-local) of choosing which IP address to hand out to a new pod.
CRI (Container Runtime Interface)
The gRPC API kubelet uses to talk to a container runtime (containerd, CRI-O) without needing to know its implementation details.
Pod sandbox
The "infra"/pause container that owns a pod's shared Linux namespaces (network, IPC) before any application container starts — this is why containers in the same pod can reach each other over localhost.
ClusterIP
A Kubernetes Service's default virtual IP — exists only as routing/NAT rules on every node, not attached to any real network interface.
Control loop / reconciliation
The core Kubernetes pattern: a controller continuously compares desired state (what you declared) against actual state (what's really running) and takes action to close any gap.
kind
"Kubernetes IN Docker" — runs full Kubernetes nodes as Docker containers for fast local/CI clusters.
kindnet / kindnetd
The lightweight default CNI plugin kind installs automatically so clusters come up Ready without any manual CNI installation step.
kubectl context
A named bundle of {cluster address, user credentials, default namespace} stored in kubeconfig, letting you switch which cluster your commands target.
Freelens
Free, open-source, MIT-licensed desktop GUI for Kubernetes; community fork of OpenLens, using your existing kubeconfig to browse/manage clusters visually.
