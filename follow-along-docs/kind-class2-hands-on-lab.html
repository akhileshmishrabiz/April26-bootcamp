  - role: worker
  - role: worker

Exercise 2

02Contexts, made real by a second cluster

Do this

Goal: contexts are invisible with one cluster. Create a second one specifically to make the ambiguity — and the risk — concrete.

kind create cluster --name extra-one
kubectl get node
NAME                       STATUS   ROLES           AGE
extra-one-control-plane    Ready    control-plane   20s
# only 1 node — this is extra-one, NOT your 3-node cluster, even though you didn't ask to switch
The exact trap demonstrated live Creating extra-one silently made it the current context. Running kubectl get node right after returned 1 node — correct for extra-one, but easy to mistake for "my multi-node cluster only has 1 node ready," if you weren't watching which cluster you were actually talking to. This is the mechanism the instructor warned about directly: run a destructive command without checking context first, and you can wipe the wrong environment. 
kubectl config get-contexts
CURRENT   NAME              CLUSTER           NAMESPACE
*         kind-extra-one    kind-extra-one
          kind-kind         kind-kind

kubectl config use-context kind-kind
Switched to context "kind-kind".

kubectl get node
NAME                 STATUS   ROLES           AGE
kind-control-plane   Ready    control-plane   4m
kind-worker          Ready    <none>          4m
kind-worker2         Ready    <none>          4m

In ~/.kube/config, each cluster contributes a cluster entry (name, endpoint, cert data), a user entry, and a context entry that pairs the two under a name you can switch by — the context name is independently renameable and is what current-context actually points at.

Clean up the throwaway cluster once you've seen the switch work:

kind delete cluster --name extra-one

Exercise 4

04DaemonSets, proven live

Do this

Goal: see, not just hear, why some workloads need "exactly one pod per node" — a guarantee Deployments don't provide.

kubectl get pods -A -o wide | grep kindnet
kube-system   kindnet-4x2kq   1/1   Running   kind-control-plane
kube-system   kindnet-8pqvz   1/1   Running   kind-worker
kube-system   kindnet-wj3rl   1/1   Running   kind-worker2
# 3 pods, 3 nodes — one each. In Class 1's single-node cluster this was always exactly 1.

kubectl get daemonset -A
NAMESPACE     NAME         DESIRED   CURRENT   READY   NODE SELECTOR
kube-system   kindnet      3         3         3       <none>
kube-system   kube-proxy   3         3         3       <none>
Why not just use a Deployment with replicas: 3? A Deployment's replica count is a cluster-wide total — the scheduler is free to put all 3 on one node, 2-and-1, whatever satisfies the number. Nothing about Deployment ties a replica to a specific node. A DaemonSet's contract is different: by default, exactly one pod per node, automatically extended to any node added later. That's why CNI plugins (kindnet), kube-proxy, and node-level observability agents (e.g. OpenTelemetry collectors) are DaemonSets — each node needs its own copy to function at all, not just "3 copies somewhere."

05ConfigMap vs Secret — and what SPC/ESO are (not built yet)

Concept only — no manifest yet

Goal: understand the two object types and the env-var-vs-volume-mount tradeoff before writing either, since Exercises 6–13 build both for real.

ObjectHoldsEnv var mountVolume mount
ConfigMapNon-sensitive config, key-valueSet at pod start; needs a restart to pick up changesUpdates live, no restart, needs app-side path handling
SecretCredentials, key-value, base64-encoded at restSame as aboveSame as above
Question raised in class — Secret vs. Secret Provider Class (SPC) ConfigMap and Secret are native Kubernetes objects. An SPC is a completely different mechanism — used when the actual secret material should live outside the cluster, in something like AWS Secrets Manager or Vault, and get pulled in via a CSI driver, the External Secrets Operator (ESO), or a Vault injector. The instructor named ESO specifically as what he plans to teach, explicitly deferring it — not covered in this lab. Worth remembering as the answer to "isn't storing a base64 value in YAML insecure?" — yes, and SPC/ESO is the real answer to that, just not today's.

Exercise 7 — Failure #1

07The naming regex error

Reproduce this on purpose

Goal: hit the exact validation error from class, read what it's actually telling you, and fix it by understanding the pattern rather than guessing.

kubectl apply -f deployment.yaml
error: metadata.name: Invalid value: "2TF": a lowercase RFC 1123 subdomain must consist
of lower case alphanumeric characters, '-' or '.', and must start and end with an
alphanumeric character (e.g. 'example.com', regex used for validation is
'[a-z0-9]([-a-z0-9]*[a-z0-9])?(\.[a-z0-9]([-a-z0-9]*[a-z0-9])?)*')
Reading the regex, not just obeying it [a-z0-9]([-a-z0-9]*[a-z0-9])? says: start with a lowercase letter or digit, then any run of lowercase letters/digits/hyphens, ending on a letter or digit — no uppercase, no underscores, no leading/trailing hyphen. This is the same rule behind every Kubernetes object name, not something specific to Deployments. Class-assigned homework: two YouTube videos on regex fundamentals (Python and Linux), worth doing since this exact pattern-reading skill comes up constantly in Kubernetes and CI configs. 
# fix: name -> flask (already lowercase in the manifest above if you copied it as-is)
kubectl apply -f deployment.yaml
deployment.apps/flask created
Exercise 8 — Failure #2

08ImagePullBackOff and imagePullSecrets

Reproduce, then fix

Goal: hit a real private-registry auth failure, understand the full token chain behind it, then wire the fix correctly — at the pod level, not the container level.

kubectl get pods
NAME                     READY   STATUS             RESTARTS   AGE
flask-6d7f8c9b5-4x2kq    0/1     ImagePullBackOff   0          45s

kubectl describe pod flask-6d7f8c9b5-4x2kq
Events:
  Warning  Failed     kubelet  Failed to pull image: no basic auth credentials
  Warning  BackOff    kubelet  Back-off pulling image "<ecr-repo>:1.0"
The full auth chain, before the fix aws ecr get-login-password generates a temporary token → passed to docker login, which authenticates and stores a credential locally (in ~/.docker/config.json on Linux; not visible the same way on Mac). That local credential exists on your laptop only — the cluster has no copy of it, which is exactly why kubelet can't pull the private image. The fix is giving the cluster its own copy of equivalent auth data, as a Secret. 
aws ecr get-login-password --region <region> > /tmp/ecr-token

kubectl create secret docker-registry ecr-secret \
  --docker-server=<account-id>.dkr.ecr.<region>.amazonaws.com \
  --docker-username=AWS \
  --docker-password="$(cat /tmp/ecr-token)"
secret/ecr-secret created
# deployment.yaml — note imagePullSecrets is a POD-level field, not container-level
spec:
  template:
    spec:
      imagePullSecrets:
        - name: ecr-secret
      containers:
        - name: flask
          image: <ecr-repo>:1.0
          imagePullPolicy: Always
imagePullPolicyWhen
AlwaysRe-pull every time — used here, since the image lives in ECR and should always be current
IfNotPresentPull only if missing locally — the common default
NeverOnly ever use a locally-built image — relevant later when building images directly inside kind
kubectl apply -f deployment.yaml
kubectl get pods
NAME                     READY   STATUS             RESTARTS   AGE
flask-6d7f8c9b5-9f7mc    0/1     ImagePullBackOff   0          10s
# still failing — but with DIFFERENT error text now. That's Exercise 9.
Exercise 9 — Failure #3

09Architecture mismatch

Reproduce, then fix

Goal: recognize a genuinely different failure signature from Exercise 8's, and understand why it's specific to newer Apple Silicon Macs.

kubectl describe pod flask-6d7f8c9b5-9f7mc
Events:
  Warning  Failed   kubelet   exec format error / no matching manifest for linux/arm64
# different error than Exercise 8 — auth now works, but the image binary is for the wrong CPU architecture
Why this one's Mac-specific The image was originally built for linux/amd64 and is being run on Apple Silicon (M1/M2/M3/M4), which is arm64. Windows users in the same class didn't hit this at all. The fix is rebuilding without forcing a --platform override, letting Docker default to the host's native architecture. 
docker build -t <ecr-repo>:2.0 .
# no --platform flag this time — defaults to your Mac's native arch
docker push <ecr-repo>:2.0
# update deployment.yaml image tag to :2.0, then:
kubectl apply -f deployment.yaml
deployment.apps/flask configured

kubectl get pods -w
flask-7a1b2c3d4-p9q8r    1/1     Running   0          8s
# this apply is also your first live rolling update — see Exercise 14 for the mechanics

10The port-5000-vs-8000 mystery

Reproduce, then fix

Goal: work an actual multi-step debugging sequence — logs, exec, and dropping to the node level — for a bug whose cause turned out to be a stale image, not a code bug.

kubectl port-forward svc/flask-svc 9090:80
# tunnel opens, but the app doesn't respond correctly at localhost:9090

kubectl logs flask-7a1b2c3d4-p9q8r
Starting gunicorn... Listening at: http://0.0.0.0:5000
# unexpected — app code, run.py, run.sh, and gunicorn_conf.py all specify 8000
The checks that ruled out a code bug run.py, run.sh, and gunicorn_conf.py were all checked directly and all correctly said 8000 — so the source wasn't wrong. Confirmed live inside the container too: 
kubectl exec -it flask-7a1b2c3d4-p9q8r -- sh
/ # netstat -tlnp
tcp   0.0.0.0:5000   LISTEN
# still 5000 — so drop to the node level and test the image directly, bypassing k8s entirely

docker exec -it kind-control-plane bash
root@kind-control-plane:/# docker run --rm -it <ecr-repo>:3.0
Listening at: http://0.0.0.0:8000
# a freshly-rebuilt image (3.0) is correct — the previously deployed image was stale/mismatched
# push the confirmed-correct 3.0 image, update the deployment, re-apply
docker push <ecr-repo>:3.0
kubectl apply -f deployment.yaml
kubectl logs <new-pod>
Listening at: http://0.0.0.0:8000

kubectl port-forward svc/flask-svc 9090:80
# now http://localhost:9090 responds correctly

11The Opaque Secret, and the echo -n trap

Reproduce the encoding bug, then fix it

Goal: build the DB-link Secret properly, and hit the exact base64 newline trap that caused real confusion in class before two separate causes got untangled.

# the trap — try this first, exactly as done live:
echo "postgresql://appuser:pw@tiny-pg.xxxx.rds.amazonaws.com:5432/appdb" | base64
cG9zdGdyZXNxbDovL2FwcHVzZXI6cHdAdGlueS1wZy54eHh4LnJkcy5hbWF6b25hd3MuY29tOjU0MzIvYXBwZGIK
# that trailing "K" segment encodes a newline echo silently appended — invisible until you decode it back

echo "postgresql://appuser:pw@tiny-pg.xxxx.rds.amazonaws.com:5432/appdb" | base64 | base64 --decode
postgresql://appuser:pw@tiny-pg.xxxx.rds.amazonaws.com:5432/appdb

↑ that blank line after appdb IS the bug — a real newline baked into the "decoded" value
The fix — and a second, unrelated error that looked related echo -n suppresses the trailing newline echo adds by default — always use it when piping into base64 for a Secret value. A second error ("unknown field DB_LINK") surfaced separately during the same debugging and was actually a YAML indentation problem under data:, not an encoding problem — worth distinguishing the two rather than assuming one fix covers both. 
echo -n "postgresql://appuser:pw@tiny-pg.xxxx.rds.amazonaws.com:5432/appdb" | base64
cG9zdGdyZXNxbDovL2FwcHVzZXI6cHdAdGlueS1wZy54eHh4LnJkcy5hbWF6b25hd3MuY29tOjU0MzIvYXBwZGI=
# no trailing newline this time — verify:
echo -n "..." | base64 | base64 --decode
postgresql://appuser:pw@tiny-pg.xxxx.rds.amazonaws.com:5432/appdb
# no blank line — correct
# secret.yaml — mind the indentation under `data:`
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  DB_LINK: cG9zdGdyZXNxbDovL2FwcHVzZXI6cHdAdGlueS1wZy54eHh4LnJkcy5hbWF6b25hd3MuY29tOjU0MzIvYXBwZGI=
kubectl apply -f secret.yaml
secret/db-secret created

12Wiring Secret/ConfigMap values via *KeyRef

Do this

Goal: replace the hardcoded DB-link value from Exercise 6 with a real reference into the Secret built in Exercise 11.

# deployment.yaml, inside the container spec
env:
  - name: DB_LINK
    valueFrom:
      secretKeyRef:
        name: db-secret
        key: DB_LINK

The ConfigMap equivalent is identical in shape, swapping secretKeyRef for configMapKeyRef:

env:
  - name: APP_MODE
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: APP_MODE
kubectl apply -f deployment.yaml
kubectl logs <pod>
# confirm the app is reading the real DB_LINK value now, not the hardcoded one from Exercise 6

Goal: trigger the third of three canonical "why is my pod Pending" interview causes — a missing ConfigMap dependency — by applying the Deployment before the ConfigMap exists.

14Rolling updates at three speeds

Do this — the live comparison from class

Goal: see maxSurge/maxUnavailable actually change rollout behavior, not just read about them. Scale up first so the differences are visible.

kubectl scale deployment flask --replicas=10
kubectl get pods -w
# wait for all 10 to reach Running before continuing

Speed 1 — default (no strategy block set)

# bump the image tag, then:
kubectl apply -f deployment.yaml
kubectl get pods -w
flask-...-new1   0/1   ContainerCreating
flask-...-old1   1/1   Terminating       ← only ONE at a time, old first replaced before next starts

Speed 2 — fast (maxSurge: 4, maxUnavailable: 4)

spec:
  strategy:
    rollingUpdate:
      maxSurge: 4
      maxUnavailable: 4
kubectl apply -f deployment.yaml
# up to 4 old pods terminated and 4 new pods created simultaneously — visibly faster

Speed 3 — slow (maxSurge: 1, maxUnavailable: 1)

spec:
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
kubectl apply -f deployment.yaml
# visibly the slowest of the three, one pod replaced at a time again but explicit this time
The takeaway stated explicitly in class Rolling update is the default Deployment strategy — the very first image bump in Exercise 9 already used it, with no strategy field set at all. Real-world tuning tends to use percentage-based values (e.g. maxUnavailable: 10%) rather than raw counts, to balance rollout speed against availability risk at real scale — with 100 replicas, you don't want 50 down simultaneously. This document doesn't have a live percentage-syntax demo to show, since the class discussed it but didn't run one — worth trying yourself as a follow-up.

15Pod Disruption Budgets — concept only

Concept only — not built this class

Goal: understand what a PDB constrains, and how it differs from rolling-update tuning, before building one in a future class.

Rolling-update settings (Exercise 14) govern disruption you trigger — deploying a new image version. A PodDisruptionBudget governs disruption the cluster/infra triggers — node drains, node upgrades, maintenance events. It sets a floor (count or percentage) on how many pods must stay available; Kubernetes will reschedule pods elsewhere first rather than violate that floor when draining a node.

# shape only — not applied in this class
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: flask-pdb
spec:
  minAvailable: 8
  selector:
    matchLabels:
      app: flask

19Glossary (lab-specific terms)

Context
A named pairing of cluster + user in ~/.kube/config. current-context decides which cluster a bare kubectl command targets.
DaemonSet
A controller guaranteeing exactly one pod per node (by default), unlike Deployment's cluster-wide replica total. Used for CNI plugins, kube-proxy, and per-node agents.
imagePullSecrets
A pod-level (not container-level) field listing Secrets containing registry auth data, needed to pull private images.
Opaque Secret
The generic Secret type for arbitrary key-value credential data, as opposed to the more structured docker-registry or tls types.
secretKeyRef / configMapKeyRef
Fields under env[].valueFrom that pull a single key's value from an existing Secret or ConfigMap into an environment variable, rather than hardcoding it.
Secret Provider Class (SPC)
Not a native Kubernetes object — a mechanism (via CSI driver or ESO) for backing a mounted volume with a secret stored in an external system like AWS Secrets Manager or Vault.
maxSurge / maxUnavailable
RollingUpdate strategy fields controlling how many extra pods can be created / how many can be unavailable simultaneously during a Deployment update.
PodDisruptionBudget (PDB)
Sets a floor on available replicas during voluntary disruptions (node drains/upgrades) — distinct from rolling-update tuning, which governs deployment-triggered replacement.
