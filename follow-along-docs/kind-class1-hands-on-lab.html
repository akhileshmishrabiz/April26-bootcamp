Before you begin

00Install & sanity check

If you've already been through the companion namespaces/CNI document, this will be quick. If not, here's the minimum to get moving — the deep "why" for each tool lives in that other document, this one is about doing.

# 1. Docker Desktop (or Docker Engine on Linux) must be running — kind needs it.
docker version

# 2. Install kind
#   macOS:
brew install kind
#   Linux:
curl -Lo ./kind https://kind.sigs.k8s.io/dl/latest/kind-linux-amd64 && chmod +x ./kind && sudo mv ./kind /usr/local/bin/kind
#   Windows (admin PowerShell):
choco install kind

# 3. Install kubectl
#   macOS:
brew install kubectl
#   Linux:
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl" && chmod +x kubectl && sudo mv kubectl /usr/local/bin/

# 4. Confirm both are on your PATH and talking sense
kind version
kubectl version --client

Optional but recommended: install Freelens too (covered fully in the companion doc) so you can watch these exercises happen visually alongside the terminal. Not required for anything below.

A note on how to use this document Every exercise below is something your instructor actually did live in Class 1 — reconstructed here so you can type it yourself, at your own pace, and actually see the output rather than just watch it happen. Wherever the class demo hit a snag (the DNS lookup that didn't work, not being able to curl a pod IP from the laptop), this guide explains exactly why, and shows the working version.
Exercise 1

01Create your first kind cluster

Do this

Goal: stand up a real, working Kubernetes cluster in under a minute.

kind create cluster
Creating cluster "kind" ...
 ✓ Ensuring node image (kindest/node:v1.31.0) 🖼
 ✓ Preparing nodes 📦
 ✓ Writing configuration 📜
 ✓ Starting control-plane 🕹️
 ✓ Installing CNI 🔌
 ✓ Installing StorageClass 💾
Set kubectl context to "kind-kind"
You can now use your cluster with:

kubectl cluster-info --context kind-kind

Notice the two lines called out above: "Installing CNI" and "Installing StorageClass" — kind does these for you automatically. On a raw kubeadm cluster you'd have to install a CNI plugin yourself before any node reaches Ready, exactly as covered in the CNI reference document.

kubectl cluster-info
Kubernetes control plane is running at https://127.0.0.1:xxxxx
CoreDNS is running at https://127.0.0.1:xxxxx/api/v1/namespaces/kube-system/services/kube-dns:dns/proxy

kind get clusters
kind
What kind create cluster actually did, in namespace/CNI terms It pulled a kindest/node image, started it as a Docker container named kind-control-plane, and — inside that container — ran kubeadm init-equivalent bootstrapping, then applied kindnetd (the default CNI) so nodes reach Ready without a manual step. Your ~/.kube/config was updated automatically with a new context named kind-kind.

03A bare pod — and why it won't self-heal

Do this

Goal: prove, hands-on, that a pod created directly (imperatively) has nobody watching over it.

kubectl run my-pod --image=nginx
pod/my-pod created

kubectl get pod
NAME     READY   STATUS    RESTARTS   AGE
my-pod   1/1     Running   0          8s

kubectl get pod -o wide
NAME     READY   STATUS    RESTARTS   AGE   IP           NODE
my-pod   1/1     Running   0          15s   10.244.0.5   kind-control-plane

Now kill it and watch what (doesn't) happen:

kubectl delete pod my-pod
pod "my-pod" deleted

kubectl get pod
No resources found in default namespace.
The point of this exercise Nothing came back. A bare pod has no controller behind it — kubectl run is an imperative, one-off command real teams rarely use for anything beyond quick throwaway testing. Kubernetes' famous "self-healing" promise is a property of controllers (Deployments, ReplicaSets, StatefulSets, DaemonSets, Jobs) — not of pods themselves. This is exactly why the next exercise switches to a Deployment.

04Deployments & real self-healing

Do this

Goal: create a Deployment, understand the Deployment → ReplicaSet → Pod naming chain, and prove self-healing actually works this time.

kubectl create deployment my-deploy --image=nginx --replicas=3
deployment.apps/my-deploy created

kubectl get pods
NAME                         READY   STATUS    RESTARTS   AGE
my-deploy-6d7f8c9b5-4x2kq    1/1     Running   0          12s
my-deploy-6d7f8c9b5-8pqvz    1/1     Running   0          12s
my-deploy-6d7f8c9b5-wj3rl    1/1     Running   0          12s

Read the pod names left to right: my-deploy (the Deployment) → 6d7f8c9b5 (a hash identifying the ReplicaSet) → 4x2kq (a random suffix for this individual pod). Confirm the middle layer exists:

kubectl get replicaset
NAME                    DESIRED   CURRENT   READY   AGE
my-deploy-6d7f8c9b5     3         3         3       40s

kubectl get deployment
NAME        READY   UP-TO-DATE   AVAILABLE   AGE
my-deploy   3/3     3            3           45s

Now delete one pod and immediately re-check:

kubectl delete pod my-deploy-6d7f8c9b5-4x2kq
pod "my-deploy-6d7f8c9b5-4x2kq" deleted

kubectl get pods
NAME                         READY   STATUS    RESTARTS   AGE
my-deploy-6d7f8c9b5-8pqvz    1/1     Running   0          58s
my-deploy-6d7f8c9b5-wj3rl    1/1     Running   0          58s
my-deploy-6d7f8c9b5-9f7mc    1/1     Running   0          3s     ← brand new pod, new IP
What just happened, mechanically The ReplicaSet's controller loop noticed current (2) ≠ desired (3) and immediately asked the scheduler for one more pod. This is the "control loop" pattern from class: continuously compare desired state to actual state and reconcile the difference — the exact same reconciliation model that etcd/controller-manager implement for every resource type in Kubernetes, not just Deployments.
Gap in the class demo, worth flagging On a real cluster (EKS, kubeadm, etc.), the control-plane node is normally tainted (node-role.kubernetes.io/control-plane:NoSchedule) so ordinary workloads never land on it — only the control-plane's own system pods run there. kind's single-node default cluster removes that taint so your one node can run everything, purely for local-dev convenience. Don't take "my pod got scheduled onto the control-plane node" as normal cluster behavior — it's a kind-specific simplification. If you want a topology that behaves like production, use the multi-node config from Exercise 4 of the companion document (one control-plane + two workers) and you'll see this taint enforced correctly.

05Reaching a pod's IP — the docker exec detour

Do this

Goal: reproduce (and understand) exactly why curl-ing a pod IP from your own laptop terminal fails, and what actually works.

# get a pod's IP
kubectl get pods -o wide
NAME                         READY   STATUS    IP            NODE
my-deploy-6d7f8c9b5-8pqvz    1/1     Running   10.244.0.6    kind-control-plane

# try it directly from your laptop shell — this will hang or fail:
curl 10.244.0.6
curl: (28) Failed to connect to 10.244.0.6 port 80: Connection timed out

This fails because 10.244.0.6 is a pod IP on the CNI's internal bridge network, which exists inside the kind-control-plane Docker container — one layer of network isolation deeper than your host, exactly as covered in the nested-container discussion. Your laptop's network stack has no route to it at all.

The fix demonstrated in class — get inside the node container first:

docker ps
CONTAINER ID   IMAGE                  NAMES
a1b2c3d4e5f6   kindest/node:v1.31.0   kind-control-plane

docker exec -it kind-control-plane bash
# now you are INSIDE the node container's shell
root@kind-control-plane:/# curl 10.244.0.6
<!DOCTYPE html>
<html>
<head><title>Welcome to nginx!</title></head>
...
The "3 pods but only 1 container in docker ps" question If you've been through this document's earlier discussion: this is the same nesting. docker ps on your host only ever shows Docker containers your host's Docker daemon created — that's one entry per kind node, never per pod. The 3 nginx pods are containers managed by the containerd running inside kind-control-plane, which your host's Docker daemon cannot see at all. From inside the node shell, the tool that lists those is crictl (talks to containerd's CRI socket directly), not docker ps — kind nodes don't run a nested Docker daemon, only containerd: 
root@kind-control-plane:/# crictl ps
CONTAINER ID   IMAGE          STATE       NAME    POD ID
9f8e7d6c5b4a   nginx:latest   Running     nginx   ...
7a6b5c4d3e2f   nginx:latest   Running     nginx   ...
5c4b3a2d1e0f   nginx:latest   Running     nginx   ...
Why this whole detour is a debugging technique, not a workflow docker exec-ing into a node to curl a raw pod IP is useful for exactly what it was used for in class: proving pod IPs are real and reachable at the network level. It is not how you access an application day-to-day. Exercises 7 and 9 below show the two real methods: a stable Service, and kubectl port-forward / NodePort for reaching things from your actual host browser.

06Writing Deployment + Service YAML from scratch

Do this

Goal: move from imperative commands to real manifests, and deliberately hit (then fix) the label-mismatch bug from class so it sticks.

Clean up first so you're starting fresh:

kubectl delete deployment my-deploy

Create a folder and a Deployment manifest:

mkdir ~/k8s-lab && cd ~/k8s-lab
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-deploy
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          ports:
            - containerPort: 80
The exact bug hit live in class — reproduce it on purpose If your Service's selector doesn't say app: nginx to match the pod template's label exactly, the Service will show 0 endpoints and silently fail to route anywhere — no error, just nothing works. In class, the Service was first written with name: my-app as its selector while the pods were labeled app: nginx — a mismatch that took a moment to spot. Try writing service.yaml below with a deliberately wrong selector first (e.g. name: nginx instead of app: nginx), apply it, run kubectl get endpoints and see it come back empty — then fix the selector and watch endpoints populate. This is the single most common real-world Service bug, and deliberately breaking it once here will save you hours later. 
# service.yaml — selector MUST match the pod template's labels above
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app: nginx
  ports:
    - protocol: TCP
      port: 8080
      targetPort: 80
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
deployment.apps/my-deploy created
service/my-service created

kubectl get svc
NAME          TYPE        CLUSTER-IP     PORT(S)
my-service    ClusterIP   10.96.45.112   8080/TCP

07Endpoints & the self-updating Service

Do this

Goal: prove the ClusterIP is "not real" (no interface) and watch kube-proxy keep it in sync automatically as pods die and are replaced — the exact demo from class, done fully.

kubectl get endpoints my-service
NAME         ENDPOINTS
my-service   10.244.0.7:80,10.244.0.8:80,10.244.0.9:80

Confirm it round-robins across all three pods (from inside the node, same detour as Exercise 5):

docker exec -it kind-control-plane bash
root@kind-control-plane:/# for i in 1 2 3 4; do curl -s 10.96.45.112:8080 | grep -o "Welcome to nginx"; done

Now kill one backing pod and watch endpoints update themselves within seconds, with zero manual action:

kubectl delete pod my-deploy-6d7f8c9b5-8pqvz
kubectl get endpoints my-service
NAME         ENDPOINTS
my-service   10.244.0.7:80,10.244.0.9:80,10.244.0.11:80   ← .8 is gone, .11 is the replacement
Tie this back to the networking document 10.96.45.112:8080 never had a network interface — it only ever existed as an iptables/IPVS DNAT rule that kube-proxy maintains by watching this exact Endpoints object. The moment the Endpoints list changed, kube-proxy rewrote the rule set on every node, in real time, with no restart of anything. This is the mechanism behind the "self-healing service" behavior demoed in class.

08DNS resolution, done right

Do this — fixes the part that didn't work in class

Goal: actually get my-service.default.svc.cluster.local to resolve, and understand precisely why the in-class attempt (running nslookup from inside the docker exec node shell) didn't.

Why it failed in class — the real reason Every pod gets its /etc/resolv.conf written by kubelet at pod-creation time, pointing at CoreDNS's ClusterIP (typically something like 10.96.0.10) with search domains like default.svc.cluster.local. That file is injected into the pod's own network namespace. The node's root network namespace — which is exactly where you land after docker exec -it kind-control-plane bash — has its own separate /etc/resolv.conf, usually just pointing at whatever DNS your Docker host uses. It was never configured to know about CoreDNS or the .svc.cluster.local suffix at all. Running nslookup/curl <service-name> from that shell was, structurally, never going to resolve a cluster DNS name — it wasn't a CoreDNS bug, it was asking DNS resolution from the wrong network namespace entirely.

The fix: run the DNS lookup from inside a pod, where the correct resolv.conf actually exists. Spin up a disposable debug pod with working DNS tools:

kubectl run dnsutils --image=busybox:1.28 --restart=Never -it -- sh
# you're now inside a pod's shell, in the pod's own network namespace
/ # cat /etc/resolv.conf
nameserver 10.96.0.10
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

/ # nslookup my-service
Server:    10.96.0.10
Address 1: 10.96.0.10 kube-dns.kube-system.svc.cluster.local

Name:      my-service
Address 1: 10.96.45.112 my-service.default.svc.cluster.local

/ # wget -qO- my-service:8080 | head -5
<!DOCTYPE html>
<html>
<head><title>Welcome to nginx!</title></head>

/ # exit
# clean up the debug pod when done
kubectl delete pod dnsutils
Small but real gotcha: image choice matters Newer busybox:latest images have a well-known, intermittent nslookup bug (musl libc's resolver sometimes reports "can't resolve" even when the record exists, then succeeds on retry). Pinning busybox:1.28 as used above avoids it. If you want a more full-featured debug image instead, nicolaka/netshoot or the official registry.k8s.io/e2e-test-images/jessie-dnsutils image both ship dig, nslookup, and curl with no quirks.

Notice you didn't even need the full name — just my-service resolved correctly. That's the search line in resolv.conf doing its job: Kubernetes appends .default.svc.cluster.local (and other suffixes) automatically until one resolves, exactly as covered in the DNS documentation.

09Reach nginx from your actual browser

Do this — the payoff exercise

Goal: the thing the class demo never quite got to — actually opening the nginx page in your host machine's browser, the two proper ways.

Method A — kubectl port-forward (fastest, zero config)

kubectl port-forward svc/my-service 8080:8080
Forwarding from 127.0.0.1:8080 -> 80
Forwarding from [::1]:8080 -> 80

Leave that running, then open http://localhost:8080 in your actual browser — you should see the "Welcome to nginx!" page. Press Ctrl+C in the terminal to stop forwarding when done.

This works because kubectl port-forward opens an authenticated tunnel through the API server straight to the pod/service — it doesn't rely on any Docker-level port mapping at all, which is why it works even though you never configured one.

Method B — NodePort + kind's extraPortMappings (closer to how real clusters expose things)

Port-forward is great for quick checks but isn't how a real, always-on app gets exposed. Recreate your cluster with a config file that maps a container port through to your host:

# kind-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 30080
        hostPort: 8080
        protocol: TCP
kind delete cluster
kind create cluster --config kind-config.yaml
kubectl apply -f deployment.yaml

Change the Service to type NodePort, pinning the exact node port to match the mapping above:

# service-nodeport.yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service-nodeport
spec:
  type: NodePort
  selector:
    app: nginx
  ports:
    - port: 8080
      targetPort: 80
      nodePort: 30080
kubectl apply -f service-nodeport.yaml
kubectl get svc
NAME                   TYPE       CLUSTER-IP     PORT(S)
my-service-nodeport    NodePort   10.96.88.20    8080:30080/TCP

Now open http://localhost:8080 — no kubectl port-forward process needs to stay running this time.

Filling the gaps

10What class 1 didn't cover (but you should know now)

1. Resource requests & limits

Class 1 never set CPU/memory requests or limits on the nginx containers — meaning they could use unlimited resources on the node. In any real manifest, add this under each container:

resources:
  requests:
    cpu: "100m"
    memory: "64Mi"
  limits:
    cpu: "250m"
    memory: "128Mi"

requests is what the scheduler uses to decide which node has room for this pod. limits is a hard ceiling — exceed the memory limit and the container gets OOM-killed; exceed the CPU limit and it just gets throttled, not killed.

2. Readiness & liveness probes

Without these, Kubernetes considers a container "ready" the instant its process starts — even if the app inside is still booting. A basic pair for nginx:

readinessProbe:
  httpGet:
    path: /
    port: 80
  initialDelaySeconds: 2
  periodSeconds: 5
livenessProbe:
  httpGet:
    path: /
    port: 80
  initialDelaySeconds: 5
  periodSeconds: 10

A failing readiness probe removes the pod from Service endpoints (traffic stops routing to it) without killing it. A failing liveness probe restarts the container. This is the mechanism that makes rolling deployments actually safe.

3. metrics-server (needed for kubectl top)

The class demo hit "metrics API not available" when running kubectl top pod. Fix it on kind with:

kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
# kind's kubelet certs are usually self-signed and untrusted by default, so metrics-server needs one extra flag:
kubectl patch deployment metrics-server -n kube-system --type='json' \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'

kubectl top nodes
kubectl top pods

4. Kubernetes Namespaces vs. Linux namespaces — don't conflate them

Class 1 used the word "namespace" for both the Kubernetes organizational concept (default, kube-system, etc.) and, in the companion doc, the Linux kernel isolation primitive. They are unrelated concepts that happen to share a name. A Kubernetes Namespace is a way of scoping API objects (RBAC, quotas, names) — it has nothing to do with a container's network/PID/mount namespace at the kernel level.

5. Multi-container pods — a working example

Class 1 explained sidecars conceptually but never wrote one. Here's a minimal working example — a sidecar that tails and reformats nginx's logs:

spec:
  containers:
    - name: nginx
      image: nginx:latest
    - name: log-sidecar
      image: busybox:1.28
      command: ["sh", "-c", "tail -F /var/log/nginx/access.log"]
      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/nginx
  volumes:
    - name: shared-logs
      emptyDir: {}

Both containers share the pod's network namespace (hence localhost works between them) and, here, an explicitly shared emptyDir volume for files.

6. Context switching between multiple clusters

kubectl config get-contexts
kubectl config use-context kind-kind
kubectl config set-context --current --namespace=default

7. imagePullPolicy — a common source of confusion

Using image: nginx:latest as the class did means Kubernetes' default imagePullPolicy: Always kicks in for the :latest tag — every pod creation re-pulls the image, even if it's already cached locally. Pin real versions (nginx:1.27) in anything beyond a quick demo, both for reproducibility and to avoid unnecessary pulls.

Reference

13Glossary (lab-specific terms)

Imperative command
A one-shot kubectl command (run, create deployment without -f) that creates a resource directly, with no YAML file and no easy way to reproduce it later. Fine for quick tests, avoided in real workflows.
Declarative manifest
A YAML file applied with kubectl apply -f — the standard, repeatable, version-controllable way to manage resources.
Selector / label mismatch
The single most common Service bug: the Service's spec.selector doesn't exactly match the pod template's metadata.labels, so the Service has zero endpoints and silently routes nowhere.
crictl
The CLI for talking directly to a CRI-compatible container runtime (containerd, CRI-O) — the "docker ps" equivalent to run from inside a node, since node-level containerd is invisible to your host's Docker.
resolv.conf (pod-scoped)
Kubelet writes a fresh one into every pod's network namespace at creation time, pointing at CoreDNS. It does not exist, and is not inherited, in the node's root network namespace.
NodePort
A Service type that opens the same port on every node in the cluster, forwarding to the Service. Combined with kind's extraPortMappings, this is how you expose something to your host machine without leaving a kubectl port-forward process running.
kubectl port-forward
Opens an authenticated tunnel through the API server directly to a pod or Service — works regardless of any Docker-level port mapping, ideal for quick local checks.
